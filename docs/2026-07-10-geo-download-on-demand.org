It captures the feature, the design the architect + a codebase exploration

three-phase workflow).

* Summary
Today the geo stack is *NorCal-only* (a self-hosted Nominatim geocoder + MOTIS
routing/transit + the Bay-Area 511 GTFS feed). This feature lets assist *download
additional geographic regions on demand*: when a query needs a place assist can't
locate in the loaded region, the agent *proposes* downloading that region (showing
a map of its extent *and the exact download size*); *you approve* through a
human-in-the-loop gate (the same shape as approving an outbound text); a
background job imports the region and, when it finishes, *notifies the agent via
a new message on the originating thread* — the travel skill directs the agent to
the appropriate next step, typically using the new geo to satisfy your original
intent. There is *no automatic re-run* of the old prompt. Plus a *geo management
page* to list/delete loaded regions and add a per-region transit layer.

The load-bearing safety idea (Pierre's steer): the protection is the *HITL approval
before the download fires* — a region import is expensive and privileged, so it
never runs until you've explicitly OK'd that specific region while seeing its map.
Whether the agent reaches the proposal user-driven ("which region?") or
auto-detected is then a secondary UX question, because the approval gate protects
either way.

* Decisions (settled in PR #194 review, 2026-07-10)

** D1 — Trigger detection: *user-driven for v1* (pre-review option 1a; "start here, expand later")
The ambiguity: =_geocode= returns the *same empty result* for an out-of-region
real place AND a typo/nonexistent place — locally we can't tell them apart. So
for v1: on "couldn't find that place," the agent states what it covers ("I have
Northern California"), asks whether the place is in another region, and proposes
a download only when you point it at one. No new service. Auto-detect (a
worldwide existence/bbox lookup that names the region proactively) is a later
refinement. Either way the *approval gate* (D-fixed below) is the safety
mechanism, so this was scope/UX, not safety.

** D2 — Catalog = the *Geofabrik central index*, narrowed by user intent
Pierre asked: is there no central index? There is. Geofabrik publishes a
machine-readable index of *all* its extracts —
=https://download.geofabrik.de/index-v1.json= (and a lighter =-nogeom= variant):
~555 regions worldwide, each with a stable id (e.g. =norcal=, =socal=,
=us/washington=), display name, parent, the official PBF download URL, and (in
the full variant) the region polygon, from which the bbox derives. Verified
2026-07-10. The index carries *no file sizes*; exact size comes from an HTTP
=HEAD= on the PBF URL (=Content-Length=, after one redirect — e.g. SoCal ≈
666 MB, verified) — which is also how the approval prompt gets its deterministic
size figure (see D-fixed).

So instead of a hand-seeded shortlist, the *catalog is a pinned snapshot of the
full-variant index* (the bbox derives from its geometry) stored in
=$TRAVEL_INFRA_DIR= — refreshed by the weekly cron, which also =HEAD=-caches
each region's size into the snapshot, so nothing is fetched live on the request
path; the one live =HEAD= happens at proposal time, giving the approval message
its exact current figure. The *curation happens at selection
time, by intent*: the agent (guided by the travel skill) narrows the index to
the region matching what you asked for ("do you cover Seattle?" →
=us/washington=), and the =/geo/add= picker offers a searchable list rather
than a fixed menu. The allowlist property is unchanged — a slug must be an
index id and the URL always comes from the index entry, never from the caller.
Prefer the *smallest extract covering the need* (sub-state over state over
country) to bound import cost. The *transit-feed overlay stays hand-curated*
(only regions where we've configured a feed, e.g. 511 =RG= for the Bay Area) —
there is no worldwide GTFS index to lean on.

** D3 — Geocoder rebuild cost: *accept the full rebuild for v1* (pre-review option 3a; agreed)
Adding a region requires a *full Nominatim rebuild* (its Docker image only imports
into an empty DB): minutes–hours, and geocoding degrades platform-wide to MOTIS's
weaker built-in geocoder *while the rebuild runs* (routing stays up). MOTIS routing
itself is cheap-incremental — only geocoding has this cost. Because a rebuild only
ever fires *after* you approve a specific region (D-fixed), the cost is bounded to
something you opted into. Deterministic, reuses the working refresh recipe; the
agent warns you it takes a while. The incremental / multi-PBF import path
(community-reported flaky) stays a possible later optimization.

** D4 — Import finishes while the LLM is busy: *hold + retry the notification* (pre-review option 4a; agreed)
The import can finish while the local LLM is saturated (e.g. the nightly eval).
The completion notification (see § Background-job architecture step 4 — a new
message to the agent, *not* a blind re-run of the last prompt) needs the LLM, so
it is held and retried until the LLM is free — we want the agent to pick the
work back up, not drop it.

** D-fixed (from Pierre's steer) — always HITL before download, *size shown*
=request_region_download= never fires an import without your explicit approval,
via the existing approval flow, with the region's map shown. No silent/auto
provisioning. (This is the "protection is HITL before download, like a text
message send" steer.) Additionally (PR #194): the approval message *must state
the total download size*, and that figure is *deterministic* — computed by code
via an HTTP =HEAD= (=Content-Length=) on the catalog's PBF URL at proposal time
— never a number the agent supplies. (The agent isn't denied the information; it
just isn't the source of it.) The later transit-add flow (its own action, outside
this proposal) sizes its GTFS download the same =HEAD=-computed way.

* What you asked for (intent)
- When asked for geo-specific info assist can't find in the current region, *offer
  to download* that region; when it's loaded, *let the agent know via a new
  message* so it takes the appropriate next step (typically: use the new geo to
  satisfy the original intent). Not an automatic re-run of the old prompt.
- When offering, *display a map* of the region's extent and *state the total
  download size* (computed deterministically, not agent-supplied) so you see
  what's being downloaded and what it costs.
- A *geo management page*: list all loaded regions, delete unused ones.
- *Transit is not bundled by default* — GTFS/511 is a separate, region-specific
  source than base OSM geocode/routing. A fresh region gives addresses +
  driving/walking/biking but *not* transit; transit is a separate opt-in per-region
  layer, and the agent must tell you when transit isn't available for a region.

* Current stack (ground truth, from exploration)
- *Tools* (=assist/tools.py=, in-process host tools on the general agent, not
  sandboxed, reach localhost directly): =_geocode= (=tools.py:496=) → Nominatim
  (=ASSIST_GEOCODER_URL=, =:461=) or a MOTIS fallback; =_motis_get= (=:424=, the
  single MOTIS HTTP boundary, =ASSIST_ROUTING_URL=); =travel= / =directions= /
  =map_data=; registered at =agent.py:382=.
- *Trigger ambiguity*: an out-of-region address and a typo both yield =None= from
  =_geocode=; =_resolve_od= (=tools.py:562=) turns that into "I couldn't find a
  place matching …". No local way to distinguish → D1.
- *Services*: MOTIS (routing + transit in one, =127.0.0.1:8088=) ingests OSM + GTFS
  from =$TRAVEL_INFRA_DIR=; Nominatim (=127.0.0.1:8089=, a Postgres volume).
  Transit = the 511 regional GTFS feed (operator =RG=, needs =ASSIST_511_TOKEN=),
  Bay-Area-specific.
- *No provisioning script and no regions registry exist.* Services were stood up by
  hand (documented, not scripted). The only automation is
  =scripts/refresh-travel-data.sh= (weekly refresh) — the template for the new
  scripts (flock, validate-before-swap, argv-not-shell, token-never-in-argv). Its
  =reimport_motis= (=:145=) imports in-place; =reimport_nominatim= (=:158=)
  destroys + rebuilds the volume.
- *Asymmetry (central)*: adding/removing a region is seconds–minutes for MOTIS,
  minutes–hours + destructive for Nominatim (→ D3).
- *Reusable web machinery*: =_render_map_block= (=manage/web/threads.py:1924=)
  already draws agent-authored =pin:= / =path:= lines as a *sandboxed null-origin
  Leaflet iframe* with vendored Leaflet + OSM tiles. A region bbox = a closed
  5-point ring encoded as a =path:= — *no new render type, no new security surface*.
- *Background-job template*: =assist/schedule/scheduler.py= is exactly the shape
  needed — a daemon poll thread + single-worker executor + health gate + in-flight
  dedup, dispatching via =_scheduled_dispatch(tid, prompt, tz)=
  (=manage/web/threads.py:1372=). Nothing in it touches the asyncio loop.
- *"It's ready" signal*: the urgent/notify seam (=assist/events/notify.py=,
  =_mark_urgent= in =manage/web/state.py:485=). =notify= is on the NORMAL tool set,
  NOT the untrusted SMS-triage set — the precedent for gating the new tools.

* Design
** Safety model — HITL approval gate before the import (the spine)
A region import is expensive (D3) and privileged (spawns docker/curl). So it is
modeled like an outbound side effect that requires approval:
1. The agent *proposes* a download: =request_region_download(slug)= records a
   *pending proposal* on the thread and renders the region's *bbox map preview*
   plus the *total download size* — fetched by code via HTTP =HEAD= on the
   catalog's PBF URL (deterministic, never an agent-supplied figure). Nothing
   heavy runs.
2. You *approve* through the existing approval flow (the same mechanism the
   SMS-send reply uses — =awaiting_approval= + the thread's approve control). On
   decline, the proposal is dropped.
3. Only on approval does the =Provisioner= enqueue the import. This makes "an
   untrusted input caused a multi-hour disk-filling docker import" *unreachable by
   construction* — a chat message or an inbound text can at most produce a proposal
   you must still approve.

Open detail for implementation: reuse the reply-approval seam vs a small dedicated
"pending download" approval. Recommend reusing the existing approval flow so
there's one HITL pattern, not two.

** Component decomposition (Löwy roles)
| Role            | Component                                              | Volatility encapsulated        |
|-----------------+--------------------------------------------------------+--------------------------------|
| Resource        | =regions.json= (infra dir); OSM/GTFS files; MOTIS =config.yml=; Nominatim volume | what data is loaded |
| Resource Access | =assist/geo/registry.py= — sole reader/writer of =regions.json= | registry format + location |
| Engine          | =scripts/add-region.sh=, =scripts/remove-region.sh= — heavy import/evict recipes | how a region is imported/evicted |
| Manager         | =assist/geo/provisioner.py= — off-loop background worker (mirrors =Scheduler=) | job orchestration + liveness |
| Client (web)    | =manage/web/geo.py= — =/geo= list/add/delete/transit routes | the management UI |
| Client (agent)  | travel =SKILL.md= guidance + =list_regions()= + =request_region_download(slug)= | agent behavior |
| Utility         | the *catalog* — a pinned snapshot of the Geofabrik index (slug → URL, bbox) + the hand-curated transit-feed overlay (D2) | the allowlist of what may be fetched |

The trigger, the page, and the delete path all depend on the registry Resource-Access
abstraction, not on MOTIS/Nominatim internals — so the architecture stays static.

** Regions registry — the unambiguous source of truth
A dedicated =regions.json= in =$TRAVEL_INFRA_DIR=, written *only* by the
provisioning scripts, read by everyone else via =assist/geo/registry.py=. Per
region: =slug=, =display_name=, =bbox [minlon,minlat,maxlon,maxlat]=,
=geofabrik_url=, =osm_file=, =has_transit=, =transit_source=, =size_bytes=,
=added_at=, =state (ready|importing|failed)=, =job_log=. The base NorCal region is
seeded =ready= / =has_transit:true= / =transit_source:"511:RG"=.

Why a dedicated file, not derived from =config.yml= + Nominatim: =config.yml=
carries no bbox / display name / transit flag / date / import-state, and the geo
page + trigger + delete path would each re-derive it. The ethos wants the "is this
region loaded" question to have *one unambiguous answer* — a registry. Consistency
is bounded by making the scripts the sole writers and flipping =state:ready= only
after a validated import (the validate-before-swap discipline the refresh script
already uses). All reads happen off the event loop (=run_in_threadpool=).

** Background-job architecture (event-loop-safe by construction)
Web/agent only *enqueue*; a =Provisioner= (mirroring =Scheduler=) runs the heavy
work in a *subprocess*; on success it dispatches the completion notification.
1. *Enqueue (on-loop-safe)*: on approval, =Provisioner.submit(slug, origin_tid)=
   writes =state:importing= and does a non-blocking executor submit. No lock, no
   subprocess, no sleep on the loop.
2. *Execute (off-loop)*: a =ThreadPoolExecutor(max_workers=1)= (one import at a
   time — disk-bound, and Nominatim can't overlap itself) + per-slug in-flight
   dedup (the =Scheduler._claim/_release= pattern). The worker runs
   =subprocess.run(["scripts/add-region.sh", slug])= — a detached, bounded child.
   *Nothing heavy touches the loop, the THREAD_QUEUE, or the LLM slot.*
3. *Status*: coarse registry states (=importing= → =ready= / =failed=) + a per-job
   log; no percent (imports give no clean progress). =/geo= polls the registry like
   =/thread/{tid}/status=.
4. *Tell the agent when done* (no automatic re-run — PR #194): on child exit 0,
   dispatch =_scheduled_dispatch(origin_tid, "<completion message>", tz)= +
   =_mark_urgent= — a new human-style message on the originating thread stating
   that the <region> download finished. The travel =SKILL.md= directs the agent's
   next step: usually, use the newly loaded geo to satisfy the user's original
   intent (the thread history carries that intent — the message does NOT replay
   the old prompt). The chat turn ended long ago, so this is a fresh turn —
   exactly the scheduled-prompt model. On exit≠0 → =state:failed= + a "download
   failed" notice (no blind retry). Per D4, if the LLM is busy/down at completion
   the dispatch is held + retried until it's free.

Why in-process Provisioner-runs-a-subprocess over =systemd-run= / cron: it reuses
the proven Scheduler + script shapes and the completion-dispatch seam is already
wired — one moving part. Its one weakness (a web restart mid-import orphans the job) is handled
by a startup *reconcile* (mirror =Scheduler.reconcile=): any =importing= entry with
no live job → =failed=; validate-before-swap means nothing half-built is ever served.

Event-loop lens (Phase-2 test): hold the provisioning lock in another thread, assert
=POST /geo/add= still returns promptly.

** Trigger detection (per D1 — user-driven for v1)
On a "couldn't find a place" result the agent does NOT silently fail and does NOT
guess. Guided by =SKILL.md=, it calls =list_regions()= to state coverage, asks
whether the place is elsewhere, and *proposes* a catalog region's download (map
preview + size) — which you then approve (HITL). The auto-detect path (a
planet/coarse existence check that names the region for you) is a deferred later
refinement (D1); when it comes, the proposal → approval → import chain stays
identical.

** Provisioning scripts (Engine)
=scripts/add-region.sh <slug>= mirrors =refresh-travel-data.sh= (flock at
=$TRAVEL_INFRA_DIR/.provision.lock=, validate-before-swap, argv-not-shell, atomic
renames):
1. *Validate slug against the catalog allowlist* (the security seam). Charset
   =[a-z0-9/-]= (index ids can nest, e.g. =us/washington=; no leading/trailing
   =/=, no =..=); slug must be an id in the pinned index snapshot; the download
   URL comes from the index entry, never the caller. On-disk names flatten =/=
   to =-= (=us-washington.osm.pbf=) so a slug never forms a path.
2. *Download* the extract → validate PBF (size floor AND ceiling + =OSMHeader=,
   the refresh script's checks).
3. *MOTIS (cheap)*: drop =<flattened-slug>.osm.pbf= into =input/=, append a dataset to
   =config.yml=, =motis import= in-place, restart on success (=reimport_motis=).
4. *Nominatim (heavy, destructive)*: re-merge all region PBFs (osmium) or pass the
   multi-PBF path, then full rebuild into a fresh volume (extend
   =reimport_nominatim=). Degrades geocoding platform-wide while it runs (D3).
5. *Transit (optional)*: only if the catalog defines a feed for the slug.
6. *Registry*: write bbox/size/date/=has_transit=, flip =state:ready= — atomically,
   last.
=scripts/remove-region.sh <slug>= is symmetric: refuse the base region, drop the
PBF + config entry, re-merge remaining, MOTIS reimport + Nominatim rebuild, update
the registry.

** Transit as a separate opt-in per-region layer
A region records =has_transit= + =transit_source=. A fresh region is
=has_transit:false=. Transit exists only where the *catalog* configures a feed for
that region (operator id + URL/token pattern, like 511 =RG=) — there is no generic
nationwide GTFS, so this is "transit only where a feed is configured." Opt-in:
=scripts/add-region.sh <slug> --with-transit= (or a =/geo/{slug}/transit= button) —
fetch the configured GTFS, add a MOTIS GTFS dataset, MOTIS reimport (cheap, no
Nominatim touch), flip =has_transit:true=. If no feed is configured, the button is
absent. The agent (guided) states plainly "transit isn't available for <region>
(driving, walking, biking are)" — the data is already honest (=_plan_transit=
returns =None= → "unavailable"); the guidance makes it *name the region*.

** Geo management page
A new submodule =manage/web/geo.py= (the schedules.py/evals.py registration
pattern). Routes:
- =GET /geo= — list regions from the registry, each with a *bbox map preview* (bbox
  → encoded polyline → an existing =path:= map block), =state=, size, date,
  =has_transit=, a delete button, and an "add transit" button when a feed is
  configured and transit is off.
- =GET /geo/add= — the catalog picker: a *searchable* list over the pinned
  Geofabrik-index snapshot (D2), each region with a bbox map preview and the
  download size the weekly refresh cached into the snapshot (no live fetch on
  the request path).
- =POST /geo/add= — enqueue (write =importing= + =Provisioner.submit=); 303
  redirect. *Never* runs the import inline.
- =POST /geo/{slug}/delete= — enqueue eviction; base region undeletable (guard);
  UI confirm.
- =POST /geo/{slug}/transit= — enqueue add-transit.
- A small status fragment polls =importing= → =ready= (like
  =/thread/{tid}/status=), so a heavy import is never on the loop.
Map preview reuses the existing =path:= renderer — no new render type, no new
security surface (the null-origin sandbox already contains it).

** Agent tool surface + guidance
Two new tools, both thread-scoped like =notify=, both on the *normal* web tool set
only (NOT the SMS-triage set):
- =list_regions()= — read-only; returns =ready= regions + =has_transit=. Called on
  a place miss, on "what areas do you cover," and before saying transit is
  unavailable. Deterministic, cheap, no import.
- =request_region_download(slug)= — validates =slug= against the catalog allowlist,
  records a *pending proposal* (HITL) with the map preview and the *code-computed
  download size* (HTTP =HEAD=, per D-fixed); the import fires only on your
  approval. *The agent's only path to an import* — the slug is allowlisted, so
  untrusted input never reaches a free-form URL/shell.
Small model → checkable structure over prose (=CLAUDE.md=: "the instruction's shape
matters more than its content"). =SKILL.md= gains a "Regions" section with checkable
steps: on a miss call =list_regions()= + name coverage + ask; propose a download
only for a catalog region; after a route in a =has_transit:false= region, name that
transit is unavailable there. Alignment-check: examples cover the *shape* ("do you
cover Seattle?", "download San Diego") not eval prompts verbatim; the eval suite
probes cases the wording doesn't telegraph.

* Threat model / attack surface (the Phase-2 security spec)
Untrusted inputs: a user chat message, an agent-filled =slug= arg, a =POST
/geo/add= body. Sinks: the provisioning subprocess (docker, curl, osmium, rm).
Containment by construction:
1. *Slug → allowlist, always* (tool + route). Charset =[a-z0-9/-]= with no
   leading/trailing =/= and no =..= (index ids nest, e.g. =us/washington=);
   slug must be an id in the pinned index snapshot; the download URL is the
   index entry's, never caller-supplied; on-disk names flatten =/= to =-= so a
   slug never forms a path; slug passed as argv, never shell-interpolated.
   Untrusted value never reaches the fetch URL, a filesystem path, or a shell.
2. *HITL gate*: even a valid slug only yields a *proposal*; the import needs your
   approval — so an inbound text can't trigger a multi-hour import / disk fill.
3. *Disk exhaustion*: cap total loaded regions + total bytes; validate download size
   floor AND ceiling (the index includes continent-scale extracts, so the ceiling —
   checked against the =HEAD= size before approval AND enforced at download — is
   what keeps them unloadable); one import at a time.
4. *Delete the wrong data*: slug allowlist + registry lookup; base region
   undeletable; the script removes only registry-owned files under =input/= — no
   path from input to an arbitrary =rm=.
5. *Secrets*: the 511 (and any future) token stays in the token file, read via
   =sed=, never argv/logs (the refresh-script pattern).
6. *Map preview*: registry/agent-authored but rendered through the existing
   null-origin sandboxed iframe — already contained.
7. *New endpoints* inherit the app's existing auth posture (localhost/PWA); =/geo/*=
   mutating routes are POST-only + enqueue-only.

* Risks & edge cases
- *Nominatim rebuild degrades the whole geocoder* while any region is added/removed
  — falls back to MOTIS for all regions until done. Message the user; accept (D3).
  Biggest user-visible wart.
- *Originating thread deleted before import finishes* → the completion-message
  dispatch no-ops on a missing thread (guard).
- *Web restart mid-import* → startup reconcile marks stuck =importing= → =failed=.
- *Two requests for the same region* → per-slug in-flight dedup.
- =config.yml= *concurrent edit* (weekly refresh cron vs add-region) → both take the
  same flock.
- *MOTIS RAM growth as regions accumulate* → cap region count; document.
- *Model over-proposing downloads on typos* → guidance gates on you asserting the
  place is real / naming a region; evals include typo cases that must NOT propose a
  download.
- *Bbox missing for a region* → the catalog carries it; else =osmium fileinfo=.
- *Failed partial import* → validate-before-swap + =state:failed=; MOTIS
  in-place-then-restart never leaves routing down.
