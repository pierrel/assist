It captures the feature, the design the architect + a codebase exploration

* Summary
Today the geo stack is *NorCal-only* (a self-hosted Nominatim geocoder + MOTIS
routing/transit + the Bay-Area 511 GTFS feed). This feature lets assist *download
additional geographic regions on demand*: when a query needs a place assist can't
locate in the loaded region, the agent *proposes* downloading that region (showing
a map of its extent *and the exact download size*); *you approve* through a
human-in-the-loop gate (the same shape as approving an outbound text); a
background job imports the region and, when it finishes, *notifies the agent via
a new message on the originating thread* — the travel skill directs the agent to
the appropriate next step, typically using the new geo to satisfy your original
intent. There is *no automatic re-run* of the old prompt. Plus a *geo management
page* to list/delete loaded regions and add a per-region transit layer.

The load-bearing safety idea (Pierre's steer): the protection is the *HITL approval
before the download fires* — a region import is expensive and privileged, so it
never runs until you've explicitly OK'd that specific region while seeing its map.
Whether the agent reaches the proposal user-driven ("which region?") or
auto-detected is then a secondary UX question, because the approval gate protects
either way.

* Decisions (settled in PR #194 review, 2026-07-10)

** D1 — Trigger detection: *user-driven for v1* (pre-review option 1a; "start here, expand later")
The ambiguity: =_geocode= returns the *same empty result* for an out-of-region
real place AND a typo/nonexistent place — locally we can't tell them apart. So
for v1: on "couldn't find that place," the agent states what it covers ("I have
Northern California"), asks whether the place is in another region, and proposes
a download only when you point it at one. No new service. Auto-detect (a
worldwide existence/bbox lookup that names the region proactively) is a later
refinement. Either way the *approval gate* (D-fixed below) is the safety
mechanism, so this was scope/UX, not safety.

** D2 — Catalog = the *Geofabrik central index*, narrowed by user intent
Pierre asked: is there no central index? There is. Geofabrik publishes a
machine-readable index of *all* its extracts —
=https://download.geofabrik.de/index-v1.json= (and a lighter =-nogeom= variant):
~555 regions worldwide, each with a stable id (e.g. =norcal=, =socal=,
=us/washington=), display name, parent, the official PBF download URL, and (in
the full variant) the region polygon, from which the bbox derives. Verified
2026-07-10. The index carries *no file sizes*; exact size comes from an HTTP
=HEAD= on the PBF URL (=Content-Length=, after one redirect — e.g. SoCal ≈
666 MB, verified) — which is also how the approval prompt gets its deterministic
size figure (see D-fixed).

So instead of a hand-seeded shortlist, the *catalog is a pinned snapshot of the
full-variant index* (the bbox derives from its geometry) stored in
=$TRAVEL_INFRA_DIR= — refreshed by the weekly cron, which also =HEAD=-caches
each region's size into the snapshot, so nothing is fetched live on the request
path; the one live =HEAD= happens at proposal time, giving the approval message
its exact current figure. The *curation happens at selection
time, by intent*: the agent (guided by the travel skill) narrows the index to
the region matching what you asked for ("do you cover Seattle?" →
=us/washington=), and the =/geo/add= picker offers a searchable list rather
than a fixed menu. The allowlist property is unchanged — a slug must be an
index id and the URL always comes from the index entry, never from the caller.
Prefer the *smallest extract covering the need* (sub-state over state over
country) to bound import cost. The *transit-feed overlay stays hand-curated*
(only regions where we've configured a feed, e.g. 511 =RG= for the Bay Area) —
there is no worldwide GTFS index to lean on.

** D3 — Geocoder rebuild cost: *accept the full rebuild for v1* (pre-review option 3a; agreed)
Adding a region requires a *full Nominatim rebuild* (its Docker image only imports
into an empty DB): minutes–hours, and geocoding degrades platform-wide to MOTIS's
weaker built-in geocoder *while the rebuild runs* (routing stays up). MOTIS routing
itself is cheap-incremental — only geocoding has this cost. Because a rebuild only
ever fires *after* you approve a specific region (D-fixed), the cost is bounded to
something you opted into. Deterministic, reuses the working refresh recipe; the
agent warns you it takes a while. The incremental / multi-PBF import path
(community-reported flaky) stays a possible later optimization.

** D4 — Import finishes while the LLM is busy: *hold + retry the notification* (pre-review option 4a; agreed)
The import can finish while the local LLM is saturated (e.g. the nightly eval).
The completion notification (see § Background-job architecture step 4 — a new
message to the agent, *not* a blind re-run of the last prompt) needs the LLM, so
it is held and retried until the LLM is free — we want the agent to pick the
work back up, not drop it.

** D-fixed (from Pierre's steer) — always HITL before download, *size shown*
=request_region_download= never fires an import without your explicit approval,
via the existing approval flow, with the region's map shown. No silent/auto
provisioning. (This is the "protection is HITL before download, like a text
message send" steer.) Additionally (PR #194): the approval message *must state
the total download size*, and that figure is *deterministic* — computed by code
via an HTTP =HEAD= (=Content-Length=) on the catalog's PBF URL at proposal time
— never a number the agent supplies. (The agent isn't denied the information; it
just isn't the source of it.) The later transit-add flow (its own action, outside
this proposal) sizes its GTFS download the same =HEAD=-computed way.

* Design-review outcomes (2026-07-10, 5-lens team + code-verified)
A parallel design-review team ran all five Phase-1 lenses (simplicity, agentic/
framework-fit, user-intention, clean-interfaces, threat-model). The three
BLOCKERs and the two cross-lens design shifts were *verified against the actual
code* before adoption. Net: the safety spine (HITL-before-import, allowlisted
slug, off-loop provisioner, =path:=-render reuse) is sound; the changes below
tighten it and cut ~250–350 LOC of over-build. Sections further down are revised
to match; this is the change record.

** BLOCKERs (verified, adopted)
- *B1 — the agent can't obtain a valid slug → it would hallucinate Geofabrik ids*
  (agentic-fit). =list_regions()= returns only *loaded* regions; nothing exposes
  the ~555-entry catalog, yet =request_region_download(slug)= needs an id like
  =us/washington= (country-prefixed, nested slash) vs =socal= (bare codename).
  Qwen3.6 can't reproduce that scheme → allowlist-reject loop on the single LLM
  slot. *Fix (adopted):* add a read-only =find_regions(query)= host tool — code
  searches the pinned snapshot by display-name AND geocodes the query against each
  region's bbox/polygon, returning candidate =\{slug, display_name, size_bytes,
  bbox\}= ranked *smallest-extract-covering-first*. The model passes the place name
  *as the user said it* (the existing =_geocode= name→resolve pattern); the commit
  tool's slug *must originate from =find_regions= output* (a checkable arg-shape
  constraint — the lever this model obeys). Bonus: makes "smallest extract" +
  "size shown" code-enforced, and is the deferred D1 auto-detect existence check
  for free (a name that geocodes to no catalog bbox ⇒ likely a typo ⇒ no proposal).
- *B2 — "reuse the SMS-reply approval seam" is broken as wired* (agentic-fit +
  clean-interfaces + threat-model). VERIFIED: =thread_manager.py:281=
  =interrupt_on = _web_interrupt_on if triage else None= — the deepagents HITL
  interrupt is armed *only on triage (inbound-SMS) turns*; a region proposal fires
  on a *normal* chat turn where =interrupt_on= is =None=, so the interrupt cannot
  fire there. =thread.py:253= =pending_reply()= is =send_reply=-specific end to
  end. *Fix (adopted):* a *dedicated pending-proposal record*, not the send_reply
  interrupt. The =propose_region_download= tool body records the proposal (slug +
  bbox + size) on the =/geo= machinery, emits the =path:= map block, and returns;
  a plain =POST /geo/{slug}/approve= (like =/geo/add=) fires the provisioner. One
  HITL shape, no hot-path interrupt refactor, and the map/size (which need code to
  run *before* approval) fit naturally in the tool body — the interrupt-before-body
  model couldn't render them.
- *B3 — the flock doesn't actually exclude* (threat-model). VERIFIED:
  =refresh-travel-data.sh:61= locks =.refresh.lock=; the PRD's add-region locked a
  *different* file =.provision.lock= → *no mutual exclusion*. An approved import
  firing near the 03:00 refresh cron interleaves two destructive Nominatim rebuilds
  (=docker volume rm= under an in-flight import + torn =config.yml=) → corrupted
  geocoder. *Fix (adopted):* ONE shared lock path taken by refresh + add + remove +
  transit (change the refresh script to it in the same PR); the Provisioner
  acquires it non-blocking so a queued import waits out the cron.

** Cross-lens design shifts (adopted)
- *Provisioner is a thin executor, NOT a =Scheduler= clone* (simplicity +
  clean-interfaces). This flow is event-driven (submit once on approval), not a
  cron — drop the poll loop / =due= / =tick= / health-gate / in-flight-dedup
  (=max_workers=1= + the shared flock + the =state:importing= pre-write already
  serialize). It's ~40 lines: a module-level =ThreadPoolExecutor(max_workers=1)=, a
  =submit(op, slug, origin_tid=None)= (=op ∈ \{add, remove, transit\}=; =origin_tid=
  only for agent-proposed adds), and a startup =importing→failed= sweep. Coupling to
  the web is *injected callbacks* (=Provisioner(registry, run_job, on_complete,
  health_check)=), never imports up into =manage/web= — mirroring
  =Scheduler(store, dispatch, health_check)= and =notify=. Saves ~100 LOC + a whole
  daemon mental model.
- *Registry: ONE writer, thinned fields* (clean-interfaces B1 + simplicity). The
  doc contradicted itself (table said =registry.py= sole writer; body said the bash
  scripts write it; step 1 had the Provisioner write it). Resolve toward the
  =ScheduleStore= precedent: *=registry.py= is the sole reader+writer*; the bash
  scripts write *nothing* to =regions.json= (they do data work only), the
  Provisioner writes =importing= then =ready=/=failed= via =registry.py=. Thin the
  record to what's actually read — =slug=, =state=, =has_transit=, =display_name=,
  =bbox=, =last_used_at= (see U3), =completion_delivered= (D4 durability, below);
  drop =geofabrik_url= / =osm_file= / =transit_source= / =job_log= (derivable from
  the catalog-by-slug or a fixed log path). Every dropped field is one fewer
  sync-divergence site.

** IMPORTANT — user-intention (U)
- *U1 — draw the real region polygon, not a bbox rectangle.* The snapshot's full
  index variant already carries the region polygon (bbox derives from it), and the
  =path:= renderer draws polylines — so the true outline costs nothing extra. A bbox
  for =us/washington= is mostly ocean + neighboring states; it doesn't answer "what
  am I downloading," the whole point of the preview. Encode the polygon ring as the
  =path:= (cap points if payload-heavy); fall back to bbox only if geometry is
  absent.
- *U2 — put the degradation cost on the approval message, deterministically.* The
  dominant cost isn't bytes — it's the hours-long *platform-wide geocoding
  degradation* during the Nominatim rebuild (D3). That currently lives only in soft
  agent prose — the exact shape Pierre rejected for size. Add a fixed, code-supplied
  line to the approval message beside the size: e.g. "Adding a region rebuilds the
  geocoder (up to a few hours); address lookups for all regions are degraded until
  it finishes."
- *U3 — "delete UNUSED" needs a usage signal.* The page shows add-date/size, never
  last-used, so deletion is uninformed. Stamp a coarse =last_used_at= when a
  geocode/route resolves inside a region's bbox and surface "used N days ago" on the
  page. (If query-path tracking is judged too costly for v1, defer it *explicitly* —
  don't silently reduce "unused" to "list".)
- *U4 — transit: OFFER to add when a feed exists but isn't loaded.* Today the
  guidance only ever says "unavailable," even when a feed is configured and transit
  is one opt-in away. Branch the guidance on feed-configured: if addable, the agent
  *offers* to add transit (its own HITL action), mirroring the download offer — this
  is the "work transit in" Pierre asked for.
- *U5 — label the proposal with the region =display_name=* (treated as untrusted —
  see T6) and *state transit is a separate layer* on the page (one line).

** IMPORTANT — agentic / small-model (A)
- *A1 — code carries the original intent into the completion message.* A bare "the
  <region> download finished" + thread history asks Qwen3.6 to re-locate + re-derive
  the original intent (multi-hop over stale context — the small model drops this).
  Store the originating request on the proposal record and interpolate it: "The
  <region> data you were waiting on is loaded. The user originally asked: '<request>'.
  Complete that now." This is NOT an auto-re-run (Pierre's steer holds — it's a
  self-contained new turn naming the intent; the agent still decides *how*).
- *A2 — =has_transit= must be in tool output* (=list_regions=/=find_regions=), so
  "name transit unavailable for <region>" is checkable against a result, not model
  memory. (Guidance-appropriate; no middleware.)
- *A3 — typo over-proposal is eval-bounded, not middleware.* Expect the small model
  to over-propose on typos; the HITL gate is the real protection (a spurious proposal
  costs a decline), and =find_regions='s geocode (typo ⇒ no catalog bbox ⇒ no
  proposal) is the by-construction damper. Do NOT add an ambiguous-signal middleware
  guard. Prove the bound with evals (below).

** IMPORTANT — threat-model (T) — [B3 above is the blocker; these are the rest]
- *T1 — CSRF/auth on the destructive =/geo= routes.* VERIFIED: only =/inbound/sms=
  authenticates (=X-Assist-SMS-Secret=, =threads.py:1423=); every other mutating
  route relies on network posture. =POST /geo/\{slug\}/delete= triggers a destructive
  Nominatim rebuild off one forgeable POST gated only by a client-side =confirm()=.
  The whole safety model is "no import without a real human approval" — but on the
  web path that approval *is* an unauthenticated POST. *Fix:* a server-side token
  (reuse the =X-Assist-SMS-Secret= shape, or an anti-CSRF token) on =/geo/add=,
  =/approve=, =/delete=, =/transit=; server-side re-confirm delete.
- *T2 — the index PBF URL is a trusted-into-=curl= sink.* "URL always from the index"
  contains the *caller*, not the third-party JSON. A poisoned/hand-edited snapshot
  entry (=file://=, =http://169.254.169.254=, a redirect-following HEAD) reaches
  =curl=. *Fix:* validate every catalog URL is =https://= on an allowlisted host
  (=download.geofabrik.de=/known mirror) at snapshot-refresh AND before each fetch;
  =curl --proto '=https'=; constrain redirect targets to the same host.
- *T3 — enforce the size ceiling DURING download, not from the HEAD.* A hostile host
  can advertise a small =Content-Length= then stream unboundedly (chunked omits it)
  → disk fill → the documented fork()-denial. *Fix:* =curl --max-filesize <CEIL>
  --max-time <T>=, THEN a post-download =stat= ≤ ceiling before import. One coarse
  disk bound (region-count cap sized to the rebuild's transient peak ≈ several×
  sum(PBF)), not three overlapping caps.
- *T4 — resolve the live-HEAD ⇄ cached-size tension* (threat-model F4 said drop the
  live HEAD; simplicity #3 said drop the weekly 555-HEAD cache — opposite). *Adopted
  middle:* size comes from the snapshot (cached at refresh — but lazily / for
  candidates, NOT 555 weekly HEADs), surfaced by =find_regions=; *no live HEAD on
  the request path* (it held the =THREAD_QUEUE= turn slot + re-opened T2). If an
  exact figure is ever required, a single off-loop HEAD in the tool body with the T2
  host/scheme constraint + a tight timeout — never in the approval renderer, never
  on the loop.
- *T5 — detached Nominatim import vs registry state.* =reimport_nominatim= starts a
  detached =docker run -d= and returns; the volume is destroyed up front and the
  region isn't queryable until the async import finishes. *Fix:* the script blocks on
  import completion + a =/status= 200 before flipping =state:ready= (a restart then
  kills the blocking child → reconcile→failed is the correct consistent outcome), not
  fire-and-forget.
- *T6 — prompt injection via the index =display_name=.* The completion message +
  =find_regions=/=list_regions= output must build agent-facing text from the *slug*
  (bounded allowlist) + code copy, never interpolate the raw third-party
  =display_name= into the prompt; if shown, confine it to the map label (already a
  capped sandboxed text node).
- *Nits:* slug→filename collision (store =osm_file= explicitly or reversible-encode);
  =rm=/osmium =basename=-confine registry paths; the =/geo/add= picker must not render
  ~555 Leaflet iframes (paginate/filter first, build HTML in =run_in_threadpool=);
  transit-add token discipline (=curl -K= stdin, never argv; keep the fetch URL out of
  the job log).

* Design
** Safety model — HITL approval gate before the import (the spine)
A region import is expensive (D3) and privileged (spawns docker/curl). So it is
modeled like an outbound side effect that requires approval:
1. The agent *proposes* a download: =propose_region_download(slug)= (slug from
   =find_regions=, per B1) records a *pending-proposal record* on the =/geo=
   machinery and renders the region's *polygon map preview* (U1) plus the
   *total download size* (from the snapshot cache — T4, no live request-path HEAD)
   and the *code-supplied degradation warning* (U2). Nothing heavy runs.
2. You *approve* via a plain =POST /geo/{slug}/approve= (server-token-gated — T1),
   *not* the send_reply interrupt (which can't fire on a normal turn — B2). On
   decline, the record is dropped.
3. Only on approval does the =Provisioner= enqueue the import. This makes "an
   untrusted input caused a multi-hour disk-filling docker import" *unreachable by
   construction* — a chat message or an inbound text can at most produce a proposal
   you must still approve. (HITL mechanism resolved in B2: a dedicated proposal
   record, one HITL shape, no hot-path interrupt refactor.)

** Regions registry — the unambiguous source of truth
A dedicated =regions.json= in =$TRAVEL_INFRA_DIR=, with *=assist/geo/registry.py=
as the SOLE reader+writer* (the bash scripts write none — B1/C-registry resolve
the earlier self-contradiction; the Provisioner writes =importing=→=ready=/=failed=
via =registry.py=). Thinned record (only what a reader consumes): =slug=, =state
(ready|importing|failed)=, =has_transit=, =display_name=, =bbox=, =last_used_at=
(U3), =completion_delivered= (C1). Dropped as derivable/unread: =geofabrik_url=,
=osm_file=, =transit_source=, =job_log=. The base NorCal region is seeded =ready= /
=has_transit:true=.

Why a dedicated file, not derived from =config.yml= + Nominatim: =config.yml=
carries no bbox / display name / transit flag / date / import-state, and the geo
page + trigger + delete path would each re-derive it. The ethos wants the "is this
region loaded" question to have *one unambiguous answer* — a registry. Consistency
is bounded by making the scripts the sole writers and flipping =state:ready= only
after a validated import (the validate-before-swap discipline the refresh script
already uses). All reads happen off the event loop (=run_in_threadpool=).

** Background-job architecture (event-loop-safe by construction)
Web/agent only *enqueue*; a *thin* =Provisioner= (an executor, NOT a =Scheduler=
clone — see the cross-lens shift; no poll/due/tick/health-gate/dedup) runs the
heavy work in a *subprocess*; on success it invokes the injected completion
callback.
1. *Enqueue (on-loop-safe)*: on approval, =Provisioner.submit(op, slug,
   origin_tid=None)= (=op ∈ \{add, remove, transit\}=; =origin_tid= only for an
   agent-proposed add) writes =state:importing= via =registry.py= and does a
   non-blocking executor submit. No lock, no subprocess, no sleep on the loop.
2. *Execute (off-loop)*: a module-level =ThreadPoolExecutor(max_workers=1)= (one
   import at a time — disk-bound, Nominatim can't overlap itself; this plus the
   shared flock + the =state:importing= pre-write is the serialization, so no
   separate in-flight-dedup set). The worker runs =subprocess.run(["scripts/
   add-region.sh", slug])= (or =remove-region.sh= / =add-transit.sh=) — a bounded
   child that BLOCKS to completion (T5). *Nothing heavy touches the loop, the
   THREAD_QUEUE, or the LLM slot.*
3. *Status*: coarse registry states (=importing= → =ready= / =failed=) + a per-job
   log; no percent (imports give no clean progress). =/geo= polls the registry like
   =/thread/{tid}/status=.
4. *Tell the agent when done* (no automatic re-run — PR #194): on child exit 0,
   dispatch =_scheduled_dispatch(origin_tid, "<completion message>", tz)= +
   =_mark_urgent= — a new human-style message on the originating thread stating
   that the <region> download finished. The travel =SKILL.md= directs the agent's
   next step: usually, use the newly loaded geo to satisfy the user's original
   intent (the thread history carries that intent — the message does NOT replay
   the old prompt). The chat turn ended long ago, so this is a fresh turn —
   exactly the scheduled-prompt model. On exit≠0 → =state:failed= + a "download
   failed" notice (no blind retry). Per D4, if the LLM is busy/down at completion
   the dispatch is held + retried until it's free.

Why in-process Provisioner-runs-a-subprocess over =systemd-run= / cron: it reuses
the proven Scheduler + script shapes and the completion-dispatch seam is already
wired — one moving part. Its one weakness (a web restart mid-import orphans the job) is handled
by a startup *reconcile* (mirror =Scheduler.reconcile=): any =importing= entry with
no live job → =failed=; validate-before-swap means nothing half-built is ever served.

Event-loop lens (Phase-2 test): hold the provisioning lock in another thread, assert
=POST /geo/add= still returns promptly.

** Trigger detection (per D1 — user-driven for v1)
On a "couldn't find a place" result the agent does NOT silently fail and does NOT
guess a slug. Guided by =SKILL.md=, it calls =list_regions()= to state coverage,
then passes the place *as the user said it* to =find_regions(query)= (B1) — code
resolves name→candidate slug(s), so the model never synthesizes a Geofabrik id —
and *proposes* the smallest covering candidate's download (polygon preview + size +
degradation warning), which you approve (HITL). A query that geocodes to no catalog
bbox ⇒ likely a typo ⇒ no proposal (A3). The auto-detect path (proactively naming
the region without asking) is a deferred D1 refinement; the proposal → approval →
import chain stays identical.

** Provisioning scripts (Engine)
=scripts/add-region.sh <slug>= mirrors =refresh-travel-data.sh= (validate-before-
swap, argv-not-shell, atomic renames) and takes the *shared* lock —
=$TRAVEL_INFRA_DIR/.travel-data.lock=, the SAME file =refresh-travel-data.sh=,
=remove-region.sh=, and =add-transit.sh= take (B3 — the refresh script is changed
off its current =.refresh.lock= to this shared path in the same PR, else the
rebuilds don't exclude):
1. *Validate slug against the catalog allowlist* (the security seam). Charset
   =[a-z0-9/-]= (index ids can nest, e.g. =us/washington=; no leading/trailing
   =/=, no =..=); slug must be an id in the pinned index snapshot; the download
   URL comes from the index entry, never the caller. On-disk names flatten =/=
   to =-= (=us-washington.osm.pbf=) so a slug never forms a path.
2. *Download* the extract → validate PBF (size floor AND ceiling + =OSMHeader=,
   the refresh script's checks).
3. *MOTIS (cheap)*: drop =<flattened-slug>.osm.pbf= into =input/=, append a dataset to
   =config.yml=, =motis import= in-place, restart on success (=reimport_motis=).
4. *Nominatim (heavy, destructive)*: re-merge all region PBFs (osmium) or pass the
   multi-PBF path, then full rebuild into a fresh volume (extend
   =reimport_nominatim=). Degrades geocoding platform-wide while it runs (D3).
5. *Transit (optional)*: only if the catalog defines a feed for the slug.
6. *Registry*: write bbox/size/date/=has_transit=, flip =state:ready= — atomically,
   last.
=scripts/remove-region.sh <slug>= is symmetric: refuse the base region, drop the
PBF + config entry, re-merge remaining, MOTIS reimport + Nominatim rebuild, update
the registry.

** Transit as a separate opt-in per-region layer
A region records =has_transit= + =transit_source=. A fresh region is
=has_transit:false=. Transit exists only where the *transit overlay* (a separate
hand-curated file, C3) configures a feed for that region (operator id + URL/token
pattern, like 511 =RG=) — there is no generic nationwide GTFS. Opt-in via a
*dedicated* =scripts/add-transit.sh <slug>= (C4 — a cheap MOTIS-only reimport, no
OSM download, no Nominatim rebuild; NOT a =--with-transit= re-entry into the heavy
path) reachable from a =/geo/{slug}/transit= button, which fetches the configured
GTFS, adds a MOTIS GTFS dataset, MOTIS reimport, flips =has_transit:true=. Guidance
(U4): if a feed IS configured but transit is off, the agent *offers to add it*
(its own HITL action, mirroring the download offer); only if *no* feed is
configured does it state "transit isn't available for <region> (driving, walking,
biking are)" — the data is already honest (=_plan_transit= returns =None= →
"unavailable"); =has_transit= in tool output (A2) makes the region-naming checkable.

*Future direction — agent-driven transit download (Pierre, 2026-07-10; deferred,
to research during Copilot idle windows).* v1's transit overlay is *hand-curated*
because there is no worldwide GTFS index. Pierre wants to graduate this: an
*agent-driven* flow that (1) *researches* the transit-data options for a geo (where
its feed comes from — regional/per-operator feeds, aggregators, transitland/mobility
DBs) and (2) runs a *well-defined transform framework* to reconcile a heterogeneous
feed into the GTFS shape MOTIS ingests. Open seam question: whether this lives in
=assist= or hooks into *emacsos* (which embeds assist's agent via =AgentSpec=) —
weigh value/cost + the right seam, not yet decided. *Design the v1 overlay file +
=add-transit.sh= as the slot this future path plugs into* (the transform's output is
a feed the overlay references; the research/discovery is what the agent adds). This
is transit's distinct sub-problem: base download is bounded by Geofabrik's index,
transit needs *discovery + transformation* instead of a fixed catalog.

** Geo management page
A new submodule =manage/web/geo.py= (the schedules.py/evals.py registration
pattern). Routes:
- =GET /geo= — list regions from the registry, each with a *bbox map preview* (bbox
  → encoded polyline → an existing =path:= map block), =state=, size, date,
  =has_transit=, a delete button, and an "add transit" button when a feed is
  configured and transit is off.
- =GET /geo/add= — the catalog picker: a *searchable* list over the pinned
  Geofabrik-index snapshot (D2), each region with a bbox map preview and the
  download size the weekly refresh cached into the snapshot (no live fetch on
  the request path).
- =POST /geo/add= — enqueue (write =importing= + =Provisioner.submit=); 303
  redirect. *Never* runs the import inline.
- =POST /geo/{slug}/delete= — enqueue eviction; base region undeletable (guard);
  UI confirm.
- =POST /geo/{slug}/transit= — enqueue add-transit.
- A small status fragment polls =importing= → =ready= (like
  =/thread/{tid}/status=), so a heavy import is never on the loop.
Map preview reuses the existing =path:= renderer — no new render type, no new
security surface (the null-origin sandbox already contains it).

** Agent tool surface + guidance
Two new tools, both thread-scoped like =notify=, both on the *normal* web tool set
only (NOT the SMS-triage set):
- =list_regions()= — read-only; returns =ready= regions + =has_transit=. Called on
  a place miss, on "what areas do you cover," and before saying transit is
  unavailable. Deterministic, cheap, no import.
- =request_region_download(slug)= — validates =slug= against the catalog allowlist,
  records a *pending proposal* (HITL) with the map preview and the *code-computed
  download size* (HTTP =HEAD=, per D-fixed); the import fires only on your
  approval. *The agent's only path to an import* — the slug is allowlisted, so
  untrusted input never reaches a free-form URL/shell.
Small model → checkable structure over prose (=CLAUDE.md=: "the instruction's shape
matters more than its content"). =SKILL.md= gains a "Regions" section with checkable
steps: on a miss call =list_regions()= + name coverage + ask; propose a download
only for a catalog region; after a route in a =has_transit:false= region, name that
transit is unavailable there. Alignment-check: examples cover the *shape* ("do you
cover Seattle?", "download San Diego") not eval prompts verbatim; the eval suite
probes cases the wording doesn't telegraph.

* Threat model / attack surface (the Phase-2 security spec)
Untrusted inputs: a user chat message, an agent-filled =slug= arg, a =POST
/geo/add= body. Sinks: the provisioning subprocess (docker, curl, osmium, rm).
Containment by construction:
1. *Slug → allowlist, always* (tool + route). Charset =[a-z0-9/-]= with no
   leading/trailing =/= and no =..= (index ids nest, e.g. =us/washington=);
   slug must be an id in the pinned index snapshot; the download URL is the
   index entry's, never caller-supplied; on-disk names flatten =/= to =-= so a
   slug never forms a path; slug passed as argv, never shell-interpolated.
   Untrusted value never reaches the fetch URL, a filesystem path, or a shell.
2. *HITL gate*: even a valid slug only yields a *proposal*; the import needs your
   approval — so an inbound text can't trigger a multi-hour import / disk fill.
3. *Disk exhaustion*: cap total loaded regions + total bytes; validate download size
   floor AND ceiling (the index includes continent-scale extracts, so the ceiling —
   checked against the =HEAD= size before approval AND enforced at download — is
   what keeps them unloadable); one import at a time.
4. *Delete the wrong data*: slug allowlist + registry lookup; base region
   undeletable; the script removes only registry-owned files under =input/= — no
   path from input to an arbitrary =rm=.
5. *Secrets*: the 511 (and any future) token stays in the token file, read via
   =sed=, never argv/logs (the refresh-script pattern).
6. *Map preview*: registry/agent-authored but rendered through the existing
   null-origin sandboxed iframe — already contained.
7. *New endpoints* inherit the app's existing auth posture (localhost/PWA); =/geo/*=
   mutating routes are POST-only + enqueue-only.

* Risks & edge cases
- *Nominatim rebuild degrades the whole geocoder* while any region is added/removed
  — falls back to MOTIS for all regions until done. Message the user; accept (D3).
  Biggest user-visible wart.
- *Originating thread deleted before import finishes* → the completion-message
  dispatch no-ops on a missing thread (guard).
- *Web restart mid-import* → startup reconcile marks stuck =importing= → =failed=.
- *Two requests for the same region* → per-slug in-flight dedup.
- =config.yml= *concurrent edit* (weekly refresh cron vs add-region) → both take the
  same flock.
- *MOTIS RAM growth as regions accumulate* → cap region count; document.
- *Model over-proposing downloads on typos* → guidance gates on you asserting the
  place is real / naming a region; evals include typo cases that must NOT propose a
  download.
- *Bbox missing for a region* → the catalog carries it; else =osmium fileinfo=.
- *Failed partial import* → validate-before-swap + =state:failed=; MOTIS
  in-place-then-restart never leaves routing down.
