* Parity-target successor contract and reviewed result

The successor asks one smaller question:

#+begin_quote
Can trusted Python run stock Pi as a service-secret-free, network-contained, disposable
runner cgroup, forward at most one exact request, and make cancellation or authority
death end in bounded recursive cleanup before fresh work starts?
#+end_quote

The exercised boundary is intentionally asymmetric.  Python builds the pinned
lockfile release, creates the one-run socket and session inode, validates Pi's closed
provider envelope, owns the fixed instrumented upstream, and assembles evidence.
Bubblewrap gives Node private user, PID, mount, and network namespaces; a read-only
runtime; empty workspace and agent directories; a three-variable environment; no
active tools or ambient resources; no authority-environment canary; and no direct
host/model route.  The Pi model profile uses the fixed non-secret loopback token
=local= because the stock provider requires an API-key-shaped value.  It is not an
external provider credential and grants no authority outside this one runner.
Node and every descendant start atomically in a delegated child cgroup.  Python and
systemd retain the only cgroup kill authorities.

The first stream peer must be namespace PID 2 in that exact runner cgroup.  This
checks the launch topology, not immutable executable identity: the untrusted process
can transfer the stream or replace itself with =execve=.  The stream is therefore the
cgroup's capability.  Every possible recipient is already inside the same no-secret,
no-network, recursively killed boundary.  Python's closed request validation and
one-shot upstream gate constrain what the whole runner cgroup can do.

The trusted authority also verifies that the admitted peer's network and mount namespace inodes
differ from its own, the private network namespace has no IPv4 route, a real
invocation-local host canary is absent beneath the peer's root, and both soft and hard
core-file limits are zero.  The outer transient service independently has
=LimitCORE=0=.  These kernel observations, not a runner-provided Boolean, establish
the containment portion of the gate.

The one-run bridge accepts one provider connection.  During cancellation, stock Pi
0.83 made one additional connection after the first stream was aborted even though
both agent and provider retry settings were disabled.  The bridge rejected that
connection locally with a fixed 409.  It did not forward a second control frame or
open a second upstream request.  The report binds =connections=2=,
=rejected=1=, =requests=1=, and =upstream_requests=1= for cancellation; success and
fresh admission each bind one connection and zero rejection.  P2 must retain this
one-shot gate and recheck the behavior against the real provider.

The seven scenarios prove only this boundary:

1. one stock-SDK request has the owned system canary, one user message, exact nested
   provider options, no tools or extra privileged fields, one streamed result, and
   one persisted completed assistant message;
2. a hook invariant failure self-SIGKILLs even after its control channel is closed;
3. the same failure self-SIGKILLs after Node's send path reports backpressure;
4. =cgroup.kill= terminates Node plus a =setsid= descendant that ignores =TERM= and
   retains the sole FIFO writer;
5. cancellation closes the first Pi client, makes the in-process upstream terminal,
   rejects the extra Pi connection, and completes recursive cleanup;
6. a fresh release-bound runner, socket, session, and upstream request succeeds only
   after scenario 5's service is empty; and
7. killing Python while the first upstream and a hostile descendant are active lets
   stock systemd =KillMode=control-group= empty the service without accepting a dead
   authority's report.  The trusted authority supplies only a bounded pre-death
   readiness frame; the outer process alone assembles the terminal result from its
   pidfd, FIFO, service exit, and cgroup observations.

Every Python and Node protocol operation has an absolute bound inside a 30-second
systemd backstop.  Normal scenario success is emitted only after the runner cgroup is
empty, the admitted-peer and Bubblewrap pidfds are terminal, Bubblewrap is reaped, the control
connection and session/FIFO descriptors are closed, and the runner child cgroup is
removed.  The outer process then waits for the Python pidfd and requires the bound
service =cgroup.events= certificate before beginning another scenario.  The session
has a 2 MiB =RLIMIT_FSIZE= and exact evidence-size check.  The final report uses a
complete-write/fsync/rename sequence and emits =STOP= with partial results on any
caught build, containment, or scenario failure.  Failure of the report filesystem
itself cannot truthfully promise a report and remains a process error.

The current developer command is =experiments/pi-runtime-p0/run-p0=.  It performs
one deterministic local-provider invocation, fetching only lock-pinned packages into
a fresh npm cache when needed.  It prints the final report path after completion and exits zero
only for status =GO=.  A caught build, scenario, source-drift, or cleanup failure
prints a =STOP= report path and exits nonzero.  P0 has no live-Qwen continuation.

P0 still makes no claim about Qwen, tools, skills, hot reload, retained sessions,
fair global model admission, production Docker tool execution, the web UI, emacsos,
or the phone.  Those remain later gates.  A reviewed =GO= authorizes only P1's
harness-authoring and eval-copy experiment.

** Security scope: parity plus a stronger new boundary

P0 targets parity with the overall Deep Agents trust model, not blanket superiority.
The host account, Python authority, installed Node/compiler toolchain, package
installation step, systemd user manager, kernel, and Bubblewrap are trusted.  This
matches the current product's trust in its Python interpreter, installed dependency
set, host service manager, and container runtime.  The package lock and exact Node
version are pinned, package lifecycle scripts are disabled, the build environment is
closed and canaried, and the copied runtime is manifest-hashed and mounted read-only.
A second build sandbox would protect against a compromised trusted toolchain and is deliberately
outside this parity P0.

The newly introduced Pi runner and every process it creates are untrusted.  That
boundary is intentionally stronger and more controllable than an in-process library:
it receives no service secret, external provider credential, host network, host
workspace, ambient Pi resources, or cgroup authority; its request is admitted only
through the private exact-cgroup stream after provider-envelope checks; the authority can
kill its entire descendant cgroup.  P2 must preserve these properties when it replaces
the fixture gateway with the real globally fair provider gateway.  Product-level
authorization, tool sandboxing, session recovery, and web/phone exposure remain P2
and later threat surfaces, not claims of this disposable P0.

The runner reports readiness and its later connection counts, but no
security-gating settings census.  Pi construction is pinned in the source/build
identity; the exact provider request and final session are its external conformance
observations.  Security decisions come from the authority's kernel observations, exact
provider-bound request, one accepted control request, one instrumented upstream
request, final session inode, and empty cgroups.  A compromised runner can lie about
its readiness or counts, but cannot use them to acquire another provider admission
or host capability.

It is a vertical-slice proof, not a partial product implementation.  Every asserted
property must occur in the same exercised path.  A helper used only by its own unit
test is not evidence.

** The one path

#+begin_example
bounded outer test orchestrator/report assembler
  -> one transient user service/cgroup per scenario
    -> Python request authority + in-process gateway/upstream
      -> Bubblewrap
        -> pinned Node + stock Pi SDK/provider
          -> loopback HTTP transport bridge
            -> one-run Unix connection back to Python
#+end_example

The runner has a private network namespace and cannot reach llama.cpp or public
egress directly.  The gateway is its only provider path.  The bridge first registers
the exact Node peer incarnation without receiving a lease.  Only after stock Pi has
serialized one bounded loopback HTTP request does the bridge send its exact raw bytes
to Python.  Python independently validates the complete closed envelope, serializes
the one canonical body it will forward, then atomically issues and consumes one
lease bound to those canonical forwarded bytes before opening the fixed upstream.
The separately retained received-byte digest is parser evidence, never
authorization.

Python accepts only valid UTF-8 with a closed header set and a bounded JSON shape.
It rejects duplicate object keys, excessive depth or member count, out-of-range
numbers, ambiguous encodings, and every unknown field.  Validation and forwarding
use the same parsed representation, serialized once into canonical JSON; Python
records both received and forwarded bytes.  The upstream is an instrumented
HTTP/SSE server inside the Python authority, not
llama.cpp.  The authority owns its numeric address and port; accepts only the exact
method and relative path; uses no DNS, proxy, redirect, or content decoding; bounds
headers, request body, SSE chunk, total response, token count, and duration; and
makes backpressure cancellation-aware.  No destination field comes from a runner
frame.  The gateway stores no conversation, tool, session, approval, or fairness
state.

This P0 makes no live-model claim and does not use the shared =llm= resource.  P2
must put every provider client behind exclusive admission, bind real server
generation identity, and pass the complete Qwen provider matrix before P3.  Existing
Deep Agents, emacsos, and other host clients remain unchanged during P0.

** One request authority per scenario, no proof doubles

The Python process inside a scenario owns its only application lifecycle state
machine.  Workers may perform bounded I/O but submit observations to one serialized transition function;
they never decide admission, quarantine, cleanup, or release.  The closed states are
=STARTING=, =READY=, =REQUEST_BOUND=, =UPSTREAM_ACTIVE=, =CANCELLING=,
=TERMINAL=, =CLEANING=, and =CLEAN=.  =GO= or =STOP= is an outcome orthogonal
to those cleanup phases, never a terminal lifecycle state.  Every event carries the
runner incarnation and request sequence.  Stale events are rejected, and terminal versus
cancel, deadline versus terminal, disconnect during cancellation, and runner death
each have one deterministic winner.  Exactly one cleanup certificate may be issued.

The authority launches pinned Bubblewrap with a private inherited
=--json-status-fd=.  Bubblewrap remains namespace PID 1 and Node is namespace PID 2;
making Node PID 1 prevents its required self-directed =SIGKILL= from behaving like an
ordinary process signal.  The authority retains Bubblewrap's init pidfd.
It does not use =--die-with-parent=; otherwise authority death would not prove the
systemd backstop.  Before accepting a connection, it reads one bounded closed JSON
status object from that FD, obtains Bubblewrap's outer namespace-init PID, and opens
its pidfd.  The first connection supplies Node's exact outer PID through
=SO_PEERCRED=; the authority requires a different live PID in the expected runner
cgroup, opens its pidfd after =accept=, and nonblockingly proves both the original
Bubblewrap init and Node incarnations remain alive.  A terminal pidfd fixes =STOP=,
so numeric PID reuse cannot authorize a descendant.  The private inherited status
FD plus kernel peer credentials, not runner protocol data, anchor provenance.  UID, pathname
secrecy, descendant status, and cgroup membership alone are not peer authority.  An
unauthorized first connection fixes the outcome to =STOP=, can never acquire a
lease, and still enters ordinary =CLEANING=.  After the accepted peer connects, the
listener is closed and unlinked immediately.

Before the child can execute, a minimal pinned launcher calls =clone3= with
=CLONE_INTO_CGROUP= and the authority's pre-opened runner-cgroup FD.  The clone child
=exec=s Bubblewrap; the launcher reports that PID over its private bounded FD and
then does nothing except =waitpid= it.  The original
=CLONE_PARENT|CLONE_INTO_CGROUP= proposal was invalid because =clone3= rejects
=CLONE_PARENT= with a nonzero exit signal.  Keeping the 43-line launcher as Python's
direct child makes reaping explicit without adding cleanup policy or moving the
Bubblewrap child after creation.  This places Bubblewrap, Node, and every descendant
atomically in one runner-only cgroup nested below the scenario service.  The sandbox receives no
cgroup filesystem mount, cgroup namespace escape, or migration FD.  Node's PID-1
signal semantics are never trusted for cleanup: after a bounded =TERM= sent through
Node's pidfd and a bounded grace, the authority writes =1= once to the runner
cgroup's =cgroup.kill=.

The scenario authority may declare its application cleanup complete only after all
of these are true:

1. the exact instrumented upstream request is terminal, including after
   cancellation;
2. gateway admission is closed and the one-run connection is closed;
3. =TERM= has been sent to the exact Node pidfd, followed when needed by atomic
   =cgroup.kill=, and the runner-cgroup =cgroup.events= reports =populated 0=;
4. the Node and Bubblewrap-init pidfds are readable and the direct launcher has
   reaped Bubblewrap;
5. every accepted socket, pipe, listener, pidfd, and bounded drainer is closed or
   joined.

Because the upstream is owned in-process, authority death cannot leave an external
model generation.  Each scenario runs in a fresh transient systemd user service
with =Type=exec=, =ExitType=main=, =KillMode=control-group=, =SendSIGKILL=yes=,
=Restart=no=, bounded =TimeoutStopSec= and =RuntimeMaxSec=, =OOMPolicy=stop=, a
2 GiB =MemoryMax=, and =Delegate=yes= for the authority-owned runner child cgroup.
The proposed 1 GiB limit killed the hostile two-Node fixture at the boundary.  The
candidate requested 2 GiB, but its report failed to record the effective limit or a
bound peak measurement; this is part of the rejected evidence rather than a retained
capacity claim.
Only Python receives the delegated hierarchy; the sandbox sees no cgroup control or
migration interface.  The report records the effective properties and unit
=InvocationID= rather than trusting requested values.  When the Python main process
exits, systemd, not another application process, owns final recursive whole-service
termination, including the delegated runner child cgroup.

The bounded outer test orchestrator creates exactly one scenario service at a time,
supplies the invocation and candidate identities, waits for the service to become
inactive, verifies the exact-invocation cgroup-empty certificate defined below, and
only then starts the next scenario.  It may start or stop the whole unit and perform the
prescribed authority-death fault injection, but it cannot connect to the one-run
socket, issue a provider lease, signal a runner or descendant individually, or
choose an application transition.  It is the cross-scenario sequencer and final
report assembler, not a second live request authority.  Startup refuses a populated
stale P0 unit.

Before fault injection, the outer orchestrator binds the expected unit
=InvocationID=, opens a pidfd for its known =MainPID=, and opens the exact
=cgroup.events= FD so systemd pathname removal cannot erase the observation point.
It then SIGKILLs that Python main process while its upstream and runner are active.
The transient service must kill every remaining member and the outer orchestrator
must observe the unit inactive, the retained descriptors at EOF, and exactly one
cgroup-empty certificate: either the bound =cgroup.events= FD reports =populated 0=
before removal, or the bound FD returns =ENODEV= after the exact unit path disappears.
With no runner-visible migration interface, removal is the kernel certificate that
the cgroup became empty; =ENODEV= is not treated as a generic I/O success.  No
success claim from the dead authority is accepted.  If those stock
systemd properties do not provide this construction, or if it needs a custom cleanup
supervisor, P0 is =STOP=.

There is no separate =ProviderAdmission= model, persistent holder ledger,
process-group fallback, caller-supplied release PID, real-model quarantine, or model
restart manager.  Every launch, accept, frame read/write, upstream operation,
cancellation, cgroup transition, drainer join, and file lock has one monotonic
operation deadline.  Product work has an absolute work deadline whose expiry fixes
the result to =STOP= and enters =CANCELLING=/=CLEANING=.  Cleanup then has its own
absolute bounded fence deadline, and the outer unit stop has a separate bounded
deadline backed by =TimeoutStopSec=.  Failure of either cleanup bound remains =STOP=
and prevents the next scenario; it never grants ownership.  Every protocol also has
total frame, byte, and token budgets.

** Exact scenarios

One invocation builds one fresh candidate and runs these scenarios sequentially:

1. *Deterministic success.*  The real contained Pi SDK and stock
   =openai-completions= provider send one tool-free prompt through the real gateway
   to an instrumented fixed fake upstream.  The gateway captures the raw body and
   proves the complete provider envelope contains exactly the owned system canary,
   one user message, no additional privileged message, and no tool schemas.  Pi
   uses =noTools: "all"= plus every ambient-resource disable switch, parses the
   streamed response, and persists one completed assistant message.  The rejected
   candidate's =noTools: "builtin"= qualification applies only when P2 later proves
   dynamic disclosure.
2. *Fail-stop hook.*  The same contained construction injects a
   =before_provider_request= invariant failure.  The required bootstrap =halt=
   attempts one sanitized fixed-size nonblocking terminal frame and unconditionally
   self-SIGKILLs in a =finally=-equivalent path.  Closed and backpressured control
   connections cannot prevent death.  The gateway, not the runner, observes zero raw
   requests and zero leases, and the ordinary cleanup certificate completes.  A
   throwing halt is forbidden.
3. *Hostile descendant teardown.*  The runner creates a descendant that ignores
   =TERM=, calls =setsid=, and retains the sole remaining write half of one audited
   pipe; Node also ignores =TERM= for this fixture.  Before teardown, the
   authority/observer retains only the read half and closes every local writer.
   Immediately before the kill write, the Node pidfd must be nonterminal, the runner
   cgroup populated, and the read half not at EOF.  Forced teardown then writes
   atomic =cgroup.kill= without enumerating descendants and proves the Node pidfd
   terminal, the cgroup =populated 0=, and the read half at EOF.  Thus namespace-PID-1
   exit cannot make the cgroup proof vacuous.  The Node pidfd proves Node death;
   Python waits for its direct minimal launcher to reap Bubblewrap, while systemd
   owns any descendant that survives Python.
4. *Deterministic cancellation.*  The instrumented upstream acknowledges that the
   exact request is active, then emits an endless valid stream within per-frame
   deadlines.  The driver asks public Pi to abort; bridge disconnect and upstream
   terminal race through the serialized state machine.  Admission remains closed
   until the exact in-process request is terminal and the cleanup certificate is
   complete.  A failed cancellation stops immediately.
5. *Fresh admission after cancellation.*  Only after scenario 4 is =CLEAN=, a fresh
   runner incarnation, listener, Unix connection, lazily issued lease, request
   sequence, and session inode make one final short request.  It receives its own raw
   request/response evidence and cleanup certificate and proves no state from the
   cancelled runner was reused.
6. *Authority death.*  While the instrumented upstream and a hostile runner
   descendant are active, the test SIGKILLs the Python authority.  The transient
   service must kill every member without Python assistance; the outer orchestrator
   records the main-process pidfd terminal, unit inactive, the exact cgroup-empty
   certificate (=populated 0= or bound post-removal =ENODEV=), EOF on every read half
   whose sole remote writer the hostile descendant retained, and the effective
   unit-property census.  No report from the dead authority is accepted.

** Fresh candidate and self-contained evidence

Narrow P0 does not implement a release registry or reuse a content-addressed
directory.  It builds one fresh private candidate manifest and consumes it in the
same invocation.  Before any runner exists, each scenario copies the
descriptor-resolved source into a private mount-namespace tmpfs, verifies the copied
tree against the expected manifest, remounts it read-only, drops mount capability,
and gives the runner only that mount.  No process that retains a writable candidate
FD survives into execution.  The source and private copy are resolved no-follow and
beneath; the source manifest is recomputed after the final scenario and must still
match its build-time value.  This closes mutation by an invocation process rather
than relying on before/after pathname hashes.  An already-compromised unrelated
same-UID host process is outside P0's threat model; product release isolation and a
dedicated runtime identity remain P2 gates.
Product-grade retained release promotion, registry concurrency, rollback, and hot
reload remain P2 gates.

The build still pins Pi, Node, npm, TypeScript, and the lockfile; disables lifecycle
scripts; uses verified absolute tool binaries and a closed environment; requires the
independently reviewed lock digest and integrity for every non-link registry package;
and plants its no-secret canary before dependency processing.  The pinned
Node/npm/compiler and copied ELF closure have reviewed absolute-path hashes inside
that envelope.  The rejected lock's integrity-less nested Pi entries must be removed
or independently closed before implementation.  Failure to make that small build
deterministic is a STOP, not a reason to add a package manager or privileged build
service.

The outer orchestrator validates invocation-bound fragments and writes the final
report.  A living scenario authority may write only its own bounded fragment to the
outer-owned evidence channel; Node and descendants cannot access that channel.  The
outer process accepts no external =--live-report=, and scenario 6 success comes only
from its direct systemd, pidfd, cgroup, and FD observations.  One report binds:

- a source manifest covering every relevant tracked, untracked, generated,
  configuration, schema, and test input with modes and symlink targets while
  excluding prior artifacts, plus its digest;
- the build-time and final source manifests plus every scenario's verified private
  read-only copy identity;
- exact Pi/Node/npm versions and dependency-lock digest;
- kernel version, cgroup mode, and exact systemd, Bubblewrap, and =prlimit=
  identities plus each scenario's effective unit properties;
- complete provider profile and complete provider-bound request/schema digest;
- each received-body digest, canonical forwarded request and lease digest, response
  or cancellation, and upstream observation captured by Python rather than accepted

- each scenario's unique raw-evidence digest; and
- one application-cleanup fragment and outer unit-empty certificate for every
  normally controlled scenario, plus the outer authority-death certificate for

The report is =GO= only when every required scenario is present exactly once and
passes in that invocation.  The final report is written atomically only after every
scenario unit is inactive, every exact-invocation cgroup has its empty/removal
certificate, the final source manifest matches, and every required certificate is

** Simplicity and decision gate

The revised experiment has exactly three process roles: one bounded outer test
orchestrator/report assembler, one transient Python request authority with an
in-process gateway and instrumented upstream per scenario, and one contained
Node/Pi runner.  Systemd and Bubblewrap are existing OS launch/containment
mechanisms, not another application state machine.  The role rule constrains
ownership and processes, not the number of source modules.

It may not add a daemon, database, persistent queue, generic RPC framework, real
model client, restart manager, release registry, custom agent loop, checkpoint
scheduler, or second application lifecycle authority.  Delete the rejected proof
doubles and broad matrix rather than adapting them.

The 1,500-line gate covers every hand-authored file under
=experiments/pi-runtime-p0= after the rejected implementation is deleted, including
source, tests, shell, package/configuration JSON, schemas, and =.gitignore=.  Only
=package-lock.json= and ignored generated/artifact directories are excluded.  The
report records the sorted existing-file manifest and the total computed by
=line_count()= from =read_bytes().splitlines()=.  Deleted tracked paths are ignored.

The result must be materially smaller than the rejected 4,494-line harness and at
most 1,500 lines.  Crossing the limit is =STOP= unless Pierre explicitly changes the
experiment's question before implementation.

=GO= means only that Pi's smallest deterministic execution slice is feasible and
simple enough to authorize P1.  It does not qualify Qwen, authorize P2, or create a
usable Pi thread.  =STOP= means the required request/cancellation/teardown boundary
is already too costly or cannot be implemented through public Pi behavior; revisit
the migration rather than weakening the boundary.
