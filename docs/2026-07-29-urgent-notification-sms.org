#+TITLE: Urgent notification SMS
#+DATE: <2026-07-29>
#+STATUS: IMPLEMENTED (2026-07-29, PR #221) — deployed for testing

* Goal

When the web-only =notify= tool flags the current thread urgent, it also sends the
agent-provided notification message by SMS to the owner's configured recipient.  The
SMS ends with a link to that thread.  It is an immediate send, not a HITL proposal.
The durable urgent marker and in-app urgent pill continue to update even when SMS is
not configured or delivery fails.

* As-built baseline

=assist/events/notify.py= has one =reason= argument, marks the thread through an
injected callback, and returns a rendered confirmation.  It is registered only in the
normal web tool profile; the untrusted inbound-SMS triage profile has only the
HITL-gated =send_reply= tool.  =assist/events/reply.py= already performs the
authenticated host-to-phone =POST /outbound/sms= request.

The relevant roadmap item is =Notifications / Notify/urgent evals + firm up the
guidance on WHEN to flag urgent=.  This change will add its requested natural urgent
and routine behavioral coverage, tighten the tool guidance around the required
message, and close the item in the same PR.

* Boundaries and risks

- *Trust boundary:* the tool remains absent from inbound-SMS triage by construction.
  The normal trusted agent may send a notification directly because Pierre explicitly
  requested no HITL.  The recipient, base URL, endpoint, and shared secret never come
  from the agent's arguments.
- *Untrusted message text:* the agent can include content it has read.  That is the
  requested notification content, but it cannot choose a recipient or endpoint.  The
  transcript escapes it; the SMS payload intentionally preserves it as text.
- *Delivery:* an uncertain request is never retried, preventing duplicate SMS.  The
  marker is written before network I/O, so an outage cannot make the thread look
  non-urgent.
- *Link correctness:* no notification is sent unless the configured link base exists;
  that guarantees every sent urgent SMS ends with a usable configured-thread link.
- *Liveness:* the tool body runs in the synchronous web background worker, not an
  async route handler.  Its bounded network request therefore cannot block the
  single-worker asyncio loop.

* Design-review decisions

The simplicity, agentic-fit, intention, UX, interface, threat-model, and event-loop
lenses found no architectural change required.  The reviews sharpened two intentional
trade-offs:

- Direct sending means that content the trusted normal agent has read can influence the
  SMS wording.  This is accepted because Pierre explicitly requested no HITL.  The tool
  remains absent from untrusted SMS-triage turns, and that content still cannot choose
  recipient, endpoint, shared secret, or link base.
- The shipped change deliberately omitted per-event deduplication and rate
  limiting so each trusted =notify= call produced one message.  This decision is
  superseded by the product policy approved on 2026-08-03, which requires at most
  one notification per event and a bounded rate.  Reconciliation remains open;
  the current implementation must not be described as compliant with that newer
  contract.

The threat-model reviewer additionally required redirect refusal on the shared request;
that is included in step 1 and will be unit-pinned.
