#+title: Persistent skill tool schemas

* Decision

Normal Assist compositions keep a skill's compact native tool schemas after
that skill is loaded. The activation survives later user turns and framework
compaction, but is cleared whenever the mounted skill catalog or a retained
tool schema changes. Inbound SMS triage keeps its unchanged legacy skill
loader and prompt.

This is the T2 treatment from the preceding experiment. It is now the only
production behavior. There is no runtime treatment selector, summary parser,
or replay of synthetic messages.

* Model-visible lifecycle

1. A matching skill first loads by itself. Its ToolMessage contains the full
   SKILL.md file and the full OpenAI-style contracts for its newly available
   tools.
2. Later requests receive the same tools as compact native schemas. The
   compact form keeps names, parameter shapes, and required fields while
   removing explanatory prose that is already present in the original skill
   result.
3. A normal compaction can remove that result from message history. The native
   compact schemas remain callable. No full skill body, full contract, old
   load call, or synthetic ToolMessage is reintroduced.
4. A catalog or schema change clears activation with an overwrite. A legacy
   checkpoint without activation also exposes nothing until a new load.

The loader fails closed when a declared tool lacks the actual provider
definition needed to create its contract. The request filter, after-model
guard, and tool-execution guard all use the same allowed-tool state.

* Prior experiment evidence

Each condition used a fresh thread, workspace, and schedule store. The natural
conversation was:

1. "Remind me every day at 7 AM to take my vitamins."
2. "Pause that reminder for now."

The harness forced compaction immediately before the second turn, rejected
network access, and stubbed research. It required the persisted reminder to
be paused and recorded the post-compaction request.

| condition | N | passed | continuation outcome |
|-----------+---+--------+----------------------|
| control reset | 3 | 3 | reload schedule, then pause |
| T1 full retained schemas | 3 | 3 | direct pause |
| T2 compact retained schemas | 3 | 3 | direct pause |
| T3a summary-selected schemas | 3 | 3 | reload, because the ordinary summary retained only =create_schedule= |
| T3b guided-summary selection | 3 | 3 | direct pause, but retained five of six schedule tools |

T2 was selected because it retains a compact native schema without depending
on summary wording or retaining an unnecessarily broad full schema description.
The complete experimental conditions and outcomes remain recorded here and in
the experiment branch. The production acceptance behavior requires the intended
pause outcome and compact request boundary; it permits a reload when compaction
removed the operating guidance.

* Permanent evals

- =test_later_turn_uses_a_different_tool_from_the_retained_skill= creates a
  reminder, then naturally asks to pause it. It requires the initial schedule
  load and create call, then requires =pause_schedule= with no second load.
- =test_different_skill_tool_after_forced_compaction= uses the same natural
  conversation but forces a real-model summary between turns. It requires the
  intended schedule to be paused and verifies the first post-compaction request
  contains =pause_schedule= but neither the initial load result nor its full
  tool-contract block. Reloading operating guidance is permitted.
- The existing referential modify and named-delete cases now require direct
  use after a previous schedule turn. The compacted delete case also proves
  that the persisted target, not the similar morning reminder, is changed.
- Middleware tests cover full first-load evidence, compact retained schemas,
  durable checkpointer reuse, catalog/schema invalidation, hidden-call guards,
  unavailable provider definitions, and legacy triage compatibility.

The PR description records the matched current-main baseline and the staged
candidate N=3, N=5, and N=10 results for the production panel.

* Design review record

The design review considered simplicity, Deep Agents framework fit, and
security. It accepted catalog-bound native schema retention and rejected:

- Replaying historical ToolMessages or full contracts after compaction. That
  duplicates context and is not a native callable-tool definition.
- Summary-text parsing or a custom summary prompt. These make tool
  availability depend on lossy prose and add a second product mechanism.
- A runtime experiment-profile selector. The selected treatment is one
  production contract, and all prior treatment data is preserved above.

The security boundary is fail closed: no provider definition means no load,
catalog drift removes prior activation, and a hallucinated hidden call cannot
reach execution through either synchronous or asynchronous middleware paths.
