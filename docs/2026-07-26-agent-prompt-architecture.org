* Problem

Assist has accumulated behavior by adding instructions to an always-loaded
general prompt.  This makes a local fix cheap but imposes its cost and possible
conflicts on every later turn, including turns where the instruction cannot
apply.  It also obscures the actual contract because the model sees the fully
assembled request, not any one Jinja template.

The eval suite has the corresponding test problem.  Deterministic assertions are
excellent for exact state, security boundaries, and explicit capability probes,
but many natural acceptance evals assert an implementation trace: exact agent
names, tool order, TODO wording, regex vocabulary, or a particular orchestration
shape.  Those checks can reject a useful outcome and encourage prompt wording
that mirrors the fixture.  Replacing all checks with an unqualified model judge
would be worse: it could reward fluent claims contradicted by the workspace,
share the tested model's blind spots, or change verdicts between identical runs.

The architecture therefore needs three separations:

1. stable bootstrap instructions versus conditional skill-loaded workflows;
2. always-visible kernel tools versus skill-disclosed workflow tools;
3. deterministic contracts versus calibrated semantic outcome judgment.

* Goals

1. Make the fully rendered model request auditable for every production and eval
   profile, including middleware-injected guidance and tool descriptions.
2. Reduce the main and delegate system prompt to a bootstrap kernel: what the
   agent must know in order to choose the next source of instructions safely.
3. Keep local context gathering preloaded unless a controlled experiment proves
   an equally reliable smaller boundary.
4. Keep memory /contents/ available as context while progressively disclosing
   the conditional procedure for deciding and performing memory writes.
5. Put optional workflows such as complex task breakdown and external research
   behind skills whose descriptions provide the routing trigger.
6. Keep only the Deep Agents built-ins needed to inspect, plan, and modify work,
   plus =load_skill=, in the always-visible tool kernel.  Reveal other tools only
   after a matching skill is successfully loaded.
7. Use the portable Agent Skills =allowed-tools= field for declarations across
   Assist, domain-repository, and embedder skill sources.
8. Give every specialist a concise role contract aligned with its actual tools,
   filesystem, return shape, caller, and trust boundary.
9. Qualify a semantic outcome judge against fixed human labels before its
   verdict can gate a natural eval.
10. Change one instruction boundary per implementation phase so every result
   teaches us whether that boundary works for Qwen3.6-27B.
11. Manage the lifecycle of the skill catalog itself: temporarily omit a
    recently loaded skill description while its body is still salient, then
    restore discoverability before the model can no longer reliably reuse or
    reload that workflow.

* Non-goals

- Do not implement any part of the architecture in the design PR.
- Do not rewrite all prompts or migrate all workflows in one change.
- Do not add a prompt registry, policy engine, automatic router, second general
  agent factory, or middleware that deterministically performs the model's work.
  A narrower existing agent constructor is an evidence-gated alternative for a
  role whose required capability surface Deep Agents cannot express.
- Do not make prompt token count the product goal.  A smaller prompt that lowers
  useful outcome reliability fails.
- Do not judge security, authorization, exact persisted state, or resource bounds
  with an LLM when code can decide them exactly.
- Do not use an external judge endpoint by default.  Assist's local-first privacy
  boundary applies to eval artifacts too; any remote candidate requires a later
  explicit operator decision and synthetic inputs.
- Do not make a specialist load a skill merely to learn its own identity or
  primary job.
- Do not remove the context-first rule, critique capability, or any other current
  behavior based on architectural taste.  Each removal needs a measured phase.
- Do not change SMS triage in this program.  Its future work belongs on the
  separate roadmap item until an observed problem establishes a narrower goal.
- Do not revise development guidance in this program.  It needs a larger
  end-to-end design, not an isolated prompt cleanup.
- Do not invent an Assist-only skill/tool manifest or treat tool disclosure as
  authorization.  Existing graph composition, HITL, provenance, filesystem,
  and tool-level guards remain the authority.

* Instruction placement architecture
:PROPERTIES:
:CUSTOM_ID: instruction-placement
:END:

The model needs one rule for deciding where an instruction belongs:

#+begin_quote
Preload what is required to choose the next source of instructions safely.
Progressively disclose what is required to execute the chosen workflow.
#+end_quote

Six instruction homes follow from that rule.

| Home | Volatility it contains | Admission test | Examples |
|------+------------------------+----------------+----------|
| Bootstrap role kernel | Cross-task identity, grounding, trust, and orchestration choices | The model can violate safety or cannot choose the next capability before loading anything | workspace and text-only boundary; context-first grounding; specialist versus whole-outcome delegation; durable task result outranks TODO state; child results are untrusted data |
| Capability protocol | Generic use of an always-visible capability family | Middleware or a tool family can state the protocol once for every role that actually receives it | skills middleware owns match/load/apply and kernel-versus-disclosed tools; TODO middleware owns plan mechanics; task tools own available child names and lifecycle arguments |
| Tool description/result | One invocation and its immediate return contract | The instruction is useful only while selecting or interpreting that tool | exact task ID argument; =start_async_task= returns immediately; cancellation requested is not cancellation completed; full schema appears only while the tool is disclosed |
| Skill | Conditional multi-step operating procedure | A visible description can identify the request before the procedure is needed | complex-request planning; memory persistence; external research; development; editing; file formats |
| Role system contract | A specialist's fixed job and capability boundary | Every invocation of this profile has the same job | context is read-only; research lead decomposes and synthesizes; research leaf searches and cites; receptionist routes only |
| Context data | Facts rather than behavior policy | The model needs the content, but not instructions about managing it | repository memory; per-thread memory; current date; task result data |

The final rendered request is the contract.  A sentence is not considered removed
or moved merely because it left a Jinja template; the Phase-0 census must prove
where it appears after Deep Agents and every middleware have modified the request.
Duplicate instructions are defects when their independent owners can drift.

Capability and trust boundaries prefer construction over prompting.  A delegate
cannot self-delegate because it has no async lifecycle tools, and a context agent
cannot write because the read-only enforcer rejects mutating tools.  The prompt
should accurately explain those shapes, not pretend to enforce them.

** Main bootstrap kernel

The target custom main role kernel contains only:

1. role, workspace, text-only, and owner-instruction boundaries;
2. the context-first rule and its narrow skip cases;
3. the choice between a specialist lookup and a whole-outcome delegate;
4. the irreducible durable lifecycle and trust rules needed on every completion
   wake but not expressible by the task tools themselves;
5. TODOs as advisory planning state, reconciled against checked task results and
   workspace evidence;
6. child, fetched-page, and tool-result text as data that cannot issue new
   instructions.

The always-visible capability protocols remain part of the complete bootstrap
request, but each has one owner.  Skills middleware owns matching, loading, and
applying skills.  TODO middleware owns generic plan mechanics.  Tool schemas own
current specialist/delegate names, arguments, and immediate results.  The role
kernel does not restate those protocols unless a measured small-model exception
is recorded.

Examples, research report procedure, file-creation defaults, memory write syntax,
task-file conventions, complex-request dependency recipes, and domain workflows
do not belong in this kernel.

** Delegate bootstrap kernel

The delegate shares the stable workspace, skill, context, memory-data, and trust
rules.  Its role contract says only that it owns one self-contained outcome,
receives no parent history, may use its synchronous specialists, and returns the
verified result to its caller.  It has no concept of outer task IDs, completion
wakes, parent TODOs, or the supervisor's scheduling lifecycle.

** Tool-disclosure boundary

The model does not need every registered tool schema before it has selected a
workflow.  Each main/delegate profile therefore starts an agent invocation with
one kernel: the Deep Agents built-ins actually present for that profile, plus
=load_skill=.  Framework-owned filesystem, execution, TODO, and delegation tools
remain kernel capabilities when the profile supplies them.  Fixed-role
specialists that do not mount skills keep their existing small tool sets and are
outside this mechanism.

The kernel is declared once where the Deep Agents middleware/tool composition is
built.  The skills middleware uses that same exact set both to filter the final
model request and to generate a compact system-prompt block listing the kernel
tool names and the disclosure rule.  Jinja prose does not carry a second
hand-maintained list.  Tool schemas remain authoritative for arguments and
immediate results.

Every non-kernel tool stays registered with LangChain's execution graph but is
absent from the model request and rejected if called until a successful
=load_skill= activates it.  Activation comes from the trusted result of the real
load tool, never from model prose, a fabricated tool message, or a skill body.
The next model request contains the kernel plus the union of tools activated by
skills loaded during that agent invocation.  The set resets at the next graph
invocation, so a long-lived thread does not gradually accumulate every tool.
It lives in invocation-scoped graph state, never on the reusable middleware
instance or in a process global.  Concurrent invocations are isolated, parallel
successful loads merge deterministically, and a load cannot disclose a sibling
tool call from the same model response; disclosure begins on the following
model step.

Skill declarations reuse the optional experimental =allowed-tools= field from
the [[https://agentskills.io/specification#allowed-tools-field][Agent Skills specification]].  The upstream Deep Agents parser already
loads this field as a space-separated string.  Assist initially accepts only
tokens that exactly match model-visible tool names; command-pattern syntax is
not interpreted.  Kernel tools need not be repeated in =allowed-tools=.  A skill
body can continue to describe portable actions in neutral prose; the frontmatter
is the machine-readable disclosure declaration.

The startup skill list remains name plus description only.  It does not reveal
the =allowed-tools= values early.  After a successful load, the tool result names
the newly available tools and their schemas appear on the following model call.
This keeps both the procedure and its non-kernel tool surface progressively
disclosed.

P2b deliberately leaves the startup catalog's cross-turn lifetime unchanged.
P2c separately experiments with omitting a recently loaded skill's catalog
entry while its trusted load result remains salient.  Separating the phases
keeps tool visibility failures distinguishable from catalog-lifecycle failures.

All skill sources obey the same resolution contract:

- bundled shared and main-only Assist skills declare their non-kernel tools in
  their own =SKILL.md=;
- an in-repo =.claude/skills/= skill can disclose only a tool already registered
  in the current composed agent;
- an embedder skill from =AgentSpec.skill_sources= can disclose a custom tool
  supplied through that same composition's =AgentSpec.tools=;
- a name collision uses only the winning skill's body and =allowed-tools= under
  the existing last-source-wins resolution.  Declarations are never unioned
  across shadowed skills.

A declaration cannot create a tool, bypass HITL, relax URL provenance, change
filesystem access, or expand a role's registered graph.  Unknown or unavailable
names disclose nothing and produce a bounded skill-loading diagnostic.  Because
=allowed-tools= is experimental and other Agent Skills implementations may
ignore it, Assist documents and tests its exact-name interpretation without
claiming it is portable authorization.

** Memory boundary

Memory data and memory management are different volatilities.  Existing memory
contents remain preloaded because they affect the very first interpretation of a
request.  The instructions for recognizing a durable fact, choosing a memory
target, and persisting it become a conditional memory skill.  A short visible
skill description must match explicit requests ("remember this") and natural
persistent facts or forward-looking preferences.  The skill body owns write
mechanics and exclusions such as credentials and transient state.

This boundary must be re-evaluated against the merged per-thread-memory design.
The resulting memory skill must fit the final repository/thread targets and
promotion rule, but this program preserves the existing access model rather
than introducing a new authorization boundary.

** Research boundary

The main/delegate only need to recognize that current or external facts require
the research specialist and then load a research workflow.  The skill owns
selection, brief formation, prior-result reuse, generic grounding,
partial-result handling, and unavailable-search handling.  It is return-shape
neutral.  Each bound tool/subagent description owns its caller's concrete return
shape and immediate consumption contract: direct findings for async main, a
report path for synchronous delegate/legacy main.

Research specialists keep system contracts because research is their entire
role.  The lead owns decomposition, report synthesis, and its private report
workspace.  The leaf owns search/fetch discipline, source fidelity, stopping,
and a findings-with-sources return.  Report critique and fact checking remain
inside the research topology unless an eval demonstrates another caller with a
real need.

** Other specialists

The context, report-critique, fact-check, receptionist, thread-description, and
capture profiles each receive a direct capability audit.  No shared prose is
assumed correct for them.  Development guidance stays unchanged: its coupled
main/delegate/skill workflow needs a separate end-to-end redesign if evidence
ever establishes the need.

The capture profile must stop treating "add text to the main system prompt" as
the default remedy.  Its output should identify the observed outcome failure and
the narrowest candidate instruction home without prescribing that the main
prompt grow.

* Hybrid eval architecture
:PROPERTIES:
:CUSTOM_ID: hybrid-evals
:END:

Every eval declares which evidence decides its result.

** Deterministic gates

Keep deterministic validation for:

- exact file/state mutations and preservation of existing content;
- capability absence, authorization, trust provenance, and other security
  boundaries;
- task lifecycle facts such as checked terminal status, no blocked dependent,
  exact task ownership, and cancellation state;
- resource bounds, tool-call counts that exist specifically to prevent a
  runaway, valid schemas, and process liveness;
- explicit capability probes whose purpose is to prove that a named tool,
  skill, or agent path can work.

A deterministic gate can fail a case before semantic judging.  The judge cannot
waive it.

** Natural outcome observation

A natural acceptance case gives the judge only evidence a user could care about:

1. the natural prompt sequence;
2. relevant initial fixtures;
3. final files or a normalized workspace diff;
4. the final user-visible response;
5. a minimal terminal event ledger when the requested outcome includes task
   state that is not represented in files;
6. a case-specific list of requested outcomes and forbidden outcomes written in
   user language.

The judge does not see expected tool names, prompt variant names, desired TODO
shape, or routing traces.  Agent output, fetched content, and file content are
delimited as untrusted evidence.  The judge is still fallible and may follow text
inside them; paired qualification cases test that failure directly.  When an
agent claims success but the final artifact disagrees, the artifact is
authoritative.

Each case declares the artifact paths needed to decide its outcomes.  The
observation builder resolves them inside the synthetic eval workspace, rejects
symlinks or traversal outside it, caps file count, per-file bytes, total bytes,
and final response/event-ledger size, and records every omission.  An outcome
whose required evidence exceeded a bound is unjudgeable and cannot pass.  Broad
repository diffs, environment data, credentials, and real thread artifacts are
never collected merely because they are available locally.

The judge returns structured data:

- =pass=, =partial=, or =fail=;
- one verdict per requested outcome, with evidence from the observation;
- any forbidden outcome or contradiction;
- a short overall rationale;
- confidence only as diagnostic metadata, never as a way to turn a failure into
  a pass.

Strict schema validation requires exactly one verdict for every requested
outcome ID, no unknown or duplicate IDs, valid enum values, and evidence
references limited to observation IDs actually supplied.  One normal eval gets
one bounded judge call with explicit wall-clock and output-token limits.  Invalid
schema, timeout, overflow, missing outcome, or required-evidence truncation is
=judge_error= and therefore not a pass; it is never retried until a favorable
verdict appears.

Natural-suite reporting preserves all three labels.  A phase's acceptance gate
uses full passes; partial outcomes are reported separately rather than rounded
up or hidden with =xfail=.

** Judge qualification

The first candidate is the existing local model in a dedicated, temperature-zero
judge prompt with thinking enabled if the endpoint supports it.  This is the
simplest private candidate, not an assumption that a model can grade itself.

Calibration uses thirty labelled observations split before judge-prompt work:

1. an eighteen-case development set, balanced six each across pass, partial, and
   fail, used to write and revise the general rubric;
2. a twelve-case blind qualification set, balanced four each across the three
   labels, whose inputs and labels remain hidden until the judge prompt, model,
   thresholds, and development work are frozen.

Both sets mix objectively inspectable synthetic artifacts with natural outcomes
from current eval shapes.  Each qualification label includes at least one
natural outcome, and the set includes fluent false claims, missing files,
incomplete multi-part outcomes, benign paraphrases, and prompt-injection text
inside artifacts.  Pierre labels natural observations without seeing candidate
verdicts.  A corpus custodian who does not tune the judge keeps the qualification
set blind.

The candidate runs three times over the twelve-case qualification set.  It
qualifies only if all of these are true:

- the majority verdict exactly matches at least 10 of 12 labels;
- zero human/objective =fail= cases receive a majority =pass=;
- no majority verdict differs from its label by two grades;
- at least 30 of 36 individual verdicts match their case's majority, with no
  individual =fail= to =pass= flip;
- the report includes the three-label confusion matrix and every rationale cites
  evidence actually present in the supplied observation;
- paired observations with identical semantics but benign versus
  instruction-shaped artifact, file, or final-response text have the same
  =pass= versus =not pass= verdict on every individual run;
- every fluent false-success and forged-evidence-identifier case is a non-pass on
  every individual run.

The model and prompt version are recorded with every verdict.  Failure
disqualifies the candidate and reveals the qualification set for diagnosis.  A
changed model may use the same development set, but a changed prompt or rubric
requires a newly frozen balanced twelve-case blind set; do not tune on a revealed
qualification set and call the rerun qualification.

The three qualification runs measure stability; they are not a production
voting scheme.  Normal eval gating uses its single bounded verdict.  Aggregate
qualification accuracy never waives the paired-injection, false-success,
forged-evidence, or two-grade-flip hard gates on any individual run.

If the current local model does not qualify, the judge remains diagnostic and
cannot gate evals.  The next alternatives, in order, are:

1. retain outcome-specific deterministic validators plus human review for
   natural cases;
2. qualify a stronger separately configured local judge endpoint;
3. with explicit operator approval and synthetic-only observations, qualify a
   remote judge.

Do not mask a weak judge with majority voting, repeated sampling until the
desired verdict appears, or per-eval prompt exceptions.

* Experiment protocol for every implementation phase
:PROPERTIES:
:CUSTOM_ID: experiment-protocol
:END:

1. Rebase the phase branch on the then-current =main= and regenerate the prompt
   census.  Record all active profile and memory surfaces.
2. Pre-register the phase hypothesis, one controlled instruction move, targeted
   cohort, adjacent regression cohort, pass/fail gate, expected learning, and
   alternatives in this state document before changing behavior.
3. Baseline the exact cohorts on unchanged =main= at N=10, unless an unchanged
   model, prompt, fixture, and validator already have a recorded N=10 result.
   Preserve transcripts, rendered prompt fingerprints, deterministic results,
   semantic verdicts when a judge is qualified, and token counts.  Until then,
   retain current outcome validators and record human adjudication only for a
   case they cannot decide.
4. Make only the declared instruction-home change.  Do not combine wording
   tuning with a tool/capability change.
5. Run targeted and adjacent cohorts at N=3 as an early diagnostic.  A
   deterministic regression stops the phase immediately; sampling difference
   from the N=10 natural baseline is evidence to investigate, not yet a gate.
6. Run the full design and code review loops.  Re-run affected cohorts at N=5
   after review, then N=10 for stability.  The N=10 candidate must meet the
   unchanged-main N=10 full-pass count and the natural floor.  Any shortfall
   fails the phase, consistent with the repo eval contract.
7. Keep a residual-closing rider only if it clears the residual completely;
   otherwise revert to the simpler candidate.
8. Record what the result taught, including failed hypotheses, before starting
   the next phase.  Later phases consume evidence, not the original assumption.

The acceptance floor for a natural cohort is the greater of its recorded
baseline and 70% full passes.  This floor does not permit trading away an
existing reliable behavior merely because the aggregate suite remains above
70%.  Deterministic and security gates remain 100%.

** Eval execution and liveness

Offline execution does not isolate the shared =--parallel 1= llama.cpp slot from
production web traffic.  That contention has not been a material problem in
practice, so this program does not add production admission, maintenance state,
or a provider gate preemptively.  Real-model commands still acquire the
workspace =llm= resource to serialize cooperating development sessions and run
during an ordinarily quiet period.  Production is not covered by that lock.
Any observed overlap that can affect a verdict is an infrastructure failure:
preserve it, exclude it from behavioral percentages, and rerun the same sample
only after the provider is idle.  Reopen P0b only when a reproduced overlap
invalidates a comparison, repeatedly wedges the provider beyond the existing
timeout, or causes material production failure.

The judge is one bare, non-streaming model call with no Assist agent, tools,
middleware, checkpointer, sandbox, =THREAD_QUEUE=, or subagents.  A subject run
fully closes its response stream and atomically persists its observation before
the judge starts.  Subject and judge calls serialize on the hardware reservation
even if configured through different local endpoint URLs.

Before launch, the phase state document records case count times repetitions,
expected subject turns/subagents and judge calls, measured one-case p50/p90
duration, projected GPU minutes, per-case deadline, block partition, and total
expected wall time.  A case deadline is shorter than the one-hour block cap.  If
the projection does not fit bounded blocks, narrow or partition the
pre-registered cohort before launch.

The existing =scripts/run-evals.sh= owns the useful eval hygiene: home-backed
scratch, its single-writer lock, exact-mount orphan cleanup, per-node logs/JUnit,
and GNU =timeout --kill-after=.  It is not yet a cohort selector or outer block
supervisor.  Before P1's first model call, its reviewed plan must make the
smallest test-side adaptation that reuses that preamble while accepting
explicit node IDs, bounding the whole selected block below one hour, and
returning the aggregate failure status.  The operator then invokes that focused
entry point through =tools/agentic resource run llm=.  A later phase reuses the

## Memory

The block above between `<agent_memory>` tags is the contents of the
file `/workspace/AGENTS.md`.  It is what you remember about the user across
conversations.  Treat it as authoritative for facts about the user's

### How to save a memory

Persistent memory lives in `/workspace/AGENTS.md`.  To save a new fact,
append a one-sentence prose line to that file using your existing
filesystem tools.

If `<agent_memory>` above shows `(No memory loaded)` the file is
empty — use `write_file`:

  write_file(file_path="/workspace/AGENTS.md", content="<your sentence>\n")

Otherwise the file already has content — use `edit_file` to append.
The current contents shown between the `<agent_memory>` tags above
are your `old_string`; the same content followed by your new sentence
is your `new_string`:

  edit_file(
    file_path="/workspace/AGENTS.md",
    old_string="<everything currently between the agent_memory tags>",
    new_string="<that same content>\n<your new sentence>",
  )

Constraints on the saved sentence:
- Plain prose, one sentence per fact.
- No `<agent_memory>` tags.  No markdown headings (`#`, `##`).  No YAML.
- Never save credentials, API keys, or passwords.

### When to save

- The user explicitly says "remember", "save", "commit to memory", or
  similar.
- The user states a persistent fact about themselves (identity,
  possessions, preferences, environment) NOT already in
  `<agent_memory>` above.
- The user gives forward-looking feedback or a behavioral rule.
  Examples: "in the future ...", "from now on ...", "always ...",
  "never ...", "I prefer X over Y", "I'd rather see ...", "don't do X
  again", "next time ...".  Save the rule even when the user did not
  say "remember".

### When NOT to save

- Transient state ("I'm running late", "I'm on my phone").
- One-off task requests ("find me a recipe", "what's 25 * 4?").
- Acknowledgments and small talk ("thanks", "sounds good").
- Credentials, API keys, passwords — never echo or save these.

### Pre-action check (MANDATORY — apply on every turn)

Before any work tool (`task`, `write_todos`, `read_file`, etc.), scan
the user's latest message for a fact about the user, an explicit
save request, or forward-looking feedback that is NOT already in
`<agent_memory>` above.  If you find one, your save MUST happen this
turn: `write_file(file_path="/workspace/AGENTS.md", ...)` if `<agent_memory>`
above shows `(No memory loaded)`, otherwise
`edit_file(file_path="/workspace/AGENTS.md", ...)`.  The save can run before
or after `load_skill`, but both must precede every other tool call.

The save is required even when the user's whole turn is just a
preference or rule ("I prefer Python over JavaScript", "I have 3
cats", "in the future, do X"): the correct turn is the save tool
followed by a short prose reply.  A prose-only reply ("Got it, I'll
remember that") is NOT a substitute — the memory is lost.

This is the single most common bug: the model acknowledges the fact
in prose but never persists it.  The check exists to prevent that.

** Hypothesis

** P2b.1: Declare the kernel and validate skill tool names
:PROPERTIES:
:CUSTOM_ID: phase-2b-tools-declare
:END:

*** Value

Tool ownership becomes inspectable before any schema disappears from the model.
Skill authors use a standard field, and a misspelled or stale tool name fails a
deterministic test instead of becoming a behavioral mystery.

*** Hypothesis

The P0 census can classify the actual Deep Agents built-ins as the profile's
kernel and assign every other currently used tool to at least one skill without
adding a runtime registry or changing behavior.

*** Controlled change

Define one construction-time kernel set from the actual Deep Agents built-in
tool instances present for the profile plus =load_skill=.  Pass that set to the
skills middleware; generate the system-prompt kernel list from it.  Do not copy
the names into the main Jinja template.

Add =allowed-tools= to each bundled shared/main-only Assist skill that calls for
a non-kernel tool.  Kernel tools are omitted from the field.  Parse frontmatter
through the same upstream Agent Skills parser used at runtime.  Keep the current
model-visible tool set unchanged in this child.

Add a deterministic repository test that walks every
=assist/skills/*/SKILL.md= and =assist/main_skills/*/SKILL.md=.  For every
=allowed-tools= token it proves:

1. the value is one exact model-visible tool name, not a command pattern;
2. a tool with that name exists in at least one recorded real Assist
   composition;
3. the declaration is non-kernel in that composition; and
4. source precedence leaves the same winning declaration that =load_skill=
   returns.

The test validates declarations, not prose by regex.  Completeness comes from
the P0 tool-owner census and the behavior cohorts; parsing Markdown examples for
tool-like words would create a brittle second skill language.

*** Test and gate

- The full bundled-skill declaration scan is deterministic and 100% green.
- A misspelled, patterned, stale, or kernel-redundant fixture fails with the
  skill path and tool name.
- P0 reports no registered non-kernel tool used by a current workflow without a
  skill owner.  A deliberately shared tool may name multiple owners; the report
  records the reason rather than treating this as accidental duplication.
- The generated kernel block exactly matches the kernel schemas in the final
  request for main, delegate, executable/non-executable backend, and legacy
  compositions.
- Final model-visible tools and all natural outcomes remain byte/behavior
  equivalent to baseline except for the new generated kernel prose.

*** Expected learning and alternative

This child reveals whether “Deep Agents built-in” is a stable construction
boundary or whether the current graph intermixes framework and app tools too
early.  If provenance cannot be recovered without a second registry, stop and
first make the existing composition return its kernel/tool groups explicitly;
do not infer ownership from a hand-maintained list of names.

** P2b.2: Gate Assist-owned tools after skill load
:PROPERTIES:
:CUSTOM_ID: phase-2b-tools-assist
:END:

*** Value

Ordinary turns bind a smaller, more relevant schema set, while a selected
workflow receives its full tools together with its instructions.

*** Hypothesis

Qwen can load the matching skill from name/description with unchanged natural
reliability, then use the newly disclosed tool on the following model call.
Removing unrelated schemas should not add more than the existing one skill-load
round trip and may improve tool selection.

*** Controlled change

Extend the existing small-model skills middleware rather than adding a parallel
router.  All tools remain statically registered with the LangChain tool node.
For the final model request the middleware keeps only kernel tools plus the
=allowed-tools= union of successfully loaded skills.  The same middleware's
tool-call wrapper rejects a hidden non-kernel call, so a hallucinated remembered
name cannot bypass schema filtering.

A successful =load_skill= updates trusted invocation-scoped graph state with
the exact resolved winning skill and returns its body plus the newly available
tool names.  The field and reducer must isolate concurrent graph invocations
and merge parallel successful loads deterministically; mutable middleware
instance state is forbidden.  Failed loads, fabricated messages, model prose,
and shadowed skill bodies update nothing.  Multiple skill loads union their
tools for the current invocation.  =before_agent= resets the active set at every
new graph invocation; the next user/scheduled invocation loads what it needs
again.  Deep Agents lifecycle tools needed to process completion wakes remain
kernel.

The successful tool response also attaches a non-model-visible
=ToolMessage.artifact= with the closed schema =schema=, =requested_name=,
=winner_fingerprint=, and =result_sha256=.  The winner fingerprint covers the
winning name, description, loaded body digest, and declared tool names, but not
its host path; the result digest covers the exact model-visible tool content.
Failure responses carry no success artifact.  This message artifact is the sole
cross-invocation load evidence used by P2c; active tool state itself remains
invocation-scoped.

This child gates tools owned by bundled Assist/main-only skills.  Tools owned
only by domain or embedder skill sources remain explicit baseline-visible
migration exceptions until P2b.3.  The P2b.1 census names those exceptions;
there is no source-specific runtime rule beyond leaving them out of the gated
set.  This isolates whether the small model follows disclosure at all before
external-source semantics enter the experiment.

*** Test and gate

- In a bundled-source composition, before any skill load the final request and
  executable set contain exactly the profile kernel; a direct hidden-tool call
  is rejected deterministically.  A composition with external sources contains
  only that kernel plus the P2b.1-recorded migration exceptions.
- A successful load reveals exactly its declared registered tools on the next
  call.  Unknown, unavailable, failed, and fabricated loads reveal none.
- Two valid loads produce the exact union; a new invocation resets to kernel;
  thread checkpoints never accumulate old disclosure state; concurrent
  invocations on one agent cannot observe each other's loads.
- A model response containing =load_skill= and a hidden sibling call rejects the
  sibling regardless of execution order.  The tool appears only on the next
  model request.
- HITL, URL provenance, read-only enforcement, role omission, and existing tool
  argument/resource guards remain unchanged and pass 100% deterministic tests.
- Baseline/candidate natural cohorts cover travel/directions, specific-site
  reading, scheduling/subscription, whole-outcome delegation, and at least one
  host-effect workflow that retains its existing approval boundary.  Each runs
  N=3 diagnostic, N=5 post-review, and N=10 stability under the shared protocol,
  meeting its unchanged-main baseline and 70% floor.
- Capability cases distinguish “skill not loaded,” “skill loaded but tool not
  disclosed,” “tool disclosed but not selected,” and “tool selected but outcome
  failed.”
- Kernel-only and unrelated journeys add no model round trip.  A scoped journey
  adds at most its existing skill-load round trip and meets the cross-phase
  latency guard.
- The experiment report records initial and peak schema count/token cost plus
  wrong-tool, unavailable-tool, and unnecessary-skill-load rates.  Token
  reduction is evidence, not the pass condition.

*** Expected learning and alternative

The likely failure is skill-selection recall, not dynamic binding.  First tune
the skill description under its natural cohort.  If one tool family still has a
reproduced N=10 regression, retain that family in the kernel as a named measured
exception; do not add an LLM tool router or restore every tool.

*** Value

The tool surface follows the skill regardless of where the skill came from, so

*** Hypothesis

The existing source-order metadata and =AgentSpec= composition are sufficient:

* P2c: Suppress recently loaded skill descriptions until they are useful again
:PROPERTIES:
:CUSTOM_ID: phase-2c-skill-description-lifecycle
:END:

** Value

A skill body that was just loaded already supplies the workflow.  Repeating its
routing description in every following system prompt spends context and can
invite redundant reloads.  Restoring the description later preserves
discoverability when that prior body is no longer reliably available.

** Hypothesis

The model can continue applying or explicitly reloading a recently loaded skill
without seeing the same name/description entry on every near-term turn, provided
the entry returns at a measured recency boundary and immediately after
compaction removes the trusted load evidence.

** Controlled change

Run this only after P2b so tool disclosure and catalog disclosure are measured
independently.  On each model request, derive recently loaded skills from the
trusted, tool-call-paired =load_skill= results still present in that invocation's
visible message history.  A result counts only when its successful
=ToolMessage.artifact= has the exact P2b schema and its winner fingerprint still
matches that thread's resolved catalog snapshot.  Its =result_sha256= must also
match the still-visible =ToolMessage.content=; a summary, truncation, copied
body, or artifact without the original body is not load evidence.  A snapshot
mismatch, compaction, or eviction therefore returns the entry to the catalog.
User prose, model prose, fabricated or malformed tool messages, failed loads,
stale fingerprints, and another thread's history cannot suppress an entry.  Do
not add a process-global timer, middleware-instance set, or second durable skill
registry.

P2c retains Deep Agents' existing session-snapshot contract: skill discovery is
cached in the thread checkpoint, and source additions, removals, or new shadows
do not hot-reload into that thread.  P2c neither weakens nor claims to repair
that independent limitation.  A new thread resolves a fresh snapshot and has no
prior load evidence, so its current winning entries are all discoverable.

Omit a matched skill's name/description from the generated =Available skills=
catalog while one pre-registered candidate gate remains active.  Compare, one
at a time:

1. a fixed number of completed user turns since the successful load;
2. a fixed number of provider-reported input-plus-output tokens since the load;
3. a compaction-aware gate that suppresses only while the trusted load result
   and body remain in the visible history; and
4. only if the single-axis candidates leave a reproduced gap, the smallest
   hybrid of turn/token recency plus the compaction boundary.

The entry returns when the selected threshold expires.  It also returns by
construction when compaction or message eviction removes the trusted successful
load evidence, regardless of counters.  A newly relevant thread with no such
evidence always sees the skill.  The system prompt may carry one compact generic
sentence saying that recently loaded catalog entries can be omitted and may be
reloaded by their previously returned exact name.  Suppression removes only the
exact row from the generated =Available skills= catalog.  Independently owned
prompt guidance, including the surviving =dev= and =complex-request= hooks,
remains byte-equivalent; P2c does not reopen the development-guidance boundary.

P2b's invocation-scoped =allowed-tools= activation still resets at each graph
invocation.  The model can reload an omitted recent skill by the exact name in
its trusted prior tool result because =load_skill= remains in the kernel.  If
natural evals show that description suppression reliably prevents this required
reload, the candidate fails.  Persisting tool activation across turns is not
silently bundled into P2c; it would be a separate experiment with its own
accumulation and revocation contract.

The chosen threshold is one reviewed constant, not a per-skill tuning table.
Turn counts use completed user turns, not provider calls or child wake messages.
The token candidate sums =prompt_tokens + completion_tokens= from the deployed
provider's normalized usage metadata on main-agent responses after the
successful load; it excludes subagent and judge traffic.  This deliberately
measures actual model I/O, including a repeated prefix, rather than estimating
tokens from characters.  The counter advances only from trusted response
metadata retained in the visible thread history.  Missing, malformed, negative,
or non-integral usage fails open by restoring the catalog entry.  Deterministic
tests use fixed usage-metadata fixtures and cover a threshold crossed within a
turn as well as between turns, so they do not depend on an installed tokenizer.
Compaction is observed from the actual visible history boundary rather than
inferred from wall time.

** Test and gate

- Deterministic history tests prove a real successful paired load suppresses
  exactly its winning catalog entry; failed, fabricated, malformed, shadowed,
  snapshot-mismatch, result-digest-mismatch, cross-thread, and parallel loads
  suppress nothing outside their own history.  Checkpoint round trips preserve
  the closed artifact without exposing it in model-bound content.  A new thread
  created after a source add/remove/shadow sees its fresh winning catalog with
  no inherited suppression; mid-session hot reload remains out of scope.
- Boundary tests cover exactly-before/at/after each turn and token threshold,
  multiple independently loaded skills, a re-load that refreshes recency, and
  compaction/eviction that restores the entry on the next model request.
- The final provider-bound =Available skills= catalog contains neither the
  omitted row nor its description.  Unrelated catalog entries, source
  precedence, and independently owned prompt guidance remain byte-equivalent;
  deterministic fixtures cover =dev= and =complex-request= explicitly.
- P2b kernel, schema filtering, execution filtering, same-response disclosure,
  and invocation reset tests remain 100% green.  A recent skill that needs a
  non-kernel tool either reloads successfully by its trusted prior exact name or
  the natural journey fails visibly; hidden tools never become executable from
  catalog suppression alone.
- Natural multi-turn cohorts exercise immediate reuse, an unrelated intervening
  turn, a return near each candidate boundary, a post-compaction return, two
  recently loaded skills, and domain/embedder skills.  Each candidate runs N=3
  diagnostic and N=5 post-review; only the selected policy proceeds to N=10.
- The selected policy may not reduce any full-pass count below unchanged P2b or
  the common 70% floor.  It reports prompt characters/tokens saved, redundant
  =load_skill= calls, required reload success, wrong-skill selection, and missed
  rediscovery separately.  Token reduction is evidence, not the pass condition.

** Expected learning and alternatives

Turn count is the simplest likely policy.  Token recency may better track a
long tool-heavy turn, while the visible-history/compaction boundary avoids a
stale counter after summarization.  The experiment chooses from measured
reliability, not maximum prompt reduction.

If every suppression policy causes a natural regression, leave the catalog
always visible.  If only one skill has a reproduced exception, keep that entry
visible and record it rather than building per-skill lifetimes.  If compaction
does not expose a trustworthy visible-history boundary, restore descriptions
conservatively on any ambiguous history instead of guessing that the body
survived.

* Cross-phase security and integrity

This program adds no production listener, privilege, or host tool.  P0/P1 add
evaluator authority: untrusted agent output could instruct the judge to ignore
the rubric, and a lenient judge could turn a real failure into a reported pass.
P1c adds a mutable household review pad plus Kindle and email delivery.  Review
revision 3 also makes self-extension an aspirational product behavior, creating
future untrusted-code, trial-effect, and promotion-integrity surfaces even
though P1c implements none of them.
Containment is therefore structural:

- deterministic gates run first and cannot be waived by the judge;
- agent artifacts are delimited as data, with paired injection cases treating
  any changed verdict as disqualifying rather than assuming delimiters suffice;
- judge inputs omit secrets and real user/family data;
- default judging remains local;
- model/prompt versions and complete verdict evidence are retained;
- qualification includes prompt-injection artifacts and fluent false-success
  claims;
- failed qualification leaves the judge diagnostic only.
- the completed P1c pilot kept canonical bytes inert until authenticated
  approval, confined untrusted pad content, used immutable per-revision pads,
  and recorded per-channel outcomes without ambiguous retries.  The refined
  operative transport and promotion controls now live only in the canonical
  meta-repository =AGENTS.md=;
- any later self-extension design must run trials without production credentials
  or real effect interfaces, require separate exact approval for an intentional
  live effect, and bind promotion evidence and approval to the exact candidate
  and target scope; content, dependency, resolved security configuration,
  permission, destination, or scope drift invalidates them.  Mandatory-check
  selection, immutable check definitions, runner/toolchain, result evidence, and
  promotion remain in a trusted control plane outside the candidate's
  permissions and are included in that approval record.

For the approved self-extension clause, “hold the change to relevant checks” is
a pass gate: a failed required check blocks promotion.  The exact tested
candidate includes the security-relevant resolved configuration and permissions,
not source bytes alone.  A future implementation must use a production-equivalent
no-effect adapter for mediated boundaries and, only where that cannot validate
the real boundary, a separately approved bounded live trial.  These are
architecture consequences of the approved policy, not post-approval edits to
its canonical bytes.

Prompt movement must not weaken capability-based security.  Trust boundaries,
tool omission, filesystem permissions, URL provenance, HITL, and resource bounds
remain code-enforced and covered by existing deterministic tests.

P2b's schema filtering is paired with execution filtering so a hallucinated
hidden name cannot run merely because LangChain registered it.  This is still
not an authorization boundary: =allowed-tools= selects context from the tools
the profile already owns, while HITL and each tool's existing guards decide
whether a disclosed call may take effect.  In-repo and embedder skills cannot
create tools by naming them, and untrusted skill text cannot fabricate a
successful load-state update.

SMS triage is explicitly outside this program.  Its existing behavior remains
covered by its current tests and can be reconsidered only as separate roadmap
work when an observed problem supplies a concrete goal.

P3 changes instruction placement only: it keeps memory data preloaded and moves
the write decision and procedure into a skill.  It does not alter who can read
or write memory, nor add a new authorization mechanism.

* Program completion gate
:PROPERTIES:
:CUSTOM_ID: final-architecture-gate
:END:

The roadmap umbrella remains open after individual phases ship.  The architecture
is complete only when a final P0 census proves all of the following:

1. every surviving normative instruction maps to exactly one of the six homes;
2. the custom main and delegate role prompts contain only the enumerated role
   kernel, while separately owned capability protocols remain singly owned;
3. every positive capability and return-shape claim matches the final graph;
4. each skills-enabled profile has one exact generated kernel; every registered
   non-kernel tool has a validated skill declaration or a measured kernel
   exception, and only successfully loaded skills disclose/execute their tools;
5. bundled, domain, and embedder skill collisions resolve body and tool
   declarations from the same winner;
6. each remaining always-on procedural exception names the failed experiment and
   reproduced regression that justified it;
7. all deterministic security gates pass and every natural cohort meets its
   unchanged-main N=10 baseline and 70% floor;
8. README and architecture documentation describe the final architecture, while
   product policy, eval descriptions, docstrings, comments, and roadmap remain
   consistent with its approved outcomes and authorization boundaries without
   encoding one internal topology as product intent.

This gate can close with a measured exception.  It cannot close by weakening a
phase threshold, accepting an unexplained duplicate, or rounding a partial judge
verdict up to a pass.
