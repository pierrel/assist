#+TITLE: notify tool + iOS PWA home-screen badge (notifications roadmap v2)
#+DATE: <2026-07-04>
#+STATUS: APPROVED + BUILT (2026-07-05) — Pierre's decisions folded in (see below); implemented in PR #168

* What Pierre asked for
Give the agent a =notify=-style tool to flag URGENT / time-sensitive
responses/events, and drive a **badge on the iOS home-screen (PWA) icon — a badge
ONLY, NO push notification** (memory queued-assist-feature-roadmap.md). Builds on
the just-shipped v1 "new" unread badge (#167): that badge marks *unseen* responses;
=notify= adds a *stronger* "this needs a fast response" signal.

This is the first concrete instance of the "event-triggers" future the
thread-schedules design anticipated: a scheduled/SMS turn can raise a
stronger-than-unseen signal the web app surfaces.

* Two parts — durable core vs best-effort (the volatility split)
The design SEPARATES what's reliably achievable from what iOS gates:
- *PART A — durable core (ships, deterministic, testable):* the =notify= tool +
  an urgent state (mirrors v1's =_UNSEEN=) + an in-app "urgent" pill + a boolean "any urgent?" flag.
- *PART B — best-effort (ships, platform-gated):* the iOS PWA icon badge via
  =navigator.setAppBadge=, on app open/foreground. The CLOSED-app real-time badge
  is DEFERRED (it needs Web Push, which on iOS is inseparable from a user-visible
  notification — i.e. it IS the "push notification" Pierre said no to).
They share ONE seam: a cheap boolean "any urgent?".

* DECISIONS — RESOLVED by Pierre (2026-07-05)
** D1 — Notification permission → ACCEPTABLE, BUILD Part B.
Pierre: "permission prompt is fine … let's build part b." Lighting the iOS icon
badge requires granting the =Notification= permission (the standard prompt), even
though the code NEVER posts a notification (no banner/sound/alert — only the icon
badge). Accepted.
** D2 — the icon badge is a BINARY DOT, NOT a count. Keep the "urgent" pill.
Pierre: "I like the 'urgent' pill but not the count." So the home-screen icon shows
a plain badge DOT (=navigator.setAppBadge()= with NO argument) whenever ANY urgent
thread is unopened, and =clearAppBadge()= when none remain — no number. The in-app
thread-list "urgent" pill stays (per-thread visibility). The Part-A seam is
therefore a BOOLEAN "any urgent?" (=bool(_URGENT)=), not =len(_URGENT)=.
** D3 — clear the THREAD's urgent on open; the ICON dot persists until ALL urgent opened.
Pierre: "On open of the thread that has an urgent notification. The app icon badge
should persist until all urgent threads are opened." So =get_thread= clears that
one thread's urgent (its pill goes away); the icon dot reflects =bool(_URGENT)= — it
stays until EVERY urgent thread has been opened (the set drains to empty), then
clears on the next app open/foreground.

* PART A — the durable core

** A1. Urgent state — a parallel =_URGENT= set (mirrors =_UNSEEN= exactly)
=manage/web/state.py=, after the =_UNSEEN= block (~:342-401). A parallel
=_URGENT: set[str]= + a =urgent_response= marker file — the SAME representation v1
uses and Pierre already blessed (lock-free set = O(1) read path; durable marker =
survives restart, so a scheduled/SMS urgent flag isn't lost to a deploy). Chosen
over reusing =_UNSEEN= (different lifecycle/precedence; overloading one set forces
a flag-in-a-set) and over a generic factory (only two sets ever — YAGNI).
Helpers, each a 1:1 analog of the =_UNSEEN= version, BUT only those with a live
caller (design-review F1 — no callerless clone):
- =_URGENT: set[str] = set()=; =_urgent_path(tid)= → =<thread_dir>/urgent_response=.
- =_mark_urgent(tid)= — =add= + BEST-EFFORT marker write (=try/except OSError: pass=;
  runs in the terminal/tool path off-loop — a marker failure must NEVER flip a good
  turn to error). Verbatim mirror of =_mark_unseen_response=.
- =_clear_urgent(tid)= — =discard= + BARE missing-ok never-raise =os.remove= in
  =try/except OSError= (runs on the loop in =get_thread=; no =_atomic_write=, no
  lock — verbatim mirror of =_clear_unseen_response=, incl. the TOCTOU-safe
  try/remove, not isfile→remove).
- =_has_urgent(tid)= → =tid in _URGENT= (the pill's =elif=); =_any_urgent()= →
  =bool(_URGENT)= (the Part-B seam — a BOOLEAN "any urgent unopened?", NOT a count,
  per D2). Both O(1).
- =load_urgent_cache()= — =clear()=-first rebuild from markers at startup (mirror of
  the fixed =load_unseen_cache=), called in =lifespan= beside =load_unseen_cache()=.
Lifecycle hooks (symmetry): =_evict_caches= += =_URGENT.discard(tid)=; =get_thread=
clears BOTH =_clear_unseen_response= and =_clear_urgent= on open.
*Concurrency:* identical to v1 — GIL-atomic =add=/=discard=/=in=/=len=, no lock,
safe across the on-loop reads/clear and the off-loop =_process_message= mark.

** A2. The =notify= tool — WEB-only, closure-built, trusted-turns-only
NEW =assist/events/notify.py= (beside =reply.py=). WEB-only (touches web state;
core =assist/tools.py= built-ins run in emacsos/CLI which have NO Manager/web-state
— same rationale as schedule/subscription/reply tools).
- Surface: =def notify(reason: str) -> str= — one string arg (the small model gets
  one-arg tools right). Reads =tid= from =get_config()= (=_thread_id()=); if none,
  RETURNS a corrective string (="Couldn't flag this: no active thread."=) — never
  raises, never marks a =None= key (design-review F8, matches every sibling tool's
  =if not tid: return "…"= opener). On success: =_mark_urgent(tid)=, return
  =f"Flagged this thread as urgent: {reason}"=. =reason= is NOT persisted to the
  marker (existence is the whole signal — no PII in the badge); it lives in the
  transcript the user reads.
- Builder: =def notify_tools(mark_urgent) -> list= — a CLOSURE over the
  mark-urgent callback (design-review F9), mirroring =schedule_tools(store)=. This
  AVOIDS the =state=↔=notify= import cycle BY CONSTRUCTION (no in-function import),
  the dominant idiom here.
- *Registration (containment by construction — the security core):* add
  =notify_tools(_mark_urgent)= to =set_web_tools(...)= at =state.py:106= ONLY —
  NEVER to =set_web_triage_tools= (=state.py:107=). A TRIAGE turn (untrusted inbound
  SMS) gets ONLY =_web_triage_tools= (=thread_manager.py:280= = =reply_tools()=), so
  =notify= is simply not in that turn's tool list — an attacker's SMS cannot force a
  badge on Pierre's phone. A test PINS =notify ∉ _web_triage_tools=.

** A3. The urgent pill + the badge seam
=manage/web/threads.py=:
- *Thread-list "urgent" pill* in =render_index= (~:139-180): insert
  =elif _has_urgent(tid):= a red/orange pill BETWEEN the =error= arm and the
  =_has_unseen_response= ("new") arm. Precedence:
  =queued/busy > error > URGENT > new > unmerged= (urgent beats plain "new" — an
  agent-flagged item is more time-sensitive; below error/busy — a running/broken
  thread is actionable now). Mutually-exclusive =elif= → one pill per row. Pin the
  slot (don't append). This pill is the RELIABLE in-app surface (design-review F2) —
  the iOS icon badge is the enhancement; without the pill, =notify= would be a
  near-no-op whenever the PWA is closed.
- *Badge seam* for Part B (D2 — a DOT, not a count): inject
  =<meta name="assist-urgent" content="1">= (or ="0"=) into the index =<head>=
  (~:204), =content= = ="1" if _any_urgent() else "0"=, computed ONCE (not per row),
  O(1). No JSON endpoint (the meta is smaller + one fewer route — design-review F3).

* PART B — iOS PWA icon badge (best-effort, platform-gated)
Honest feasibility (verbatim into the PR):
- ✅ =setAppBadge()= (a DOT)/=clearAppBadge()= from the OPEN/foregrounded page works on
  iOS 16.4+ for a home-screen-installed PWA with Notification permission — no push,
  no service worker. "Set a badge DOT when any urgent, on open/foreground" is
  reliably deliverable (eventually-consistent-on-foreground — which is when the user
  looks at the icon anyway).
- ⛔ DEFERRED: a badge that updates while the app is CLOSED needs a service worker
  woken by Web Push, which on iOS requires a user-visible notification → violates
  "badge only". Not attempted; documented.
** B1. PWA manifest + static assets
NEW dedicated =manage/web/static/= dir (manifest + icon PNGs ONLY — no threads,
config, or secrets). =manifest.webmanifest= (name, short_name, start_url "/",
display standalone, icons 192/512). Served via a =StaticFiles= mount in =app.py=
(the first one — the codebase inlines JS/CSS, but a manifest must be a fetchable URL
and icons are binary). =StaticFiles= reads on the threadpool (off-loop) + rejects
=..= escapes by construction → liveness- and traversal-safe. HTTPS already satisfied
(:5050 mkcert). Verify no apple-touch-icon already ships.
** B2. =<head>= metas (index, ~:204)
=<link rel="manifest">=, =apple-mobile-web-app-capable=,
=apple-mobile-web-app-title=, =<link rel="apple-touch-icon">= (the home-screen
icon), + the A3 assist-urgent meta.
** B3. Permission + page script (static inline =<script>=, like =_GEO_SEND_SCRIPT=)
No server data except the boolean-via-meta (0/1 — no XSS surface). Feature-detect
=('setAppBadge' in navigator)=; request =Notification.requestPermission()= LAZILY on
a user gesture (never unsolicited on load — iOS may auto-deny); on =load= +
=visibilitychange→visible=, read the =assist-urgent= meta and call
=navigator.setAppBadge()= (NO argument → a plain DOT, per D2) when ="1"=, else
=clearAppBadge()=; try/catch → silent no-op on any browser lacking the API
(desktop/older iOS degrade to the in-app pill). The dot persists on the icon at its
last-set value while the app is backgrounded/closed, and re-syncs to =_any_urgent()=
on the next foreground — so it stays until ALL urgent threads are opened (D3).

* Event-loop liveness (single-worker uvicorn — blocker-level) — all CONFIRMED
- Reads on the loop: =_has_urgent=/=_any_urgent()= = GIL-atomic set =in=/=len=, O(1),
  no lock; the =<head>= meta is one =len()= (cheaper than the per-row =_has_unseen=
  the list already does). =_clear_urgent= on the loop = bare missing-ok unlink +
  discard, never-raise.
- The MARK runs OFF-loop (the =notify= tool executes inside =_process_message=, a
  sync BackgroundTask). =StaticFiles= serves on the threadpool. No new lock/blocking.

* Security / containment (by construction)
- =notify= unreachable from the SMS-TRIAGE turn (not in =_web_triage_tools=) — the
  core containment, pinned by a test. HONEST residual (design-review F2, accepted,
  NOT hardened): a SCHEDULED turn (=triage=False=) DOES hold =notify=; if untrusted
  content already steers a trusted turn to self-schedule a "call notify" prompt, it
  could fire — but that turn can already =send_reply=-draft/schedule/subscribe, so
  a badge on Pierre's own phone is not the marginal risk. Scoped, not over-claimed.
- Nuisance: =_URGENT= is set-keyed-by-tid → N calls collapse to one; bounded by
  thread count (same as =_UNSEEN=). No cap needed.
- No leak: the badge is a BARE integer; =reason= isn't persisted; manifest is static
  app metadata. Count is only visible on Pierre's own unlocked device.

* Risks
1. iOS Badging drift (highest) — feature-detect + silent no-op + the in-app pill
   fallback. Best-effort, documented.
2. The Notification-permission prompt (D1) — the sharpest edge vs "no notification";
   Pierre's decision, gates Part B.
3. Precedence / clear-policy (D3) — one-place changes, cheap to re-rank.
4. Import cycle — avoided by construction via the closure builder (F9).
