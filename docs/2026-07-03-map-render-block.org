#+TITLE: Map render block — visualize places + routes on a tiling map
#+DATE: <2026-07-03>
#+STATUS: DESIGN (Phase 1, awaiting Pierre review) — design-review team run, findings folded in

Extends the render skill (=docs/2026-06-28-render-skill.org=) with a new
=type: map=. Origin: the "coffee shops near Fellow Barber" work — showing places
and the routes/distances between them on an actual map, IN ADDITION TO the prose
answer (the map complements the text reply, it does not replace it).

* What Pierre asked for
- A map in the assist WEB chat view.
- EXACTLY ONE map per turn, but that one map carries MULTIPLE things: pins AND
  paths (routes), etc.
- A tiling library, as open/libre as possible.
- Tile source (Pierre's call): OSM public raster tiles for v1; self-host later.

* The contract — INLINE payload (Pierre review)
The agent emits a ```render fenced block =type: map= carrying the map DATA INLINE
(GeoJSON), NOT a workspace file path. Pierre's call: the generated map data should
not live in the (domain) repo. Inline is the v1 default; if a map ever needs to be
a file (very large), the fallback is a =.gitignore='d renders dir, NOT a tracked
workspace file.

This DIVERGES from the render skill's file/pdf "path = workspace file" boundary,
deliberately: file/pdf render the user's REAL documents (a path IS the point); a
map is GENERATED visualization data (ephemeral, not a user file). The security
boundary that matters for a map is CONTAINMENT of agent-authored data
(§Containment) — inline honors that identically to a file, and inline actually
REMOVES the file-traversal/exfil surface (no path, no serve route, no
=_safe_workspace_file=). =_RENDER_DISPATCH= gains ="map": _render_map_block=;
parse stays web-only in =_render_assistant_content=; =_RENDER_BLOCK_RE= NOT
touched (one-map-per-turn is a flag, not a new scan).

*Trade-off (MEASURED — a non-issue):* inline data lives in the assistant MESSAGE,
so it re-enters the LLM context on later turns. But it's TINY: ~250 bytes (pins)
to ~750 bytes (pins + a route) with the compact line format below — measured on a
real scenario (6 coffee-shop pins geocoded + a real 133-point MOTIS walk route).
Pierre's point holds: the place NAMES the model supplies hit the context EITHER
WAY (and they're already in the conversation); only the tool-GENERATED geometry
(coords + polyline) could be kept out of context by writing a file (tool returns
just a filename) — but at ~750 bytes that's not worth a file + repo clutter. So
inline wins; context cost is negligible. The =.gitignore='d-dir file stays the
escape hatch only for an unusually large map. A render-time SIZE CAP bounds a
runaway block.

** Data = a SIMPLE line language (Pierre review), not raw GeoJSON
The block is one line per thing — simple, compact, and it fits the existing
=key: value= block parser:
: type: map
: pin: <lat>,<lon> <label>
: path: <google-encoded-polyline> <label>
Repeated =pin:= / =path:= keys = one map, many things (=_parse_render_block= grows
a small tweak: accumulate repeated =pin=/=path= keys into lists instead of
last-wins). The web layer expands them to Leaflet markers + Leaflet-side
decoded polylines. Chosen over raw inline GeoJSON: MEASURED ~6x smaller on the
real scenario (simple lines 747 B vs GeoJSON 4328 B; pins-only 246 B) — the
google-encoded polyline (a compact string) is what shrinks a path vs a GeoJSON
coordinate array — and it reads plainly, matching "the render block domain
language should be simple".

* The three decisions

** 1. A =map_view= tool provides the DATA — and returns the ready-to-paste block
*Why a tool at all* (Pierre asked: was there an eval showing the model can't emit
mappable JSON? — honest answer: NO, I assumed it; reframing): the load-bearing
reason is NOT JSON-formatting but DATA ACCURACY. The model does not know precise
lat/lon or route geometry; asked to produce them it CONFABULATES — literally the
"1398 Valencia" fabrication we just investigated (the model invented Fellow
Barber's address, 0 sources had it). So coordinates MUST come from geocoding
(Nominatim =_geocode=) and the route polyline from MOTIS (=_decode_polyline=),
never the model's memory — the same "research must not judge distances"
principle. =map_view= supplies that data. This holds regardless of the model's
JSON skill.

*Two sub-questions, EVAL-GATED (Pierre's point — resolve with data, not
assumption):*
(a) Does =map_view= return the WHOLE ready-to-paste block (=type: map= +
=pin:=/=path:= lines, model echoes it verbatim) — the render-skill "structure
beats prose" default — OR can the model reliably COMPOSE the =pin:=/=path:= lines
from tool-provided coords (a lighter design)? UNTESTED.
(b) *Gate before build:* a focal eval — feed the model accurate coords (tool
output) and check it emits a well-formed inline map block (mirror the render
skill's own 3/3 emission gate). PASS → the lighter "model composes" path is
viable; FAIL → =map_view= returns the whole block. Either way the DATA comes from
the tool; the eval only decides who assembles the block.

Ownership: the GENERAL/orchestrator agent (it already holds =travel=/=directions=;
=map_view= registers alongside them at =agent.py:375=), NOT the research
sub-agent — consistent with the just-merged "research must not judge distances"
principle. The map is a general-agent concern.

** 2. Leaflet (BSD-2) + vendored + OSM public raster tiles (v1)
Leaflet over MapLibre for v1: both BSD, but Leaflet is ~a couple files + raster
tiles, no vector-tile pipeline. MapLibre GL JS + vector tiles is the
self-hosted-tiles follow-up (data contract unchanged when we swap). Leaflet
JS/CSS is VENDORED + served same-origin (never a CDN). Tile source:
=https://tile.openstreetmap.org/{z}/{x}/{y}.png= with attribution — Pierre's v1
call; the tile URL is a hard-coded constant (no agent input → no SSRF).

** 3. Containment: a sandboxed iframe + its own CSP (NOT inlined in the chat page)
The two design reviewers split here, and this is the load-bearing decision:
- The existing render embeds are safe by CONTAINMENT — each is an =<iframe>=
  WITHOUT =allow-scripts=, so agent HTML can't execute (threads.py ~1348).
- A map needs JS (Leaflet) over AGENT-AUTHORED data (the geojson labels). The
  *simplicity* reviewer noted the chat page already runs inline dev scripts with
  no CSP, so inlining "fits the posture". The *threat-model* reviewer countered:
  those existing scripts are trusted DEV code; the map is the FIRST place
  UNTRUSTED agent data drives script execution in the app origin — inlining it
  there means a popup-XSS slip is a full-origin (session) compromise.
- *Decision (fix-by-construction + the new adversarial-security lens for a new
  untrusted-data render path):* render the map inside a dedicated
  =<iframe sandbox="allow-scripts allow-popups">= pointed at a new
  =/thread/{tid}/map?path=…= HTML route that carries its OWN CSP
  (=default-src 'none'; script-src 'self' 'nonce-…'; img-src 'self' data:
  https://*.tile.openstreetmap.org; connect-src 'self'; style-src 'self'
  'unsafe-inline'; object-src 'none'; base-uri 'none'=). A popup-XSS is then
  JAILED in the iframe, never the chat origin — preserving the "embeds can't
  touch the app origin" property. The simplicity reviewer's inline-in-chat-page
  alternative is considered-but-rejected: modest extra structure (one route + a
  CSP header) buys real containment for untrusted-data-driven scripts.

* Rendering flow (inline data + sandboxed iframe — no file routes)
1. =_render_map_block= (threads.py) parses the inline =pin:=/=path:= lines from
   the block into a small structured object (=[{lat,lon,label}]= pins +
   =[{polyline,label}]= paths), applies a render-time SIZE/COUNT CAP (oversized →
   code block), and emits a SANDBOXED iframe via =srcdoc= so the data travels WITH
   it: =<iframe sandbox="allow-scripts allow-popups" srcdoc="…">=. NO file I/O
   (the data is in the block, not a file) → no on-loop-read concern. The srcdoc
   HTML contains: a CSP =<meta>=, the parsed pins/paths as a =<script
   type="application/json">= data island (NOT executed; =</= escaped so it can't
   break out), a small init script, and Leaflet.
2. NO =/thread/{tid}/map= or =/map.geojson= routes, NO =_safe_workspace_file= —
   inline data has no path, so the traversal/exfil surface is gone.
3. *Containment via sandbox:* =allow-scripts allow-popups= but NO
   =allow-same-origin= → the iframe is a NULL/opaque origin: it cannot touch the
   parent page's DOM, cookies, or session. A popup-XSS is jailed there. The CSP
   meta is defense-in-depth (=script-src= the asset host + init; =img-src= self +
   data: + =https://*.tile.openstreetmap.org=; =connect-src 'none'=;
   =default-src 'none'=). Leaflet's JS/CSS load as SUBRESOURCES from a same-origin
   asset route (a sandboxed null-origin iframe can still fetch subresources; a
   cached vendored-bytes route, NOT a first-ever =StaticFiles= mount — the
   codebase inlines every asset today) so it isn't re-sent per map.
4. The init: =L.marker= per pin + =L.polyline(decode(path))= per path (a small
   Leaflet-side polyline decoder). Popups bound via a DOM text node
   (=el.textContent = String(label); marker.bindPopup(el)=) — NEVER
   =bindPopup(string)= (Leaflet treats a string as HTML) and NEVER =innerHTML=;
   =fitBounds= to all layers; the OSM =L.tileLayer= (hard-coded https URL +
   attribution). Bad/missing/oversized data → empty map, never a throw.
5. One map per turn: =_render_assistant_content= renders only the FIRST
   =type: map= block (a =map_rendered= flag checked before dispatch); later map
   blocks fall through to code blocks.

* v1 vs follow-up
*v1:* one map/turn; pins AND paths; Leaflet vendored + OSM public tiles; the
=map_view= tool (supplies data; returns the block pending the emission eval);
INLINE data in a sandboxed =srcdoc= iframe + CSP; the render-SKILL extension
(not a new skill); XSS-safe popups; render-time size cap.
- *Paths in v1 (reconciling the simplicity reviewer):* build paths by REUSING the
  route geometry the travel stack already decodes (=_street_narrative= decodes the
  MOTIS polyline then discards it) via a small SHARED helper — NOT a parallel
  geocode+plan+"a|b|mode"-string code path inside =map_view=. Drop per-route
  =mode= (default walk). If sharing the geometry proves fiddly under time
  pressure, the documented fallback is *pins-only v1, paths follow* (pins alone
  still ship a visible map).
*Follow-up (flagged, not built):* self-hosted tile server (tileserver-gl /
OpenMapTiles) — removes the external OSM dependency + the viewer-IP leak, natural
given we self-host Nominatim + MOTIS; MapLibre + vector tiles once those land;
push =render_thread= off the event loop (pre-existing render-doc follow-up — this
design adds no new on-loop I/O).

* Security model (by construction)
- *XSS:* the iframe SANDBOX (=allow-scripts allow-popups=, NO =allow-same-origin=
  → null origin, cannot touch the parent page's DOM/cookies/session) is the
  containment; textContent-only popups + a =label=-only property allowlist are the
  prevention. The inline GeoJSON is fully untrusted (agent-authored) — escaping is
  at the RENDER layer, and even a slip is jailed in the null-origin iframe.
- *Inline-data safety:* the parsed pins/paths go into a =<script
  type="application/json">= data island (not executed), =</= escaped so it can't
  break out into an executable script; the whole =srcdoc= attribute is
  HTML-escaped; labels are text-node only (above). A render-time SIZE/COUNT CAP on
  the block is the binding resource bound (the agent could emit a huge block). NO
  file path → NO traversal/exfil surface at all (an upside of inline vs a file).
- *Event-loop:* =_render_map_block= does NO file I/O (data is in the block); it
  builds a string. =_RENDER_BLOCK_RE= untouched; one-map-per-turn flag.
- *Tiles:* hard-coded keyless https OSM URL (no SSRF, no secret); a keyed provider
  (if ever) proxied server-side, never in page HTML. External tile privacy leak is
  the accepted v1 trade-off; removed by self-hosting.

* Risks
1. Block-emission reliability — mitigated by =map_view= returning the whole block
   (finding #1); measured by the focal eval.
2. Route-polyline reuse fiddliness — mitigated by the pins-only fallback.
3. Popup XSS — mitigated by iframe-sandbox + CSP + textContent, tested
   adversarially (symptom-level).
4. Event-loop liveness — no file I/O in =_render_map_block=; read in the sync
   route (code-review event-loop lens must confirm).
5. OSM tile-usage policy — feature cap + one-map-per-turn keep volume low;
   self-hosting removes it.
