* State

Status: proposed, revised 2026-08-05.  Both stronger-boundary P0 attempts stopped at
mandatory local review.  Pierre then clarified that the migration target is security
parity with the trusted Python/Deep Agents authority, with stronger containment only
around the new disposable Pi runner.  The resulting parity-target successor has a
reviewed seven-scenario report with status =GO= and scope =P1_ONLY= after thirteen local
review rounds; see =docs/2026-08-04-pi-runtime-p0.org=.  P1 is the only authorized
next experiment.  Every product phase remains unauthorized.

Recommendation: make Pi the intended replacement for Deep Agents, through a
side-by-side migration with hard stop gates.  M1/P3 makes the same deployed web UI
serve Deep Agents and Pi, selected immutably per new thread, so Pierre can use Pi for
ordinary work including the current research child.  M2/P5e keeps both /complete/
implementations available for a final full-system comparison after web,
emacsos/phone, voice, and unattended-client parity.  The selector remains through
M2.  Qwen harness authoring is measured and reported before M1 but its maintenance
score does not gate the runtime.  Deep Agents remains the default and rollback path
until the reviewed default switch.

The Pi path starts with the approved prompt-rearchitecture target rather than
reproducing today's large Deep Agents prompt.  It owns the complete provider-bound
system prompt, progressively discloses skills and tool schemas, and runs a
harness-neutral counterpart of every existing behavioral eval.  A fresh immutable
runner release becomes available without restarting the web service to new threads
and to quiescent existing threads; an outstanding async chain keeps its whole thread
on the pinned release until it is terminal.

Pi capabilities are organized as a statically assembled first-party extension
suite with one lifecycle kernel and distinct skills, tools, async-task, and optional
TODO extensions.  Host authorities such as model admission, Runs, approvals,
sandbox management, and async-child lifecycle deliberately remain outside Pi.  The
consolidated “Target end state: Pi-only Assist” section states exactly what remains
and what is deleted.

Pi is not yet proven with the local =Qwen3.6-27B= model.  The migration therefore
keeps evidence gates, but its success path deliberately ends in cutover and deletion
of Deep Agents rather than permanent coexistence.  Existing threads keep their
original engine; pre-schema threads are Deep Agents.  Assist retains its durable
Runs, Docker boundary, approvals, skills, web UI, and client-specific trust
boundaries unless a later measured
simplification replaces one explicitly.

One constraint outranks the attractive prompt and reload features: Pi does not
provide LangGraph's current synchronous mid-turn checkpoint/resume and fair-yield
contract.  If preserving restart recovery, the two-hour active-work bound, queue
fairness, and at-most-once host effects requires recreating a second graph runtime in
the bridge, stop.  Pi is then not a simpler replacement.

* Why consider a different harness

Deep Agents currently supplies a useful bundle: the LangGraph loop and checkpoints,
filesystem tools, TODOs, skills, memory, subagents, summarization, human approval,
and middleware composition.  Assist has since grown stronger product-level versions
of several of those responsibilities:

- =RunService= owns durable work, observers, interruption, and asynchronous child
  delivery;
- =ThreadQueue= owns single-model fairness and liveness;
- =DockerSandboxBackend= owns per-turn containment, filesystem access, and egress;
- the web app owns threads, rendering, status, approval cards, and retries;
- Assist owns its small-model hardening, skills, memory policy, and specialist roles.

The remaining Deep Agents bundle is no longer free.  =create_deep_agent= appends a
framework base prompt after Assist's prompt and adds more instructions through its
middleware.  The prompt census found a 31,279-character system prompt and 28,037
characters of tool schemas on the main web path before the user message.  That makes
the final request harder to reason about and works against the prompt-architecture
rule: preload only what is necessary to choose the next instructions safely, then
progressively disclose the chosen workflow.

Pi is attractive because its core is closer to an agent loop plus typed tools,
messages, streaming events, sessions, and compaction.  Its SDK permits a custom
resource loader and custom tools, while its extension API can change the active tool
set.  This is enough to test whether Assist can remove framework-owned prompt
material and middleware glue without rebuilding an entire agent runtime.

* Goals

1. Determine whether a pinned Pi runtime improves control over the exact
   provider-bound system prompt and tool schemas.
2. Determine whether the local Qwen model preserves current natural outcomes and
   can reliably make reviewed changes to the small Pi harness.
3. Preserve the existing web experience, durable Run contract, queue, sandbox,
   approvals, and async child behavior.
4. Make prompts, skills, and trusted runner code take effect on a new thread or the
   next independent work of a quiescent thread without restarting =assist-web=;
   continuations and async causal chains keep their pinned release.
5. Keep Deep Agents available beside Pi until parity is measured and rollback is no
   longer useful.
6. Reach a final implementation that deletes more Assist and framework glue than it
   adds.  A permanent two-harness abstraction is a failed outcome.
7. Put an actually useful Pi web thread in Pierre's hands at the first safe product
   milestone, before specialist, phone, and unattended-client parity is complete.
8. Carry the complete prompt-rearchitecture target and an accounted counterpart of
   every current behavioral eval onto Pi; do not create a smaller favorable test set.
9. Keep an explicit per-new-thread Deep Agents/Pi choice from the first usable web
   preview through a complete dual-runtime release candidate, then define the exact
   Pi-only system that replaces it.
10. Give cohesive Pi capabilities separate typed extension ownership without
    pretending an in-process extension can own durable product or security policy.

* Non-goals

- Do not integrate the disposable P0 experiment into a product path.
- Do not migrate or reinterpret existing thread histories.
- Do not replace the Assist web UI with Pi's terminal UI or a community web UI.
- Do not replace =RunService= with Pi sessions or replace durable async children with
  a Pi subagent package.
- Do not weaken the Docker, egress, authorization, approval, queue, or git controls.
- Do not load project-discovered, global, or unaudited community extensions in the
  production process.
- Do not allow the model to rewrite the running production harness.
- Do not treat a shorter prompt, a successful demo, or terminal chat as an
  acceptance result.

* Pi capability assessment

This assessment is pinned to =@earendil-works/pi-coding-agent= 0.83.0 (npm
=gitHead= =845d6ff1f6643aba440341cce877ce1c43ebbc39=, Node 22.19.0 or newer)
and repository =main= at

** Project fit and stewardship

Pi's appeal is not only a feature comparison.  Its deliberately small core, short
prompt, typed extension surface, and expectation that users reshape the harness
match Assist's preference for explicit ownership over accumulated framework magic.
The ability to edit an extension while another task continues on the old release is
especially relevant: the product can remain useful while its next agent shape is
being built and tested.

Earendil acquired Pi in April 2026 and kept Mario Zechner as a major stakeholder and
team member.  Earendil is a Public Benefit Corporation whose published purpose
emphasizes open protocols and human agency; its operating principles include
focused outcomes, original curiosity, craft, ambitious goals with credible steps,
and technology as a means rather than an end.  Those values are a positive
stewardship signal and align unusually well with Pierre's reasons for building
Assist.

Values are not a supply-chain control.  The current Pi core is MIT licensed and
Earendil has publicly committed to keeping the core MIT, while also stating that
future adjacent features may be Fair Source or proprietary.  Assist therefore pins
only the MIT core and public SDK, maintains an upgrade and fork escape hatch, and
does not make cutover depend on an Earendil cloud or proprietary component.

** Core and SDK

The coding-agent SDK exposes =createAgentSession=, an =AgentSession= event stream,
custom tools, =SessionManager= JSONL sessions, compaction, and session replacement.
Its documented RPC mode is newline-delimited JSON over stdin/stdout, which provides
a useful transport shape for Python integration without a new listener.  The SDK is
the relevant surface; the TUI is not.

A =DefaultResourceLoader= can override the system prompt, context files, skills,
prompts, and extensions, but Pi 0.83.0's =buildSystemPrompt()= unconditionally
appends the current working directory even for a custom prompt.  The loader and
command-line =--system-prompt= therefore cannot establish complete ownership by
themselves.  Assist must construct the loader explicitly, disable ambient discovery,
and make =assist-kernel= the sole audited owner of =before_agent_start=; it returns
the exact Python-rendered prompt after Pi's builder.  The rejected narrow P0 observed
the intended canary once but did not verify the complete provider-bound census.  A
newly reviewed successor must do so before P2, which must separately
prove that =setActiveTools= cannot displace the per-turn override or reintroduce
framework text; if the public hook ever fails to dominate the builder, stop rather
than accept the extra text.

The extension API supports custom tools, tool-call interception, and
=setActiveTools=.  That is a direct fit for [[file:2026-07-26-agent-prompt-architecture.org::*P2b: Progressively disclose non-kernel tools through loaded skills][prompt-architecture P2b]]: =load_skill=
can reveal both the skill body and its declared =allowed-tools= schemas for the
current invocation.  Tool visibility is not authorization; the existing Python
guards remain authoritative.

** Library, TypeScript, and a possible Rust boundary

Deep Agents' clearest architectural virtue is that Assist imports a library and does
not maintain a fork.  Preserve that property.  The compiled runner imports the
pinned Pi SDK as a normal dependency, calls public factories and events, and owns
only Assist policy and translation.  It does not copy Pi's loop, patch
=node_modules=, invoke private fields, or load the Pi CLI's ambient configuration.
An upstream upgrade is a lockfile change that must pass the provider, prompt,
session, lifecycle, and protocol contract suites before promotion.

Inside the runner, use strict TypeScript with =strict=,
=noUncheckedIndexedAccess=, =exactOptionalPropertyTypes=, and exhaustive
discriminated unions.  Tool and protocol definitions have one schema source and
produce both compile-time types and runtime validators.  Unknown event, message,
tool, or session variants fail closed.  TypeScript safety stops at the process
boundary, so Python independently validates the same closed wire schema; generated
artifacts include a version and digest so either side rejects drift.

The existence of Deep Agents for TypeScript is not by itself a reason to port the
current design to it.  That would change language while retaining the framework
prompt and graph/middleware composition this migration is intended to simplify.  It
remains a fallback comparison if Pi fails specifically on durability while a typed
Deep Agents implementation proves a materially smaller integration.

Pi's documented RPC shape is deliberately language-neutral, which leaves room for
Rust without asking Rust to reimplement the SDK.  The first product slice should not
put Python, Rust, and Node in the production turn path merely for aspiration.  A
small disposable Rust conformance client may proceed in parallel with P1 through P3
to parse and fuzz the bounded runner protocol and supervise a fixture process.  It
is a useful learning and safety artifact but does not gate the first web thread.
Promote Rust into the product only if a later focused
design proves that one Rust supervisor replaces, rather than wraps, the equivalent
Python process/protocol code; it must not add a daemon, listener, store, or third
policy owner.  Pi remains the pinned Node SDK process either way.

** Hot reload

Pi can reload extensions, skills, prompts, themes, and context resources.  Its own
documentation says the command that calls =ctx.reload()= continues in the old call
frame and only later events use the new runtime.  That behavior is suitable for an
interactive coding terminal but creates a mixed-version boundary inside a durable
web Run.

Assist should use a simpler contract:

1. Deploy builds and validates one immutable versioned runner directory, then
   atomically switches a =current= symlink.  There is no watcher or runtime build.
2. After the =work_id= is reserved but before it is executable, Python atomically
   resolves the thread's release cohort.  If that thread is nonquiescent for any
   reason, including an active, pending, interrupted, approval, child, retry, wake,
   or resumable Run, the new work inherits its held fingerprint; otherwise
   Python resolves =current=, verifies the artifact digest itself through no-follow
   opened descriptors, and acquires an ephemeral release hold.  A child-reported
   digest is diagnostic only.
3. A read-only preflight opens and validates the thread session through that held
   release without appending a session entry, calling the provider, or invoking a
   tool.  If it rejects an unanticipated old session, preflight the thread's held
   last-compatible release instead.
4. In one release-registry/Run transaction, commit exactly one successfully
   preflighted fingerprint on the logical work and thread cohort, convert its hold
   into the durable reference, and release other holds.  Only then may a runner
   append the input or make a provider/tool request.  Crash recovery either finishes
   this transaction or repeats read-only selection; it never repins a work that has
   begun execution.
5. Every fair-yield, restart, approval continuation, spawned child, child retry,
   terminal child handoff, and completion-wake Run atomically increments or
   transfers the causal parent's release reference before admission, records that
   fingerprint itself, and validates it before starting a short-lived pinned Node
   runner.  Engine inheritance without release inheritance is invalid.
6. The runner reads the current trusted prompt, skill catalog, and bridge code once.
7. It reports the immutable directory digest plus hashes of those inputs when the
   runner starts; Python compares them with its independently verified, already
   pinned Run value before any provider request.
8. That fingerprint remains fixed until the whole causal async chain is terminal.
   Its last durable release happens only after the terminal result or wake is
   appended.  A thread cannot advance its cohort while any active, pending,
   interrupted, approval, child, retry, wake, or resumable reference exists.
9. The next independent =work_id= on a quiescent thread starts a new runner and
   therefore receives deployed changes without restarting the web service.  A thread
   with outstanding async work deliberately remains on its old release; other
   threads can adopt the promoted release immediately.

There is no file watcher and no model-callable reload tool.  Partial editor writes
cannot enter a running turn, and a transcript cannot acquire an =A -> B -> A=
release sequence from a late old child or wake.
Prompt and skill edits, runner changes, and dependency upgrades become live only
after the ordinary reviewed deploy atomically promotes a validated directory.  A
candidate must open and continue fixtures for every retained Pi session, protocol,
custom-entry, and tool-call version before promotion.  Each thread records its last
compatible release.  If read-only selection falls back before the authoritative
work pin, the UI reports it; one work never partially runs both releases.  An active
logical work keeps its resolved old directory.  Garbage collection shares the
release-registry lock and retains every active/resumable causal reference,
per-thread cohort and fallback, rollback reader, and version
in the compatibility suite; it cannot race resolve/pin/spawn.
This is restart-free Run-boundary reload, not arbitrary in-process hot swapping.

This boundary still leans into “build the agent while also doing other work.”  A
development agent may edit a disposable runner worktree, compile it, run the entire
deterministic contract suite and selected evals, and produce a candidate immutable
release while production work continues on the old fingerprint.  Pierre can promote
the reviewed candidate without restarting =assist-web= and open a new experimental
thread or start work on a quiescent thread to test it immediately.  Promotion is explicit;
the model cannot publish its own change, and an active work item never changes code
underfoot.  Fast iteration comes from parallel old/new releases and cheap process
startup, not from weakening the release boundary.

The mature =pi-subagents= package demonstrates that Pi can support foreground and
background delegation, named agents, and custom rendering.  It also confirms why it
is the wrong boundary here: Assist already has durable task IDs, user steering,
completion wakes, queue priority, cancellation, and web status.  Replacing those
with subprocess-local extension state would be a regression and would leave two
sources of truth.

The official sandbox example and community sandbox packages are similarly useful
for comparison, not adoption.  Pi extensions run in the trusted Node process, and
the documented sandbox guarantee does not cover every extension.  Assist's current
model-facing commands must continue to execute only in its per-turn Docker
container on an internal network whose only egress is the allowlist proxy.

** Capability-oriented extension suite

The first revision proposed one large =assist-runtime= extension.  That keeps load
order simple but weakens the library-like boundaries that make Pi attractive.  The
revised recommendation is a small non-extension runner bootstrap plus a closed suite
of cohesive first-party Pi extensions.  Most agent capabilities get their own typed
extension; product authorities stay outside Pi.

This is a source, type, ownership, and test boundary, not a security boundary.  Pi
extensions share one Node process and its authority, and Pi 0.83 normally logs an
extension error and continues.  Splitting a policy into extensions does not isolate
it from a malicious or broken sibling.  The contained process, closed manifest,
=fatal=/=halt= contract, Python authorities, and Docker boundary still provide the
security and failure containment.

The minimal runner bootstrap owns only the pinned SDK construction, bounded wire
protocol, release/extension manifest verification, namespaced capability registry,
and fail-closed handler wrapper.  It has no model-callable tool or product policy.
One immutable release manifest lists exact extension IDs, versions, digests,
dependencies, exclusive event ownership, registered tool names, state schema
versions, and prompt contributions.  The build rejects cycles, duplicate tool names,
undeclared event overlap, undeclared cross-extension imports, and any ambient or
community extension.  Promotion and rollback always move the whole compatible
release atomically; there is no per-extension hot swap inside an active session.

Keep the suite in one private =assist-pi-runtime= package and statically import its
extension factories.  Pi performs no directory/package discovery.  This preserves
independent source contracts without giving separately installed packages an
unreviewed lifecycle or dependency graph.

The intended suite is:

| Extension | Owns inside Pi | Deliberately does not own |
|-----------+----------------+---------------------------|
| =assist-kernel= | The only cross-cutting lifecycle hooks: exact prompt assembly, final active-tool application, provider census, normalized events, session fsync, whole-batch tool transition ordering, and measured Qwen recovery modules | Product policy selection, durable operation truth, model admission, or arbitrary prompt fragments |
| =assist-skills= | Trigger-only catalog, =load_skill=, skill parsing, =allowed-tools= capability declarations, and memory-as-a-skill presentation | The final =setActiveTools= call or repository/thread memory persistence, privacy, promotion, and authorization |
| =assist-tools= | Typed schemas and bounded RPC adapters for workspace, retrieval, render/artifact, and other Python-owned tools | Filesystem, shell, Docker, network, host effects, approvals, credentials, provenance stores, git policy, or result persistence |
| =assist-async-tasks= | Start/check/update/cancel/list tool schemas, typed RPC adapters, and model guidance | Child admission, task IDs, role/engine/release selection, queue priority, cancellation truth, completion wakes, or =RunService= lifecycle |
| =assist-todo= | TODO tools, mechanics, guidance contribution, and namespaced session entries, /only if/ paired evals select TODOs | A second task database, durable async work, schedules, or =RunService= state |

=assist-todo= is absent if the TODO experiment loses.  Memory is exposed by
=assist-skills= because the prompt-architecture program selects memory as a skill;
its durable store stays in Python.  Sandbox /management/ is intentionally not an
extension: =assist-tools= only presents and invokes a narrow model-facing adapter.
Pure prompt, recovery, batch-gate, and result-validation modules remain separately
typed and tested inside =assist-kernel= because only one extension may own their
cross-cutting event order and fail-closed boundary.

Capability extensions contribute typed prompt fragments, tool declarations, and
activation requests to the kernel registry.  They do not append directly to the
system prompt, call =setActiveTools=, or register cross-cutting lifecycle hooks.
=assist-kernel= deterministically composes those contributions and is the only owner
of =before_agent_start=, =before_provider_request=, =message_end=, =tool_call=, and
=tool_result=.  A capability callback returns a closed result; invariant, protocol,
or fsync failure synchronously takes the kernel's =fatal= path rather than relying on
Pi to propagate an exception.

=load_skill= needs a same-invocation commit point because =before_agent_start= runs
before the repeating agent loop.  During =assist-skills= execution, Python first
validates the selected source/digest and returns the canonical capability set.
Before the tool result returns, =assist-skills= invokes a synchronous kernel-owned
=commitActivation= API.  The kernel appends and fsyncs a namespaced activation record
bound to work ID, release, skill digest, and durable tool batch, recomputes the union,
and alone calls =setActiveTools=.  The next provider request cannot begin until the
load result and activation commit are complete.  Resume reconstructs the active set
from that trusted record; a new independent work starts from the base set.  Python
independently requires the same activation identity before executing a disclosed
tool.  Failure before the durable record leaves nothing active; failure after it is
recovered from the record and never reruns the skill load blindly.

Each extension is tested alone with a fake narrow host contract and again in the
exact assembled manifest.  An extension can be developed while production uses the
old release, but promotion waits for the whole suite's type, lifecycle,
prompt-census, crash, retained-session, and eval gates.  Runtime =load_skill=
activation is a state change within that pinned release, not code hot reload.

Several important responsibilities are therefore /not/ Pi extensions:

- fair use of the single-slot llama.cpp server is owned by the host provider gateway
  and =RuntimePolicyAuthority=;
- =ThreadQueue=, Runs, async-child lifecycle, schedules, subscriptions, SMS, and
  voice admission remain product orchestration;
- Docker sandbox creation, network policy, credentials, filesystem mounts, process
  cleanup, and git enforcement remain Python/OS authorities;
- approval decisions and durable operation results remain =ToolBatchStore= plus the
  existing web projection;
- the browser and phone UI remain their current clients.

This makes those boundaries stricter than pretending in-process code can enforce
them.  A malicious sibling extension can exercise any runner-wide RPC surface, so
extension ID or namespace is never authorization evidence.  It still cannot exceed
the Python-issued invocation manifest, durable batch/CAS state, approval decision,
or backend checks.  The assembled-suite adversarial probe calls every adapter
outside a kernel-journaled batch and proves Python rejects it without an effect.

** Preserve lifecycle, not the middleware stack

Deep Agents' middleware lifecycle is valuable because policies have recognizable
model, tool, state, and completion phases.  Pi exposes enough typed events to keep
that clarity without recreating a chain of opaque wrappers.  The closed release
manifest fixes the suite's phase table, and each retained behavior declares one
extension owner, input/output type, order, failure rule, and parity test:

| Pi phase | Extension owner | Assist responsibility |
|----------+-----------------+-----------------------|
| =session_start= | =assist-kernel= | Validate release, manifest, engine session, and durable input identity before work |
| =before_agent_start= | =assist-kernel= | Compose approved capability contributions, replace the complete system prompt, and set invocation-scoped active tools |
| =context= | =assist-kernel= | Apply only the approved skills/memory/compaction projection without mutating durable history |
| =before_provider_request= | =assist-kernel= | Enforce the exact owned first system message, fail on any other envelope drift, and census the final provider payload.  This public final-boundary transformation is required because Pi 0.83's public =agent.continue()= bypasses =before_agent_start= |
| assistant =message_end= | =assist-kernel= | Journal the complete ordered tool batch before Pi may persist the assistant leaf |
| =tool_call= | =assist-kernel= | Run sequential whole-batch preflight, capability, authorization, and approval decisions before execution |
| =load_skill= execute/result boundary | =assist-skills= through =assist-kernel.commitActivation= | Durably bind the skill digest/capabilities to this work, apply the recomputed active set before returning, and reconstruct it on resume |
| custom-tool =execute= then =tool_result= | Named capability extension, then =assist-kernel= | Capability extension calls its narrow Python adapter; Python durably records the operation result before =execute= returns; kernel validates the normalized, sanitized, bounded value before session append |
| =turn_end= and =agent_end= | =assist-kernel= | Fsync the completed session boundary, then project normalized events and terminal outcome to the parent |
| =session_shutdown= on reload | =assist-kernel= | Flush extension state before a public Pi reload.  Pi 0.83 =dispose()= does not emit this event, so normal exit is an explicit bootstrap terminal frame followed by Python-owned cgroup teardown, never an assumed extension callback |

Pi 0.83 preflights sibling =tool_call= events sequentially before its default parallel
execution, which is promising for the batch gate, but P2 must prove the exact journal
and pause ordering through public hooks before a Pi web thread.  Extension ordering
is explicit; ambient or community extensions cannot enter the closed release
manifest.

Ordinary extension exceptions do /not/ fail closed in Pi 0.83: the extension runner
reports =extension_error= and continues.  The runner bootstrap therefore has one
audited synchronous =halt(frame)= primitive.  Every extension handler is registered
only through a typed =mustHandle= wrapper whose =fatal(reason)= path invokes it
on invariant, journal, fsync, protocol, or policy failure.  =halt= writes a bounded
terminal frame to the dedicated control connection when possible and sends its own
process =SIGKILL=; it never throws or returns.  The
durable journal, session, and child exit remain the parent's sources of truth.
The rejected narrow contract required one =before_provider_request= failure in the
real contained path, but its candidate did not prove closed or backpressured halt.
A newly reviewed successor must prove the bootstrap before P2 extends it across
=before_agent_start=, =message_end=, first =tool_call=, custom-tool return,
=tool_result=, and =turn_end=, and proves that no later provider request, tool effect,
result append, or queue release occurs before the parent terminalizes
handlers/backends, empties the named cgroup, and reaps the direct child.  The parent
then performs the one ordinary release.  If synchronous termination cannot enforce
that contract without a Pi fork, stop.

Policies that remain authoritative in Python, including backend containment, host
authorization, approval decisions, URL provenance, and git controls, are not
duplicated in the extension suite.

This is the Deep Agents lesson to retain: a legible lifecycle and explicit
composition.  It is not permission to port fifteen middleware classes one for one.
The responsibility census must show which policies disappeared, moved to a cohesive
typed Pi extension, or stayed at the Python operation boundary.

=RuntimeSession= contains only the operations the current clients actually use:
send or stream a message, continue a recoverable turn, inspect or resolve a pending
approval, obtain normalized visible/raw message metadata, and return a recovery
snapshot containing leaf state, pending batch, resumability, and durable input
identity.  It does not expose =agent=, =runconfig=, LangGraph, or Pi types.

Python builds one serialized runtime manifest per engine invocation: for Assist this
is a durable Run; for emacsos it is the authenticated conversation generation and
request.  The manifest carries the immutable provider-profile digest, rendered
prompt, normalized tool schemas, skill
descriptors, approval policy, role, context, and trusted capability IDs.  Python
retains callbacks and backend objects; Node receives data only.  =AgentSpec=
continues to be the Python embedder declaration during coexistence, but its
=BaseTool=, =BackendProtocol=, and Deep Agents =interrupt_on= objects never cross
the pipe.  A conversation's runtime engine is separate immutable metadata because
engine choice is an operational migration concern, not agent identity.

For new threads, =ThreadManager= atomically publishes the visible thread directory
with an immutable =runtime.json= before admitting its first Run, using the existing
temporary-directory-and-rename pattern for hidden threads.  Every new thread writes
an explicit engine and provider-profile digest; the initial profile is the exact
local Qwen profile.  An absent marker means Deep Agents plus the historical local
profile only for a directory that predates this schema.  Hidden child metadata copies
and validates the parent/client engine, exact provider profile, and causal parent's
release fingerprint, and atomically holds that release before admission, so recovery
never guesses.  No adapter converts
LangGraph checkpoints into Pi JSONL or vice versa.

The Pi runner is a contained child process of the existing synchronous per-turn
worker.  The selected Bubblewrap version closes arbitrary inherited FDs, so the
parent creates two one-run Unix listeners, mounts only their inodes into the private
runner namespace, accepts one exact-cgroup connection on each, then closes
and unlinks the listeners.  One connection carries bounded control and tool frames;
the other carries the stock Pi provider's bounded HTTP/SSE exchange through a
loopback-only transport bridge.  Python admits the first peer only through the private
listener from the expected namespace slot in the exact transient cgroup.  Each
accepted one-run stream is a capability of that cgroup, not process identity;
the protocol nonce binds the run and sequence rather than authenticating a process.
Stdout and stderr are separate bounded logs and can never be parsed as protocol.
There is no routable TCP listener, shell-built command string, secret in argv, or
inherited Pi user config.  Every request carries a parent-generated unguessable nonce,
engine-session ID, monotonically increasing sequence, operation name, JSON value, and
exactly one closed authenticated client identity:

- ={kind: "assist", run_id, work_id, thread_id}=; or
- ={kind: "emacsos", conversation_generation, request_id, client_thread_id}=.

No fake Assist Run is created for emacsos.  The nonce is never model-visible.  Both
sides reject unknown fields, oversized or duplicate frames, invalid ordering, and
any tool not registered for that role.

Dedicated off-loop drainers consume stdout and stderr to EOF for every runner.  They
retain only a fixed diagnostic tail but continue discarding after the cap, so noisy
output cannot fill a pipe and deadlock the holder.  Teardown joins both drainers and
closes every FD before any queue or client lock releases.

The runner constructs every Pi service explicitly.  It uses
=SettingsManager.inMemory()= with one audited complete configuration, an explicitly
constructed model and credential source, and =SessionManager.open()= on the one
server-selected thread path.  It starts with all built-in tools disabled; P2 later
adds only Assist custom tools.  Every =no*= resource switch is set even though the
custom loader also supplies explicit empty resources.  P0 pins this construction and
checks its external provider/session behavior without treating untrusted
runner-reported settings as a security attestation.  P2 adds the effective-settings,
model-compatibility, session, resource-family, and active-tool census for every
disclosed tool set as conformance evidence.  Neither
=~/.pi= nor project settings can alter retry, compaction, shell, model, or discovery
behavior.

Running Pi inside the model's workspace sandbox would mix trusted harness state with
model-controlled files.  Instead the runner gets its own OS containment envelope:
dedicated unprivileged identity, fixed allowlisted environment, read-only immutable
release, private temporary directory, read-write access to only the one parent-created
engine-session inode, cgroup/resource limits, and no direct network route to the model
or general network.  Its only provider path is the lease-enforcing gateway below.
It cannot read the service home, worktree, deployment environment, other threads,
Docker socket, or phone credentials.

Pi 0.83 resolves its agent directory at module import through =os.homedir()=.  The
closed environment therefore contains only =PATH=/runtime=, =PWD=/tmp=, and
=HOME=/tmp/home=; that home is an empty directory inside the private tmpfs.  It is
not the service home and cannot contain Pi configuration.

The web client's model-facing filesystem and commands continue through the existing
Docker container.  Other embedders continue through their Python-owned backend;
emacsos keeps =EmacsBackend= on Deep Agents until P5b replaces its shared full-trust
identity with the narrowed worker.  Host-effect tools call the
same Python functions and authorization checks used by Deep Agents.  If this runner
containment requires a second elaborate runtime, P0 fires the simplicity stop gate.
P2 separately fires its stop gate if the enforced real-model data plane requires a
second elaborate runtime.

The runner source, installed Pi package, lockfile, and system prompt are outside the
model workspace and read-only to the sandbox.  Qwen can edit a copy only in an
explicit development fixture.  A reviewed deploy makes that change live at the next
independent logical-work boundary.

** Shared model data plane

A queue token that honest code may bypass is not admission control.  The llama.cpp
listener must be reachable only by one small local provider gateway running under a
separate OS identity or network namespace.  Kernel routing/firewall policy denies
the Pi runner, =assist-web=, emacsos-server, sandboxes, and phone backend a direct
connection.  Every Pi and Deep Agents provider request crosses the gateway before
P3.

Trusted Python orchestration asks the gateway for a one-use lease bound to its OS
peer, client service, authenticated execution identity, engine, release, model ID,
body digest, request/token/time budget, and cancellation authority.  A Pi runner
receives only that lease for the next request.  The gateway consumes it once, checks
the exact non-redirecting destination and request digest, forwards within the bound,
cancels the upstream on revocation or disconnect, and rejects replay, extra requests,
identity substitution, or cross-lease cancellation.  A later provider call needs a
new parent-authorized lease.  The gateway logs metadata, never prompts, tool results,
credentials, or response bodies.

Closing a client socket is not proof that llama.cpp stopped generating.  The gateway
keeps the admission slot until it observes the upstream's terminal response or a
provider-owned idle/cancel acknowledgement for that exact request.  If neither
arrives by the bounded cancellation deadline, it quarantines the model as
unavailable and uses the existing bounded model-maintenance path to restart and
prove zero active generation before admitting another lease.  A failed restart
keeps the model unavailable; elapsed time does not transfer ownership by itself.

The same gateway is the fair admission owner across authenticated work identities.
It holds no conversation, session, Run, tool, or approval state.  Build its slot
accounting for a configured capacity =N=, but deploy and qualify P3 with =N=1= and
llama.cpp =--parallel 1=.  The provider's queue is defense in depth, not the fairness
boundary.  The gateway applies bounded per-client/per-work queues, user-priority
aging, and queue caps so one dispatcher cannot occupy every pending position.  A
lease owns one exact slot until terminal/idle proof; cancellation cannot target a
sibling slot.  The gateway verifies configured capacity against the protected
server view and fails closed on mismatch.

After the local Pi web path is stable, a separate experiment may benchmark
llama.cpp =N=2=, then higher only if measured VRAM, maximum-context behavior,
latency, output quality, and voice/user fairness remain acceptable.  Test queue
floods, two long generations followed by phone work, cross-slot cancellation,
OOM/context interference, gateway/model crash, and restart with every slot active.
An unproved zombie quarantines the whole model.  =--parallel N= is resource sharing,
not authorization or fairness, and an in-process Pi extension must never own it.

Any fault requiring a whole-model quarantine is one atomic server-generation
transition: close admission, revoke and fence /every/ active slot lease, mark each
affected provider operation interrupted or quarantined, reap every associated
runner/stream, and prove the old llama.cpp generation dead or idle before restart.
A closed socket is not terminal proof.  No sibling request auto-retries, appends a
partial assistant/tool leaf, or reuses its old lease after an OOM, zombie
cancellation, gateway crash, or server restart; each receives a visible recoverable
or ambiguous outcome from its own durable state before any new lease is issued.

The rejected narrow P0 nominally ran one stock-SDK request, cancellation, and cleanup
through a disposable in-process gateway and instrumented upstream, but review did not
accept the cancellation or cleanup proof; it neither contacted nor locked the shared
model.  A newly reviewed successor is required before P2 routes every live Assist and emacsos provider client
through the reviewed gateway, passes the complete real-Qwen provider matrix, and
proves real-model cancellation/restart fencing before the first Pi web thread.
If a small gateway plus kernel-enforced exclusive model reachability cannot be built
and operated simply, stop rather than ship an advisory lock or direct runner access.

** Optional OpenRouter experiment, after the local Pi path

OpenRouter could add independent cloud capacity and access to stronger models.  It
does not make the one local llama.cpp slot parallel, and it must not be coupled to
the Pi migration's Qwen qualification.  Pi already supports OpenRouter provider
configuration and forwards explicit routing preferences, so no community extension
is needed.

Recommendation: finish the local-Qwen P3 dual-runtime milestone first.  Then run an
independent, synthetic-data OpenRouter conformance/privacy/cost probe and, only if it
passes, offer an explicitly selected /new web thread/ provider experiment.  A busy
local queue never implies consent to export a prompt.  There is no automatic local
to cloud or cloud to local overflow, fallback, model substitution, or mid-thread
provider change.  Every child, retry, and completion wake copies the exact immutable
provider-profile digest, model, provider allowlist, privacy flags, cost policy, and
broker class before admission; a local parent copies an explicit local-only profile.
=RuntimePolicyAuthority= and the one-use provider lease bind the same fields.  Phone,
voice, schedules, subscriptions, SMS, triage, and other unattended clients remain
local until separately designed and approved; OpenRouter success never gates Deep
Agents retirement.

The Pi runner keeps its empty environment and no-network boundary.  A completion-only
key lives in the provider gateway or a smaller dedicated cloud broker, supplied by a
system credential, never argv, tracked files, Pi JSONL, logs, or runner environment.
The broker validates a one-use lease and exact body digest, injects the key, permits
only the fixed HTTPS origin/path/model/provider profile, rejects redirects, and
reserves a conservative worst-case charge before dispatch from a persisted current
pricing snapshot and the bounded input/output/reasoning budget.  Authenticated terminal usage
or an authoritative generation lookup may reconcile the reservation downward;
missing usage retains the reservation and estimated charge.  Per-request, per-work,
and daily local caps plus the inference key's provider-side hard spend cap bound
partial-stream failures.  The broker holds no OpenRouter management credential.

OpenRouter's documented defaults are too permissive for Assist: provider fallback is
on, collection-eligible providers are allowed, and ZDR is opt-in.  The first probe
therefore forces =allow_fallbacks=false=, =data_collection="deny"=, =zdr=true=,
=require_parameters=true=, one exact =only= provider allowlist, bounded =max_price=,
no OpenRouter plugins, server-side tools, or context transforms, and =store=false=
where supported.  Assist's declared model tool schemas remain in the exact
body-digest contract.
Returned routing metadata must match the requested model/provider/profile; a partial
stream, unexpected route/transform, 402, 429, or 503 is a visible bounded failure,
not a replay or fallback loop.  ZDR still sends content to OpenRouter and the chosen
upstream, and OpenRouter permits some in-memory prompt caching under ZDR, so the UI
must describe cloud handling honestly rather than equating it with local privacy.

* Prompt ownership and the prompt-architecture program

Pi must implement the approved instruction-placement architecture, not fork it or
first reproduce today's prompt.  Prompt-architecture P1 and P1b remain prerequisites
for paired natural conversation outcomes because they establish the outcome judge
and separate natural acceptance from capability probes.  They do not block the Pi
provider probe or harness-authoring experiment, whose compiled artifacts and actual
deterministic behavior decide the result.  Pi and Deep Agents then use the same
frozen product cohorts and the same six instruction homes.

For each Pi runtime invocation, Python renders the exact role kernel and the audited
inline =before_agent_start= hook returns it as the final per-turn system-prompt override.
The custom resource loader supplies an explicit empty set
for ambient context files, prompt templates, global skills, and extensions, then
adds only the role's audited Assist resources.  Pi's default prompt, current working
directory prose, global =AGENTS.md=, =SYSTEM.md=, =APPEND_SYSTEM.md=, and =~/.pi=
resources must not reach the provider.

P2 changes the active tool set before and after =load_skill= and proves that Pi's
base-prompt rebuild cannot displace the per-turn override or reintroduce the working
directory.  A newly reviewed P0 successor must prove the tool-free synthetic provider
boundary; the rejected candidate did not complete its effective census.  The provider
request, not =DefaultResourceLoader= configuration, remains the contract.

The provider-bound census is the gate, not the source configuration.  It records:

- exact final system text and provenance spans;
- exact active tool names, descriptions, and schemas;
- model/provider compatibility flags;
- role, skill catalog, memory, and context sources;
- Pi package version, source commit, lockfile digest, and runner fingerprint.

Prompt-architecture P2 through P5 should remain harness-neutral.  Once Pi
qualification starts, each later prompt-architecture phase compares the two
harnesses on the same proposed instruction change.  Narrow Pi P0 uses only a
synthetic ownership canary and neither depends on nor edits the active prompt work.
Before Pi P2/P3 selects tool disclosure, reconcile the completed Deep Agents prompt
experiment with Pi P1 rather than reproducing a second large implementation.

The first usable Pi web release must include every prompt-architecture improvement
approved by then, plus the already-approved target shape for phases whose Deep
Agents mechanics are the obstacle: generated role kernel, natural-versus-capability
eval separation, progressively loaded instructions, invocation-scoped
=allowed-tools= schema and execution filtering, and explicit memory/context homes.
It does not inherit the current 31,279-character prompt for the sake of mechanical
parity.  Any Pi-only realization is still judged against the same user outcomes and
security contracts; it does not silently redefine the prompt-architecture program.

* Sessions, recovery, and approvals

Pi's JSONL session is the model-context record.  Assist's =RunService= remains the
product source of truth for admission, status, observers, and terminal outcome.
One new harness-neutral =ToolBatchStore= is operation truth, not a third Run
lifecycle: it owns ordered sibling calls, canonical arguments, approval decisions,
execution state, and durable results.  =RunService= stores only Run lifecycle and a
batch reference; Pi JSONL stores model context plus authenticated recovery markers,
never Run or operation truth; web status remains a projection.

Before the provider can run, the server appends a public Pi custom session entry
carrying the authenticated =run_id=, =work_id=, engine-session ID, and canonical
input hash.  Recovery distinguishes input not appended, appended but not started,
and completed without comparing message text.  P2 kills the runner before and after
each append boundary.  If public Pi session APIs cannot provide this identity
without ambiguous replay, the experiment stops.

Pi can continue a session whose leaf is a user message or completed tool result.
It must not blindly replay a tool call whose result was not durably recorded.  The
=ToolBatchStore= records every host-effect operation before its result is appended to
the Pi session.  Once bound after append, the server keys a call by authenticated
thread, immutable engine session, durable assistant session-entry ID, batch index,
tool-call ID, canonical tool name, and requested-argument digest.  Requested
arguments remain immutable.  An
approval edit adds a compare-and-swap decision version with separate effective
arguments and digest; execution idempotency is the batch item plus decision version.
It rejects duplicate IDs within a batch or session, and
an approval continuation carries the original durable batch identity.  A repeated
completed call receives the recorded result.  An ambiguous non-idempotent call stops
with a visible recovery error instead of executing twice.

Cross-store ordering is journal first:

1. On the public assistant =message_end= hook, before Pi has assigned a session-entry
   ID, write and fsync a =prepared= batch containing a server-generated batch ID,
   previous durable leaf ID, ordered calls, and assistant content hash.  Only then
   allow Pi to append the assistant leaf.
2. Pi documents that =tool_call= waits until the current assistant message has been
   persisted.  At the first sequential preflight, fsync the session file through its
   public path, read the new durable assistant entry ID, compare its parent, calls,
   and hash, then atomically bind the prepared batch and mark
   =assistant_appended=.  After a crash in this gap, recovery may perform the same
   unique parent/hash/call match; zero or multiple matches are corruption, never a
   reason to execute.  A prepared batch without a leaf is safe to discard.  A
   tool-bearing assistant leaf with no matching durable batch is corrupt and cannot
   execute.
3. Before handing any permitted item to a Python handler, compare-and-swap it from
   =ready= to =executing= and fsync the item, decision version, effective-argument
   digest, effect class, and any target-enforced idempotency key.  The handler's
   terminal result or error is then written and fsynced before its custom-tool
   =execute= returns to Pi.  A crash with =executing= and no terminal result is never
   treated as not started.  It may retry only when the handler proves a target-side
   idempotency contract for that exact key; otherwise recovery marks it =ambiguous=
   and does not execute it again.
4. Complete one ordered result batch before appending any tool result to Pi.  For an
   ambiguous item, include a durable synthetic ambiguous result; every unstarted
   sibling receives a durable not-executed result.  Append and fsync the complete
   batch before accepting another user message, then mark =results_appended= and
   transition the Run.  Pi therefore never remains indefinitely at an unmatched
   tool-call leaf.  Orphan prepared/results records are reconciled by stable IDs,
   never by text or model-controlled call ID alone.
5. P2 force-kills immediately before and after every =ToolBatchStore= write, Pi
   append/fsync, and =RunService= transition and proves the one
   recovery action for every partial state.  If Pi's public blocking hooks cannot
   enforce journal-first ordering, stop.

Approval uses the current web contract:

1. The runner receives one complete assistant message and, inside =message_end=,
   asks Python to preflight the entire ordered tool-call batch before Pi persists or
   executes any call.  It journals the classification before returning.
2. If no call needs approval, Python executes permitted calls under the current
   mutation-serialization rules, records every result, and appends exactly one
   ordered result for every tool-call ID.
3. If any call needs approval, Python has persisted the full ordered batch, exact
   canonical arguments, and the fact that every sibling is unexecuted.  Pi 0.83 has
   no public “pause after persisting this assistant message” return value.  On the
   first =tool_call=, after binding and fsyncing the assistant leaf, the extension
   writes the interruption frame/journal state and invokes synchronous =halt=
   termination primitive before returning to Pi.  No sibling executes.  Only after
   child death is confirmed may the queue be released and the Run become
   =interrupted=.
4. The existing approval card appears in the conversation.  Approval, edit, or
   rejection applies once with compare-and-swap and creates an ordinary continuation
   Run.  A repeated submission returns the existing decision.
5. A fresh runner opens the session at the durable assistant leaf.  Python executes
   the approved form at most once, records its result, executes each permitted
   deferred sibling or records its policy rejection, and produces exactly one result
   per original tool-call ID in original order.
6. Only after the complete result batch is durable does the runner append it and
   call Pi =continue()=.

The current web UI supports one approval card per interrupted batch.  More than one
approval-required sibling is therefore an invalid batch: execute none and append one
ordered policy-error result for every call, telling the model to propose gated
effects one at a time.  One gated call mixed with permitted siblings follows the
defer-whole-batch flow above.  P2 tests two gated siblings and the mixed case.

This transition is a P2 feasibility test, not assumed SDK behavior.  It must use
public Pi session and event surfaces plus the contained child-termination boundary.
P2 proves =message_end= precedes persistence, first =tool_call= observes the
persisted leaf before execution, text-only =turn_end= can fsync before parent
completion, and self-termination prevents every sibling effect.  If Pi begins
sibling execution before the batch gate, cannot append a complete externally
recorded result batch, or requires a custom agent loop, checkpoint scheduler, or Pi
fork, the replacement experiment stops.

Sandboxed file and shell operations are not assumed to be exactly once after a
process crash.  If a result is missing, the UI reports the ambiguous operation and
requires inspection or a fresh user instruction.  Reducing the probability of a
duplicate is not a correctness guarantee.

* Threat model

The new attack surface is a trusted Node dependency and child process, a
cross-language message parser, dynamic tool selection, and persisted Pi JSONL.  The
design contains each surface by construction:

- exact-lock Pi and TypeScript dependencies; no runtime package install, update
  check, telemetry, or network discovery;
- fetch and compile in a disposable unprivileged build environment with no service
  secrets; disable npm lifecycle scripts by default, audit any required exception,
  and promote only the immutable compiled artifact and verified lock.  The service
  host runs no npm install, compiler, or TypeScript loader;
- use an empty dedicated Pi home and explicit resource loader; never scan global,
  project, domain, or user extension directories;
- do not import community packages into production without a separate source audit;
- expose no Pi built-in filesystem or shell operations on the host;
- run under the dedicated OS containment envelope described above; probe unreadable
  canary files and environment values plus direct-model and general-egress denial in
  P0;
- make the separately contained gateway the only kernel-reachable model peer.  It
  chooses one exact allowlisted scheme, address, port, and model ID, forbids
  redirects, and enforces one-use bound leases for every client.  Clear =HOME=, XDG
  variables, =NODE_OPTIONS=, =NODE_PATH=,
  proxy variables, and every provider credential from the runner environment.  The
  current local endpoint requires no Node-held credential; any later cloud-provider
  credential stays in the gateway/broker, while the runner receives only the
  request-bound one-use lease over its private control connection;
- keep web model file/shell access in the existing per-turn Docker container and
  each other client in its approved Python backend; all host effects remain behind
  Python authorization and approval gates;
- use the two inode-mounted one-run Unix listeners described above, never stdout or
  a reusable service listener; admit only the expected namespace slot from the exact
  transient cgroup, treat the stream as that cgroup's capability, and bind its nonce
  to the run/sequence.  Bound frame size/count, logs,
  tool output, session growth, process time, PIDs, FDs, CPU, and memory;
- validate messages and tool arguments independently on both sides; never create a
  shell command by concatenating model or bridge values;
- test that secrets cannot appear in argv, environment metadata, prompt census, Pi
  session files, stdout/stderr, errors, crash reports, or logs;
- have the parent create a 0700 engine directory and 0600 regular session file under
  one fixed root with dirfd/no-follow operations, retain that file descriptor, and
  bind only the writable file inode into the runner.  Pi alone writes its JSONL; the
  parent fsyncs and verifies the retained inode and records each committed offset and
  prefix digest.  Reject links and nonregular files, enforce record/line/file quotas
  before Pi parses, allow only audited record kinds, load no path-based attachment
  from session data, and recover only a verified uncommitted suffix.  Test crash-safe
  append and directory/file =fsync=;
- make active-tool state invocation-scoped and derived from the server-owned catalog
  and trusted skill-load record.  Python enforces the allowed set on every call;
  Pi's active set controls schema disclosure only.  Adversarial skill and tool-result
  text must not grant a capability;
- spawn directly without a shell in a named transient cgroup, close every
  non-allowlisted FD, and on every exit TERM then KILL the entire cgroup, prove it
  empty, and reap the direct child before releasing =ThreadQueue= or =_STREAM_LOCK=.
  A process group is not an authority because a descendant can create a new session.
  Test that no descendant,
  pipe, or provider socket survives cancellation, parser failure, timeout, client
  disconnect, approval interruption, or runner crash;
- treat Python tool handlers and their backend as part of the same execution lease.
  On cancellation or runner failure, stop admitting calls, invoke the backend's
  bounded termination, wait for every handler to finish or durably mark its effect
  ambiguous, terminate runner and sandbox, join drainers, and only then release.  If
  a handler cannot become terminal, keep the client/model unavailable rather than
  overlap a new turn.  Exercise cancellation during Docker =execute= and emacsos
  =apply_config=, not only during provider work;
- retain the current single-worker FastAPI rule: blocking runner and Docker work
  stays inside the synchronous background worker and never on the asyncio loop.

A malicious skill body is still untrusted text.  Loading it may guide the model but
cannot grant a tool, host path, extension, or approval.  A malicious Pi session file
is likewise data, never an extension source.

** P0: parity-target execution boundary

P0 trusts the Python authority, as the current Deep Agents path does, and treats the
new Node/Pi process plus its descendants as disposable.  It does not attempt to
protect the build from another trusted same-user process, create an independently
enforced cryptographic lease, or turn the experiment into a retained release
service.  Those requirements exceeded the intended migration threat model.

The stock pinned Pi runner must have no service secret or authenticating external
provider credential, no active tools, no ambient
skills/prompts/themes/context, no host workspace, and no direct model or public
network route.  It sees a read-only runtime and one writable size-limited session
inode.  A private one-run Unix connection carries Pi's exact HTTP request to trusted
Python, which validates the complete closed provider envelope and may forward at
most one canonical request to a fixed in-process instrumented upstream.

Python admits the first peer only from namespace PID 2 in the exact disposable runner
cgroup.  This verifies launch topology, not immutable executable identity: the
untrusted process can transfer the stream or replace itself with =execve=.  The stream
is the cgroup's capability.  Delegation within the same no-secret, no-network,
recursively killed cgroup grants no additional authority.  The peer pidfd remains
construction and cleanup evidence.

The host, rather than the runner, gates containment from =/proc=: distinct network
and mount namespace identities, no IPv4 route, a real host canary absent beneath the
runner root, zero soft and hard core-file limits, namespace-slot/exact-cgroup identity, and
effective transient-unit limits.  Runner-reported connection counts remain a
pinned-SDK conformance observation, not a security attestation.

One invocation must exercise seven fresh transient services: deterministic success,
hook fail-stop with the control channel closed, hook fail-stop after Node reaches
backpressure, hostile descendant teardown, cancellation, fresh success after that
cancellation, and Python-authority death while the upstream and hostile descendant
are active.  Each normal result is issued only after its runner child cgroup is
empty and reaped.  The outer orchestrator then requires the whole service inactive
and its retained =cgroup.events= certificate empty before starting the next case.

The reviewed run found one Pi-specific cancellation behavior: Pi 0.83 opens one
additional provider connection after abort despite retry settings being disabled.
The one-shot bridge rejects it locally; Python receives and forwards exactly one
provider request and waits for the first upstream to become terminal.  This observed
retry/reconnect behavior is part of the P2 real-provider contract, not a reason to
weaken one-shot admission.

Gate: the full report is =GO= only if every scenario passes in one invocation, every
effective systemd/cgroup and cleanup certificate is present, the closed provider
request and host-derived containment evidence match, the post-cancel run uses fresh state, the
authority-death setup has a trusted pre-death readiness frame, its final result is
assembled only from the outer process's kernel observations, and all
hand-authored experiment files remain at or below 1,500 lines.  =GO= authorizes P1
only.  It does not qualify Qwen, authorize P2, or expose a Pi thread.

* Cutover and rollback contract

The web-default switch is a reviewed product change after P5a, not an automatic
consequence of an eval score.  Full-system cutover and retirement remain separate
decisions after M2/P5e.

One Assist-owned =RuntimePolicyAuthority= is the durable authority for cutover,
rollback, and retirement admission.  It runs inside the existing trusted
=assist-web= service rather than adding a daemon and is the only writer of a 0600
host-local SQLite policy database.  No dispatcher opens that database.  External
dispatchers use a bounded Unix socket whose owner authenticates =SO_PEERCRED=,
distinct service UID and unit identity, host boot ID, and an authority-issued
unguessable process incarnation held with a =pidfd=.  Model workers, sandboxes, and
the phone UI helper cannot connect.  The closed API permits a peer only to read the
epoch, register or terminalize its own admission, and acknowledge its own
generation; it cannot publish an epoch, name another peer, alter another admission,
or forge another acknowledgement.  Only an authenticated operator action may
publish an epoch.  Corrupt or unavailable policy storage closes admission.

Every web, emacsos, voice, child/wake, schedule, subscription, SMS, triage, and
catch-up dispatcher must, on process startup and again in the same authority
transaction that records an admission, prove that the selected engine/client pair
is allowed.  A cached default is never authority.  The returned admission capability
is required to spawn a Pi runner and to obtain any engine's model-gateway lease.
Stopped dispatchers do no work; a new incarnation blocks before queue recovery or
admission until it has read the durable epoch.  Epoch publication freezes the exact
set of registered process incarnations that must acknowledge.  A missing or paused
incarnation is never expired by heartbeat or PID.  For its own child, =assist-web=
may signal through the held =pidfd= and reap it through the ordinary parent path.
For an external systemd service, the authority uses a narrowly authorized fixed-unit
fence that cannot name an arbitrary unit; the registration also binds the systemd
invocation ID.  After an authority restart, a surviving peer must reauthenticate its
persisted incarnation, boot ID, unit, and invocation ID over a fresh socket so the
authority can acquire a new =pidfd= before accepting recovery or acknowledgement.
If it cannot, systemd stops/kills the entire registered unit cgroup and remains
responsible for reaping it; inactive unit state plus an empty cgroup is substitute
proof when the old =pidfd= no longer exists.  A changed host boot ID proves every
pre-reboot incarnation dead, after which persisted admissions are still
terminalized or quarantined before recovery; a new process must register as a new
incarnation.  When a =pidfd= is available, the authority additionally waits for its
exit.  If the fixed-unit fence is unavailable, the epoch stays unacknowledged for
operator action; a timeout never implies death.  Only then may it terminalize or quarantine
every admission owned by that incarnation and remove it from the acknowledgement
set.  A later incarnation starts from the current epoch and cannot revive the old
one.  The authority owns selection policy only, never Run, session, or
tool-operation lifecycle.

** Web-default readiness packet

Before Pierre chooses a cutover, one packet reports:

- every deterministic security, recovery, queue, approval, and web gate through P5a,
  all of which must pass;
- paired N=10 natural outcomes and any statistically or practically meaningful
  regression;
- live Pi web Runs by outcome, failure, cancellation, restart, approval, child task,
  and compaction, with every lost or duplicate host effect called out;
- final provider prompt/schema ownership and the measured token/latency change;
- the complete responsibility census with old code actually deletable, new runner
  and bridge code, dependencies, build/deploy burden, and unresolved dual policy;
- Qwen harness-authoring results reported separately from runtime reliability;
- an explicit inventory of Deep Agents threads and non-web clients still awaiting
  P5b through P5d, so web-default readiness is not confused with full retirement
  readiness.

Pierre explicitly approves or declines the default switch from that packet.  A
failed hard gate cannot be waived by a good aggregate score.

** Default switch

1. Deploy the reviewed dual-runtime release with Deep Agents still the default and
   Pi available only behind the operator flag.
2. Pierre uses explicitly selected Pi threads during the P5a soak.  Review-driven
   fixes repeat checks and redeploy before more testing.
3. On approval, change one server-owned default so newly reserved ordinary web
   threads use Pi.  Atomically publish =runtime.json= with the engine and exact
   provider profile alongside the thread directory before admitting the first
   durable Run and redirecting.
4. Keep the collapsed per-thread selector through the full-system M2 comparison,
   but preselect Pi.  Deep Agents remains the explicit alternate for a new thread
   during coexistence; only the reviewed P6 retirement change removes the selector.
5. Never change the marker on an existing thread.  Active and historical Deep
   Agents threads continue on Deep Agents; existing Pi threads continue on Pi.
6. Emacsos-server new conversation generations switch only after P5b and Pierre's
   live-phone approval.  SMS, schedules, voice, triage, and hidden child roles keep
   their approved engine until each client passes its own recovery and UX gate.  A
   hidden child records the engine, exact provider-profile digest, and held release
   fingerprint selected by its parent/client contract before admission.

There is no shadow execution of live tools during cutover.  Paired comparisons use
synthetic threads and cassette or idempotent fixtures only.

** Rollback

The safe operational rollback is one durable =RuntimePolicyAuthority= epoch across
every client that has cut over, not a web-only setting:

1. Publish an epoch that closes new Pi admission for ordinary web threads, emacsos
   conversation generations, voice sessions, hidden children and wakes, schedules,
   subscriptions, SMS, triage, and catch-up.  Revert each already-cut-over default
   for /future/ work to Deep Agents; a dispatcher rejects a stale policy epoch.
2. Never open an existing Pi session with Deep Agents or rewrite its engine marker.
   Existing interactive Pi threads and emacsos generations remain readable and
   either continue on an explicitly selected known-compatible Pi runner after the
   defect is fixed or show a clear temporarily unavailable state.  A live Pi voice
   session is ended through its ordinary authenticated teardown if it cannot safely
   drain.
3. Before acknowledging rollback, durably pause or quarantine every Pi-targeted
   schedule, subscription, queued or catch-up ingress, SMS/triage item, pending
   approval, child completion, and wake.  Cancel and reap active runner/provider/tool
   work under its operation record; an ambiguous external effect stays quarantined.
   Each item may later continue on an explicitly approved known-good Pi runner,
   remain paused, or be canceled.  It is never silently redirected to Deep Agents.
4. Acknowledge only after every frozen process incarnation has persisted the new
   generation or has been fenced and its admissions terminalized/quarantined, the
   policy/admission tables prove no new Pi work can be admitted, and
   active Pi dispatch has drained or reached a durable terminal or quarantine state.
   A stopped or newly starting dispatcher is safe by the mandatory startup read.
   Crash and restart tests at every epoch/queue/operation boundary prove that no Pi
   provider or tool dispatch begins after acknowledgement.

The deploy retains the last known-good immutable Pi runner directory through the
rollback period.  The =current= symlink may move back only after that runner proves
it can open the persisted session version and tool-call shapes.  If compatibility is
not proven, disable Pi continuation rather than guessing or replaying effects.

For a user who must continue immediately, the Pi thread page offers “Continue in a
new Deep Agents thread.”  It creates a new thread with a visible link to the source
and an editable handoff message; it does not convert hidden state or silently copy a
checkpoint.  The symmetric action is available when retiring an old Deep Agents
thread in favor of Pi.

** Deep Agents retirement

After the rollback period, produce a second review packet from the live default.
Before its final census, publish and acknowledge a =RuntimePolicyAuthority= retirement
epoch that closes every new Deep Agents Run, continuation, child/wake, and
unattended-binding create/change/resume admission.  Drain, cancel, or quarantine
already admitted work under its existing lifecycle.  In the same policy transaction
that admits a visible Pi successor, make its non-retained Deep Agents predecessor
read-only; a predecessor selected to keep running blocks retirement completion and
therefore deletion.  Only after every frozen dispatcher incarnation acknowledges or
is fenced under the authority rule, every future process is covered by the startup
rule, and no live Deep Agents admission
remains does the final thread and unattended-binding census run.  Crash tests around
closure, predecessor marking, successor publication, and census prove that a stale
dispatcher cannot create a late binding or Run.

Deletion requires:

- no unresolved Pi reliability, security, prompt, queue, or web-parity regression;
- no active non-web client still depending on the Deep Agents path;
- no paused, pending, queued, catch-up, or otherwise dormant unattended binding can
  still resume against Deep Agents; every P5d census row is durably canceled,
  migrated without dual dispatch, or explicitly retains the compatibility runtime
  and therefore blocks deletion;
- Pierre's explicit decision for each still-active Deep Agents thread: keep the
  compatibility runtime longer, create a visible successor Pi thread and make the
  old predecessor read-only atomically, or make the old thread read-only;
- no thread still carrying “keep the compatibility runtime” when deletion begins;
  that disposition defers retirement and requires a later explicit decision;
- old threads remaining readable in the web UI after their engine can no longer run;
- a verified engine-neutral visible transcript and export for every thread whose old
  engine reader will be removed;
- the promised net deletion demonstrated by the actual final diff.

Only then remove the Deep Agents builders and middleware, LangGraph checkpoint and
resume integration, dependency, operator escape hatch, and compatibility runtime.
The deletion change receives the full local review, deploy, web smoke, and external
review cycle.  If old clients require both implementations indefinitely, report that
Pi did not complete the simplicity goal and retain the cleaner single default rather
than claiming the migration is finished.

* Alternatives rejected

** Replace Deep Agents immediately

Rejected because Qwen provider behavior, harness maintenance, crash recovery, and
the web adapter are unproven.  Existing histories also have LangGraph-specific
checkpoints.  A big-bang conversion combines every risk and removes the rollback.

** Put Pi inside the model sandbox

Rejected for the first experiment.  The sandbox deliberately has no route to the
host, while the local model endpoint and host tools live outside it.  Adding a host
route from the model-controlled workspace to the provider gateway would expand the
strongest security boundary.  The contained host runner reaches only a one-use
gateway lease, exposes zero host model-tools, and keeps workspace operations in the
existing sandbox.

** Adopt a community “agent stack” package

Rejected because subagent, memory, sandbox, research, and GUI stacks each introduce
a competing product lifecycle or trust boundary.  Small source patterns may be
adapted after audit; the packages do not become runtime policy.

** Fork Pi first

Rejected until a concrete upstream limitation is reproduced.  The SDK, resource
loader, custom tools, and events cover the proposed experiment.  A fork would add a
fast-moving maintenance burden before Pi has earned adoption.

** Abstract every current Deep Agents type before the probe

Rejected because it front-loads a large refactor around an unqualified candidate.
P0 and P1 need no product abstraction.  P2 extracts only the boundary exercised by
current clients.

* Open decisions for implementation review

1. Whether Pi's built-in compaction preserves the exact current final-request and
   memory contracts, or Assist needs one small compaction hook.
2. The bounded rollback period and retirement policy for old Deep Agents threads if
   Pi becomes the default.
These decisions do not block P0 or P1 and should not be guessed in the design-only
change.  Emacsos runtime selection is not open: P5b fixes a server-owned default per
new conversation generation and gives the phone no picker.
