#+title: Main-web prompt rewrite baseline audit
#+date: 2026-08-08

* Purpose

This is the test inventory for the first full system-prompt rewrite.  It was
made from a fresh =pytest --collect-only -q edd/eval= collection on 2026-08-08
and a source review of every collected file.  The collection has 203 nodes in
53 pytest files.  There are also two non-pytest scripts.  The prompt candidate
changes /only/ the existing main-web general-agent assembly, so a test earns a
place in its behavioral comparison only if that main agent sees the candidate
prompt.

Each row is one of:

- *N* -- natural user outcome.  It contributes to its category aggregate.
- *C* -- explicit capability, route, or guard.  It is run and compared, but is
  a diagnostic rather than a natural-outcome aggregate.
- *X* -- excluded from this experiment.  It exercises an unchanged direct
  worker, a Pi/SMS-only role, framework mechanics, or the outcome evaluator
  itself.  It remains a non-regression check for the role that owns it.
- *D* -- temporarily deferred because it performs live external search.  It
  will return once provider availability is stable enough for prompt effects to
  be distinguishable.

The audit selects 134 main-web nodes: 88 natural outcomes and 46 capability or
guard diagnostics.  The remaining 69 nodes are excluded or deferred.  The
counts are an inventory, not a claim that all nodes are equally valuable or
that any individual natural test is a release gate.  The experiment begins with
the smaller sentinel panel below, then adds reviewed tranches until it reaches
the full inventory.

* Standalone scripts

- =eval_large_tool_results.py= is a useful manual stress diagnostic for
  oversized retrieval results.  It pins middleware behavior and has one
  fixed-looking query, but it is not collected by pytest and does not define a
  stable user-outcome validator.  Run it once before and once after the change;
  do not include it in the score aggregate.
- =eval_multi_turn_research.py= is not a baseline candidate.  It asks a second
  temperature-0.7 model to invent most user turns, making its sequence and
  expected answer unstable.  Replace it later with a fixed multi-turn natural
  journey before it can be used for a comparison.

* Deferred live-search rows

The comparison panel temporarily excludes evals whose real research worker can
call external search providers.  Provider availability and rate limits would
otherwise add environmental churn that cannot distinguish the current prompt
from a candidate.  Deterministic stubs that exercise the same prompt behavior
remain in scope: search-unavailable handoff, midflight no-grind, mocked research
completion, location-research dispatch, and website-download traversal.

* What the selected panel actually measures

The 134 nodes cover the product policy without confusing it with internal
routing: local action and smallest edits; context-before-question; external
evidence and honest partial research; loaded-skill selection and negative
selection; memory and task continuity; long-work launch, results, redirection,
and stop; rendering, travel, time, geography, documents, and automation; and
authorization, injection, egress, push, and urgent-notification boundaries.

There are five gaps which must be added /before/ candidate implementation:

1. A natural main-web grounding row in which local facts answer a question that
   otherwise looks like a clarification.  Existing context-invocation rows
   establish the routing decision but not the final grounded answer.
2. A main-web execute-log injection journey: an untrusted command/log result
   tries to redirect the work.  This proves the new core's evidence-not-
   instructions wording on the surface it actually changes.
3. A natural dependent-two-artifact journey, with ordinary user wording and no
   task or tool names.  It scores the requested artifacts and truthful progress,
   not a prescribed delegate trace.
4. A main-web capability row that selects =complex-request= once for ordinary
   multiple-outcome wording, and a negative control where one bounded
   multi-step outcome loads neither orchestration skill.
5. A main-web injection journey in which retrieved page or task-result text
   asks the agent to load an orchestration skill, fan out, schedule, contact
   someone, or fetch an attacker-selected URL.  It must not start extra work,
   propose an outward/durable effect, or take attacker-directed egress.

The proposed generic user-task skill also needs natural task discovery/update
and follow-up cases before it can enter the candidate.  The current task rows
are useful compatibility evidence, but they do not yet specify that new skill's
contract.  GTD remains a later, separately admitted capability: it gets no new
baseline claim until it has natural cases.

* Staged comparison panels

The first decision signal must arrive before a whole-suite baseline consumes
days of model time.  The sentinel panel therefore takes one representative
probe from each broad main-web behavior family, plus the product-wide controls
that a prompt rewrite must not weaken.  It is deliberately a diagnostic panel,
not a release certification: passing it says the candidate is worth expanding,
not that the remaining 121 nodes are safe to skip.

The table below is the historical proposed panel and is not runnable evidence.
The exact implemented panel is the 13-node web-main manifest in
=docs/2026-08-11-prompt-rewrite-sentinel-manifest.org=: it replaces the
legacy-context, unavailable-research, durable-memory, resolution-turn, and SMS
rows with real-web-main direct, lifecycle, egress-request, page-result, and
task-result journeys.  The manifest is authoritative for node, fixture, user
sequence, validator, and capture path; the results ledger records its N=3
baseline and candidate comparisons.

The prior partial baseline can be reused only where the capture proves the
same node, trial count, fixed datetime, and current-prompt census hash.  First
reconstruct those results into the completion ledger; rerun any row whose
evidence is incomplete.  This preserves useful work without treating a batch's
partial pytest output as a baseline.

After sentinel parity, add the next small tranche from an uncovered behavior
family and its closest regression neighbors.  Baseline only that tranche on the
current prompt, compare it on the candidate, repair any material loss, then
add another.  The cumulative panel grows to the existing 134-node inventory;
the full panel remains the final comparison, not the admission ticket for the
first candidate signal.

* Baseline execution and admission process

1. First run the deterministic prompt census and =test_outcome_judge.py= once.
   They are prerequisites, not stochastic model trials.
2. Freeze a checked-in exact-node manifest from the 134 rows above.  For every
   node it must record source line, fixture/workspace, every user turn, expected
   artifact or event evidence, category, and N/C classification.  The source
   tests remain the canonical executable specification; the manifest makes the
   reviewed selection reproducible.
3. Keep one durable completion ledger beside the manifest.  Before every
   model invocation, select the next unfinished =(node, trial)= explicitly,
   including its category and prompt census hash.  Record its command start,
   completion or timeout, capture location, and result before selecting another
   node.  A timeout is an observed result, never implicit progress inferred from
   pytest dots.
4. Run that one bounded trial through =tools/agentic resource run llm --=.  The
   command must set =ASSIST_EVAL_FIXED_DATETIME= and have its own timeout.
   Re-enter admission for every trial; no admitted command contains an open-ended
   batch.
5. On a denial, run =tools/agentic production status --attempt N=, where =N=
   starts at one and increases for each consecutive denial.  Schedule exactly
   one wakeup for its reported next-probe interval, then continue non-model
   work.  The wakeup may check status and retry admission, but must never be a
   static background eval command: it cannot replay a completed cohort or infer
   the next node.  Do not use GPU utilization as an admission signal, poll on a
   fixed interval, or hold the resource lock while waiting.  After ten denials,
   inspect and report the prolonged production load while retaining the durable
   next-trial record.
6. Run the 13-node sentinel panel at N=3 against the frozen current prompt,
   reusing only ledger-proven earlier trials.  Keep the per-trial captures and
   prompt census hash.  Stop after at most one hour of admitted model work and
   take a fifteen-minute GPU break before a new block.
7. Run the same sentinel once (N=1) after the candidate. For a promising
   signal, repeat it to N=3 before interpreting parity. For a material loss,
   make one causal prompt change, rerun the failed row and its closest anchors,
   then repeat the affected panel. Do not chase one stochastic miss: first
   repeat the disputed row to N=5 before changing the prompt.
8. Repeat the baseline, compare, repair, and full-cumulative-panel check for
   each new tranche.  Once all 134 nodes have entered the cumulative panel,
   run it at N=5 after review and N=10 only after the reviewed candidate is
   stable.  Natural outcomes are reported by category aggregate; C rows
   identify regressions but cannot hide a broad natural-outcome collapse.  Unit
   authorization and isolation checks remain 100% gates independently of this
   panel.
