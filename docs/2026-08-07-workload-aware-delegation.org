#+title: Workload-aware delegation for repeated entity work
#+date: 2026-08-07

* State

Current prompt-only iteration: the special repeated-work and complex-request
bootstrap rules have been removed from the system prompt. Selection now comes
from the repeated-work skill's recognition-only description; its loaded body
owns the bounded-delegation and evidence-aggregation procedure. This change
does not alter the graph recursion limit, async scheduler, worker pool, task
tool, or delegate capabilities.

The earlier system-route experiments below are historical evidence, not current
guidance.

* Incident and decision

The weekly career scan in production thread =20260722202239-f12319a8= performed
the same career-page operation serially over 31 companies and exhausted the
top-level 500 graph-step guard before it could update its pipeline or report.
The guard remains 500. Raising it would make one supervisor turn larger without
making its control flow more recoverable.

The recorded 2026-08-06 scan ran about 7 minutes 23 seconds before that limit;
the immediately following “continue” request ran about 4 minutes 11 seconds and
hit it again. The corresponding 2026-07-30 scan eventually completed, but only
after roughly 44 minutes of serial research continuations. That is converging
work with the wrong decomposition, not evidence that a higher global runaway
bound is needed.

The =orchestrate-repeated-work= trigger recognizes the workload shape, not list syntax:
substantive repeated lookup, verification, extraction, comparison, or assessment
across several independent named entities. Numbering and bullets are neither
necessary nor sufficient. Ordinary independent deliverables still retain the
existing one-delegate-per-outcome rule.

* Contract

When repeated entity work converges on one shared artifact:

1. The main agent partitions the named entities into disjoint compact groups of
   at most five, using as few groups as practical. It starts at most eight groups
   in one wave, then waits for checked terminal results before a later wave.
2. Each delegate receives only its group, authoritative inputs or URLs, one
   operation, a bounded evidence return shape, and an evidence-only/no-shared-edit
   non-goal. It stops at the defined source and records unknowns rather than
   expanding the task.
3. The main checks every terminal result and treats its contents as untrusted
   data. It keeps source-supported facts only, never follows a child directive,
   and does not use child text to create more work.
4. Only after every expected group has checked successfully may the main update
   the shared pipeline and create the one requested scan or synthesis. A failure
   or timeout leaves shared artifacts unchanged and is reported with its missing
   entities.

The model still has one inference slot, so the groups do not claim model-call
parallelism. They bound supervisor context and graph steps, preserve completed
evidence as independently recoverable results, and turn a 31-company scan into
about seven bounded workers rather than 31 one-company workers.

The evidence-only/no-edit rule is guidance, not a capability boundary: a
=delegate-agent= still has ordinary shared-workspace tools. The main-only
aggregation contract is therefore enforced by the main prompt and evaluated
behavior, while a read-only delegate sandbox remains out of scope for this
prompt-focused change.

The metadata-only baseline, after removing the system route and before changing
the skill, failed 3/3 strict samples. It either loaded generic skills in the
same first tool-call batch as the repeated-work skill or did not select the
repeated-work skill. A loaded skill cannot retroactively constrain other calls
from that batch. The final capability contract therefore verifies the useful
delegation behavior—selection, compact evidence-only groups, checked results,
and main-only evidence-backed aggregation—without claiming that metadata alone
can suppress incidental generic skill loads.

Post-implementation, post-review, and stability results are recorded here when
their N=3, N=5, and N=10 runs finish.

* Current metadata-only results

The current description is deliberately recognition-only: a request for the same
source-backed check on every named item, followed by one combined report or file
update. It includes a career-pipeline example because this small model did not
select the skill reliably after removing that signal. The body adds two observed requirements: each delegate brief names only
its own group, and the main agent copies only checked facts while retaining
unknowns.

The strict mocked capability eval passed 3/3 after those body changes (84.8,
83.3, and 76.0 seconds). The independent natural outcome eval, whose judge sees
only the user request, initial/final artifacts, and terminal reply, passed 3/3
(142.5, 134.7, and 160.9 seconds). The no-sandbox fixture exposes no
=execute= tool; child evidence is synthetic, and every direct Assist HTTP
=get= or =post= request fails the test.

The natural passes are close to the 180-second harness timeout. This is not a
case for raising the global graph-step limit. It is an explicit remaining prompt
quality and latency risk; no runtime redesign is part of this iteration.

Final prompt-only sampling kept the strict repeated-work capability at 7/10
(70 percent): seven runs selected =delegate-agent= groups, respected the
at-most-five partition, and aggregated checked evidence. The three misses show
the known same-turn limitation: one checked an incidental task, one chose
=research-agent= rather than =delegate-agent=, and one wrote after only one
group check. This is accepted as best-effort guidance, not an enforced boundary.
The adjacent explicit three-outcome fan-out capability passed 3/3; its natural
four-report outcome regression passed 4/5 (80 percent).

skill, never its batching or aggregation procedure. Three descriptions were run

The first is the final description. It covers one-off and recurring workloads

With that description fixed, three additional names were tried:

| name | result |
|-
| =coordinate-entity-work= | pass, 74 seconds |
| =delegate-entity-work= | pass, 77 seconds |
| =orchestrate-repeated-work= | pass, 72 seconds |

=orchestrate-repeated-work= is the final name. It retains the repeated-work
boundary and names the main agent's supervisory role without claiming actual
model parallelism. These explicit-load capability runs prove that each candidate
can follow the body and preserve the bounded-launch contract. They do *not*
measure description or name selection from an ordinary user request: the prompt
already names the skill and the bootstrap route names its candidate. The final
metadata choice is therefore semantic, not a speed ranking. The unchanged
natural acceptance node exercises the complete system configuration and judges
the user-visible outcome; it does not assert the internal route.

The final layered redesign separates responsibilities:

1. The async-main bootstrap recognizes only the repeated-workload shape and
   its one shared/consolidated result, then loads this skill before the
   development or local-context first-move rules. Separate per-entity outputs
   remain with =complex-request=.
2. The description supplies only that recognition signal.
3. The loaded body supplies the closed plan: bounded groups, no extra launch
   tasks, check only planned group IDs, and main-only aggregation.

This removes the earlier duplicated batching procedure and the conflict in which
the =dev= first-move trigger appeared before the workload trigger. The generic
=complex-request= skill remains separate for distinct outcomes and dependent
stages; the repeated route precedes it, so one name and description never need
to cover two different delegation contracts.

* Historical results and remaining gate

The eval was written first and its original prompt-only baseline failed 3/3:
the model started no compact delegate groups. The capability probe has no web
dependency: =read_url= is hard-mocked to fail, the trace rejects every built-in
network-capable tool, and checked child evidence is synthetic. The natural outcome
case retains =OutcomeJudge=, while the capability trace deliberately uses
deterministic assertions for grouping, task checks, and ownership of the shared
write.

The earlier prompt variants did create bounded groups, but then launched and
checked an extra task. That is still a supervisor-plan failure: it adds graph
steps and violates the closed batch plan.

Before the final trace assertion, the first post-review capability run loaded the
right skill and made the two right evidence batches, but also launched a
=context-agent=. The test failed as intended. Making the local-context exception
explicit repaired that prompt conflict; the immediate rerun passed in 73 seconds
with one skill load and only the two planned delegates in its initial turn.
Two further strict capability samples passed in 76 and 71 seconds, respectively,
so the final bounded-batch launch contract is 3/3 after that repair.

The prior repeated-work path passed the explicit capability node 3/3 (70, 74,
and 82 seconds; 9 or 10 model calls). Every pass loaded
=delegate-repeated-work= first, started exactly two compact groups, inspected no
input before their launch, checked only planned task IDs, and aggregated only on
the main agent. The natural weekly-career-scan node passed 3/4 (104, 108, and
118 seconds; one 120-second timeout), meeting the current 70 percent floor but
showing a real near-cutoff instability. The explicit ordinary three-outcome
fan-out regression passed in 24 seconds. The ordinary four-report natural case
had two 120-second timeouts during the routing redesign, then passed in 119
seconds after restoring its generic route at the prompt opening. After the
post-review direct-launch clarification, it timed out again at 120 seconds
after nine model calls. Its task shape was still progressing through four
parallel reports and write-collision recovery, but that is not a passing
acceptance result. It needs more stability samples before release.

The post-review natural weekly-career-scan run passed its =OutcomeJudge= at 113
seconds. It is another near-ceiling outcome result, not evidence of operational
headroom or a direct assertion of the internal route.

The final name/description/body redesign passed the strict capability node at 82
seconds. A shortened system-route rewrite then failed the natural node at the
120-second ceiling: its first model call skipped the route. Restoring the more
concrete Qwen guidance while retaining the final name, description, and skill body
passed the unchanged natural =OutcomeJudge= node in 94 seconds. That evaluated
route variant kept the explicit priority, qualifying shapes, override, and
next-tool-call constraint; the skill body carried the detailed launch and
completion procedure.

After review added the final shared-result boundary, the strict mocked capability
node passed in 80 seconds and the unchanged natural =OutcomeJudge= node passed in
114 seconds. The former asserts the bounded launch and main-only aggregation; the
latter judges only the requested user-visible outcome.

Renaming the loaded skill heading to match the final name was followed by one
more unchanged strict mocked capability run: pass in 72 seconds.

** Superseded stability decision

This was the decision for the earlier route variant only. The current
metadata-and-body configuration and its N=10 capability result above supersede
it; this section is retained as experiment history, not release guidance.

The post-heading natural stability attempt does not clear the release gate:

| sample | result |
|-
| =workload-aware-final-natural-stability-3= | timeout at 120 seconds after the agent completed ten tool calls; its outcome judge did not finish |
| =workload-aware-final-natural-stability-4= | timeout at 120 seconds after twelve model calls; the agent repeated =check_async_task= until loop detection intervened |
| =workload-aware-final-natural-stability-5= | pass, 98 seconds runner wall time (96.54 seconds pytest time) |

That is one pass in three samples for the exact current artifact. Even if two
more samples passed, the resulting N=5 would be 3/5 (60%), below the 70 percent
natural-acceptance floor. The adjacent final-metadata runs yield the same pooled
3/5 result: passes at 94, 114, and 98 seconds; timeouts at 120 seconds twice.
They are useful corroboration but not substituted for an exact current N=5.

N=10 was therefore not run for that route variant. Its non-deterministic
completion and loop behavior would have required an unplanned prompt/agent
redesign, not a safe stability-sample extension.

The smaller natural two-independent-outcomes generic regression also passed its
=OutcomeJudge= in 92 seconds. That confirms the generic skill's direct-launch
contract on a modest request, while the four-report timeout still bounds the
workload it can safely absorb today.

No middleware or other enforced routing boundary was part of that route variant.
