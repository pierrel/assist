* Requested outcome and scope

Main, delegate and researcher agents need a bounded way to retain important
exact text from user and tool context in the existing immutable thread store.
Retrieved source URLs already register automatically. This change must keep
source citation identity, navigation authorization, invalid-reference behavior,
ordinary links/code, current file updates and child completion working.
Registration preserves supplied bytes. It does not establish factual truth,
required-detail coverage, a correct source association or independent verification.

** Alternative considered: protect a complete line, paragraph or table row

The agent registers the complete exact block it wants preserved. Its generic
token occupies a line by itself in a reply or =write_file= content, or in a
research draft that the existing finalizer resolves. For example, the stored
value can be this complete Markdown row:

#+begin_example
| Søren Quill | QL-01lI-7b92-0O5a | Hold at 4 °C; do not freeze. |
#+end_example

The model writes its table header and then =ref:<record-id>= alone on the next
line. Binding inserts the complete stored row, preserving the surrounding
newlines. To protect just an ID, it may put the ID on its own line. To place an
ID inside a sentence or table cell, it instead registers that whole sentence
or row. It cannot interpolate a generic token inside a larger line.

Generic tokens are unsupported in =edit_file= arguments; the tool returns
explicit feedback before effects. The agent reads the saved literal file and
uses normal exact edits, as in the passing receiving-note baseline. A changed
block can receive a new immutable record; an old record never changes. Ordinary
inline source citations and existing source-draft updates remain available.

This is the smaller proposed boundary. It protects exact blocks and keeps
newline-separated insertion from creating new reference syntax across seams.
It constrains inline names, IDs, table cells and generic edit interpolation.
Reserved unescaped case-insensitive =ref:= text inside a generic value is
rejected explicitly. Invalid generic placement must be rejected
before source-link parsing, including a generic token hidden in a link label.

** Chosen: interpolate exact values inside sentences, rows and edits

The agent can store =QL-01lI-7b92-0O5a= alone and place its generic token after
=Shipment ID:= or inside a Markdown table cell. It can reuse a generic token
in an edit preimage or replacement. This is more flexible than Option A.

It requires a precise ownership contract for every pass. A first write must
save literal exact text; a later read must return that text without granting
URL authority to generic expansions. An edit must match the exact current
preimage, and its *complete resulting file* must remain exact after later report
finalization or checker reads. Validating =old_string= and =new_string= in
isolation is insufficient. Source refs that were intentionally present before
the edit must continue to work. Streamed and canonical messages must agree.

The bounded implementation uses full-text, single-pass expansion with
an explicit stability check. Reference-bearing =edit_file= arguments retain
surrounding newline context in *both* exact old/new strings, enclosing the edited
sentence or table row. References within that fragment remain inline. Those
preserved boundaries prevent joining an inserted value to unseen file
prefix/suffix syntax without a racy full-file precheck. Ordinary literal edits
keep the existing contract. The natural receiving-note row must demonstrate
that ordinary edits remain usable. The explicit mechanism probe demonstrates
reference-bearing edit fragments matching the saved file's exact bytes.

All supported file-tool writes/edits eagerly expand *both source and generic
references* in every role. Saved-file reads remain literal; checker reads and host/sandbox/parent
completion validate literal bytes without rewriting them. Unsupported raw legacy/shell drafts fail
before cleanup. An old source-token edit preimage now binds to the canonical
URL, so older unbound drafts require their actual literal preimage through an
existing file operation; no migration or repair mechanism is added.

A generic-bearing response uses whole-message buffering to check the same
full text before emission. Stores without generic records retain incremental
source streaming. Once any generic record exists, *every subsequent response*
buffers as a whole, including source-only or reference-free responses. Generic
tokens work in text, table cells, inline code and source labels. Ordinary HTTP
URLs are literal regions, including a URL that contains a reference-looking
substring. Source-link destinations still require source-kind records.

An explicit backslash immediately before =ref:= shields a literal token. The
backslash stays in records, files and replies; no implicit decoding happens on
any later pass. Unescaped =ref:= inside a generic value is rejected, including
legacy text rows encountered during expansion. Terminal control sequences are
also rejected rather than silently sanitized. This does not claim arbitrary
unescaped reference-looking quote support. Tests exercise retained escapes,
repeated binding, latent label/code tokens and forbidden generic link targets.
A complete-postimage check with write ownership or
durable escaping metadata would be a larger alternative if the bounded approach
fails a concrete ordinary-value case. No tracking framework is being added
preemptively.

** Actual minimal edit-boundary counterexample

A deterministic reproduction on unchanged =c2d2739= used a generic stored value
of =[= and an existing trusted source URL. The proposed replacement value is
stable when checked alone, yet joining it to the unchanged file creates source
syntax that the existing resolver later changes:

#+begin_example
Existing file:             OLD Label](ref:r65caba095a7242391242644810866049)
Edit old_string:          OLD
Generic replacement value: [
After the edit:            [ Label](ref:r65caba095a7242391242644810866049)
After later source bind:  [ Label](<https://source.example/exact-article>)
#+end_example

The example used actual SQLite rows and the existing source resolver. It did
not add a generic runtime implementation. The original value =[= contains no
=ref:= literal: this is a join-boundary problem, not merely rejection of a
reference-looking quote. Ordinary names and IDs such as =Søren Quill= and
=QL-01lI-7b92-0O5a= do not themselves have this ambiguity. A quote containing
literal =ref:= was a separate syntax boundary in the option review. The
selected implementation requires the explicit retained backslash described
above; unescaped reserved syntax is rejected rather than silently rewritten.

The independent reviewer also demonstrated a message seam: =[= followed by
= Label](ref:<source-id>)= forms a new link after generic insertion. Put-time
reserved-syntax checks alone therefore cannot establish arbitrary inline
literal safety. The selected inline implementation compares the complete result
and repeated passes, rejecting the demonstrated seam before effects.
